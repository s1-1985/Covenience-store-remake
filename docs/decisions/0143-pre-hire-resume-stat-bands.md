# 0143: 採用前レジュメ能力の粗いバンド表示(タスク#73)

## 背景

タスク#67〜72(アセット統合一巡)がマージされた後、ユーザーから
「システム面に戻る」との選択があった。`PROJECT_MEMORY.md`第21.3節
「NEW findings not yet implemented」の候補リストから、他の候補
(町の施設配置・ライバル店AI・シナリオ選択構造など)がいずれも
未実装の新規メカニクス(町の空間配置システム、ライバルAIループ、
シナリオ選択画面)を前提とする大掛かりな変更になるのに対し、
「採用前レジュメ能力の粗いバンド表示」は唯一、既存の`hire_candidate_
option`ドロップダウン1箇所に閉じた、純粋な表示上の追加であり、
必要なデータもすでに`staff_candidates`に全てCONFIRMED_OFFICIALとして
存在していたため、これを選定した。

第三攻略本の再確認(タスク#65で発見)により、以下が直接確認されている
(`docs/research/strategy-guide-third-companion-book-full-extraction-
2026-09-24.md`より): 「人材募集した段階では、その人のこまかい能力
まではわからない。表示された4つの能力では想像するしかないのだ。」
——原作の採用画面は、体力・学歴・敏捷性・社交性の4つのレジュメ能力
それぞれについて、実際の数値ではなく「普通」(40〜69)/「高い」
(70〜100)の粗いバンドのみを採用前に開示する。

`_sg_staff_candidate()`(`reference_sim/conveni_sim/baseline_data.py`)
の既存ドキュメントが明記する通り、`academic_background`(学歴)は
「賢さ」ステータス由来であり、この4レジュメ能力(体力=`stamina`、
学歴=`academic_background`、敏捷性=`agility`、社交性=`sociability`)は
既にタスク#32でCONFIRMED_OFFICIALとして全35候補分`vertical_slice.json`
の`staff_candidates`に格納済みである——欠けていたのは数値そのものでは
なく、「採用前は粗いバンドしか見せない」という原作のUI挙動だった。

## 決定

### 既存の数値表示を削除せず、確認済みバンドを追記する

このプロジェクトの`hire_candidate_option`ドロップダウンは、タスク#56
以来、レジ・補充能力の実数値を採用前から表示している(原作より情報量が
多い、意図的な簡略化)。原作の挙動(数値を隠しバンドのみ見せる)に
完全一致させて既存の数値表示を削除することも検討したが、これは
プレイヤーが既に見ている情報を減らす後退的な変更になり、単一の
アセット/UI判断としては影響が大きすぎると判断した。代わりに、確認済み
バンド情報を既存の表示文字列に追記する形で実装した(例:
「竹中小百合 — register 14 / replen 12 / ¥6,720/day (体力高い 学歴高い
敏捷性普通 社交性高い)」)——既存情報を一切失わず、原作の採用画面が
実際に開示していた粗い情報も追加で確認できる。

### バンド境界は原作の確認済み数値をそのまま使用(REMAKE_BALANCED_DEFAULTではない)

`_resume_stat_band(value: int) -> String`は`value >= 70`で「高い」、
それ以外で「普通」を返す。40〜100という全35候補の実際の値域
(最小40・最大100)は、確認済みバンドの範囲(40〜100)と完全に一致して
おり、境界外の値は発生しない。この閾値は本プロジェクトの推測
(REMAKE_BALANCED_DEFAULT)ではなく、原作から直接読み取れる確定値
(CONFIRMED_OFFICIAL)であるため、`CLAUDE.md`のREMAKE_BALANCED_DEFAULT
3点セットタグ付けの対象外——通常の証拠引用コメント+テストで十分と
判断した。

  - 実際のロースターメンバー`hamada_yuko`(体力65・学歴55・敏捷性70・

## 明示的に対象外

- 既存の数値表示(register/replenの実数値)の削除・原作完全準拠化は
  見送った——プレイヤーが既に見ている情報を減らす変更であり、今回の
  スコープ外の判断を要する。
- 体力(`stamina`)自体が「実際のパラメータ」であり、他の3つのレジュメ
  能力(学歴・敏捷性・社交性)が予測するとされる実能力ペア
  (レジ・セキュリティ/商品補充・店内移動速度/サービス・清掃)との
  相関モデル自体は実装していない——本プロジェクトは既にこれらの実数値を
  タスク#32でCONFIRMED_OFFICIALとして直接保持しているため、レジュメ
  能力から逆算する必要がない。
- `reference_sim`側への同等ロジックの移植は行っていない——
  `reference_sim`には採用UIそのものが存在しない。
