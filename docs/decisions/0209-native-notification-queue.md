# 0209 — 原作の通知予約と順次表示を本体へ接続

## 問題と変更

同じ更新で通知が複数発生すると、PhoneUIは最後の1件だけを表示し、ほかを既読にしていた。原作の予約枠と表示中状態もJSON保存の対象でなかった。

`ProgramNotifications`に原作の50枠×160バイト、予約・取り出し・初期化を移植。通常予約は枠1から、signed-byte mode5だけ枠0から探す。満杯時は-1。未解釈領域、表示中本文、種別7/8による本文非更新、音声番号100/101/119/110の変換を保持する。表示中は次の通知を取り出さない。mode1の種別別タイマー、mode2の6値と初期2か月の比較抑制、INT_MINの例外（先頭5値だけ）、mode3の評価内訳と解除ビットを移す。

表示計画は町背景更新・窓・本文・月次・年次の原呼出順と座標を返す。タイマー0だけでは終了せず、音声無効／終了の状態から表示を閉じる。これはハードウェアAPIの実装ではない。

本体の店長助言・店長報告・売れ行き・ランク・月次・年次・ライバル開閉店・雑誌等を予約へ接続した。年間売上の帳簿が切り替わった後も評価時点の年次売上を使う。月次の第3値は所持金ではなく「他経費」であり、既存の一時費用台帳へ対応付ける。従来型の通知も順に表示する。

予約全体、表示中の文脈・本文・状態をJSON保存。表示途中の再開は同じ通知から続き、次の通知も残る。古いJSONには空予約を適用する。予約長などが壊れた保存は本体状態を変更する前に拒否する。ゲームのリセット・読込みで通知オブジェクトが変わったとき、画面も同期する。

## 検証

`export_notification_cases.py <algorithm-analysis>`で独立した解析モデルから96予約／消費条件と640表示条件を生成。予約8000バイト全体のハッシュ、本文、状態ワード、取り出し順、音声番号、描画／停止要求の呼出順と符号付き座標をGodotと照合する。満杯、mode5、signed-byte、初期月、INT_MIN、評価解除、ゼロタイマーでも表示継続、JSON往復を含む。

実シーンの追加試験は、同時発生2通知→表示途中保存→読込み→同じ通知表示→タップ→次通知、実月次決算から月次表示、実年次集計から評価表示、壊れた保存の拒否、旧JSON受入れを確認する。

内装の既存行列試験は、原作床の摩耗で整数へ変わったセルとJSON後の数値セルを各マスの床コードで比較するよう修正した。各小型サンプルで最初の売上まで（上限2000更新）を確認し、長時間営業は専用の人物・10日営業試験に任せる。試験実行器はGodotのアサーション失敗後にも終了でき、成功の出力がない状態をPASSとしない。

## 未完・仮動作

原音声再生は未接続である。REMAKE_BALANCED_DEFAULTとしてタップまたは読み取り時間の経過を音声終了境界の代わりに使う。原タイマー0を通知終了条件にすり替えない。原文字コード・原描画パケットの画面再現は未移植で、Unicodeラベルのスマホ画面を使う。この仮動作はコード・設定・テストに記す。

通知生成側の全分岐／原文の完全移植ではない。誘致完成など未照合の呼出引数は原予約へ推測で入れず、既存通知の順次表示を使う。既存の他経費の台帳対応も全原呼出元を復元したものではない。原音源、原カード相互変換、終了演出、原操作画面など、全反映版の残作業を完了したことにはしない。今回は途中APKを配布しない。
