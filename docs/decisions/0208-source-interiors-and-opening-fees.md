# 0208 — 原作の敷地と内装サンプルをAndroidへ移す

## 問題と変更

前回0.2.0は町・営業処理・画像を移したが、開店時の什器配置と、上に屋外を足す構造は仮のままだった。今回、原作の30レイアウトを直接読み出し、6種類の敷地に各4種類ある家具入りサンプルを本番の開店経路へ接続した。6種類の空レイアウトもデータには保持するが、空店舗からレジを設置する操作は未接続なので選択肢にしない。

- 原作の敷地全体を使用。小型20×20、中型24×24、大型28×26の半マス座標。屋外・壁・入口・床柄・什器の位置と向きを保つ。縦長の入口は左、横長は上にある。
- 壁を固定障害物として歩行と配置判定へ渡し、セーブ後の再開でも維持する。原作の床タイルで壁と入口も描画し、仮の外周壁とIN/OUT表示を外す。
- 不足していた16種の什器を追加し、原作53種の画像IDと接続する。サンプル内の自販機・駐車場も同じ敷地座標で扱う。
- 開店前に原作サンプル1〜4を選択できる。同じ店舗サイズのままサンプルだけ変えても、選択した内装を組み直す。
- 建物代に加えて初期什器・移植した商品の仕入代を支払う。選択画面に3つの内訳を表示し、全額を払える場合だけ建てる。既存の小型店だけを選べる初期制限は継続する。
- 0.2.1-source-interior、versionCode23。同じcom.conveniremake.recoveredと前回の署名鍵を使う。

## 出典と再生成

原EXEのSHA256は`d6a167a1c9e0fe98d7e44e12968caa489ac3eb7ed3b9e46012a188af8432b1fd`。`800A2074`から3108バイト刻みの30レイアウトを、既存`layout-tables.json`と全バイト照合して抽出。什器記述は`80099F0C`、商品は`8009CE08`と`8009CE14`。`rival_helpers.load_layout/equipment_total/inventory_total`、`interior_floor_display.floor_records`、`runtime_tables.runtime_product_images`を参照した。

`python tools/ps1/export_recovered_runtime.py <algorithm-analysis>`、続けて`python tools/ps1/export_source_interiors.py <algorithm-analysis>`でデータと画像を生成する。後者は繰り返しても不足什器定義を落とさない。元EXE・BIOS・ディスクやエミュレータをAPKに含めない。

## 検証

Python既存786件成功（既知expected failure 1件）。Godot4.3の既存6本と追加source_interior_smokeを実行。追加テストは24サンプルの固定壁・経路・費用・JSON保存/再読込を検査し、小型店の全8サンプルで営業と売上を確認する。実シーンの選択ボタンを操作し、サンプル2に変えて建てた結果も確認する。スクリーンショットはLinux/OpenGLでAndroid UIを描画したもので、Android実機画面ではない。APKのバージョン・同じ署名証明書・同梱データを検査する。

## 残る制約

原作データの配置を使うが、ゲーム全体の完全再現ではない。REMAKE_BALANCED_DEFAULT: 什器への到達点は原作方向を優先した到達可能な隣接点、店員の開始点は入口近くの到達可能点。客・店員の経路探索と行列、外見と性別の対応、スマホUIと音楽は引き続きクライアント側のもの。

レジ一体の宅配便在庫、および元の商品表の27番目の特殊カテゴリはrawの在庫ワードを保持するが販売へ未接続。この未接続在庫の代金は請求しない。屋外/屋内別の配置許可、空店舗からの手動開業、原作そのもののメニュー・音源・人物アニメーション、ライバルのサイズ/採用選択、全シナリオは未完了。解析成果全部を反映済みとは呼ばない。

旧0.2.0のセーブを続ける場合、そのセーブの旧レイアウトを維持する。今回の開店手順と初期内装を確認するには「はじめから」を使う。Android実機・タッチ操作は未確認。
