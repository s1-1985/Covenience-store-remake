## 1. 最重要の発見: 3.3節の「未解決」記載は古い情報だった

前回の引き継ぎ記録(2026-09-18その1)第3.3節は、以下3項目を「前回セッションから
持ち越し、今回未着手」としていた:

- ベンチの維持費(既存168円 vs 攻略本160円)
- 大型店舗建設費の攻略本内部矛盾(18,000,000円 vs 24,000,000円)
- 顧客の10列行動データの分解(スキャン解像度の限界で2回失敗)

しかし`docs/research/strategy-guide-fixture-crosscheck-2026-09-16.md`第9節
(2026-09-17追記)を読んだところ、この3項目は**このGodotクライアント作業とは別の
セッション(`reference_sim`側、Codexとの共同作業と思われる)によって、2026-09-17
時点で既に解決済み**だったことが判明した:

- ベンチ維持費: ユーザーから同じ4分割PDFを高解像度(400dpi)で再アップロードされ、
  「衝突する内容は攻略本準拠」の明示的指示のもとで160円/日に確定・
  `reference_sim/conveni_sim/baseline_data.py`へ反映済み。
- 大型店舗建設費: 攻略本内部で7箇所が18,000,000円、1箇所のみ24,000,000円という
  「攻略本自身の内部矛盾」と判明。外部資料との対立ではないため、多数決で
  18,000,000円を採用(この判断自体は変更なし)。
- 顧客の10列行動データ: 高解像度再スキャンで全143行を10桁(ス/素/マ/集/買/価/距/
  サ/平/休)明瞭に判読でき、`CUSTOMER_VISIT_SCHEDULE`を完全に置き換え済み。

さらに`game/data/vertical_slice.json`を実際に確認したところ、ベンチの
`maintenance_yen_per_day`は既に`160`(service_bonus`4`)になっており、**Godot
クライアント側にも既にこの解決済みの値が反映済み**だった(タスク#31のstore-grid
移植時、またはfixture_catalog初期作成時に、`reference_sim`の解決済みデータから
直接ポートされていたと推測される。具体的にどのコミットで最初にこの値が入ったかは
未調査)。

大型店舗建設費(18M/24M)については、Godotクライアントがそもそも複数店舗
サイズ(小/中/大)の建設費データを一切実装していない(現状は単一の固定店舗のみ、
店舗拡大は`chain_visitor_milestone.gd`の`try_expand_chain()`が抽象的な土地代
(`LandValuePolicy`)を使うのみで、店舗サイズ別の建設費テーブルは未使用)ため、
この項目は「未解決」ではなく単に「まだ必要とされていない」。

**結論**: 前回の引き継ぎ記録第3.3節の内容は、作成時点で既に古くなっていた
(2026-09-16の引き継ぎ記録の内容をそのまま踏襲し、2026-09-17の`reference_sim`側の
解決を確認していなかったと思われる)。今回この誤りを訂正する。今後、同種の
「攻略本の数値矛盾」系の記録を参照する際は、`docs/research/`配下の最新日付の
crosscheckドキュメントを必ず先に確認すること。

## 2. このセッションでやったこと

1. 添付PDF4点(本1/本2/本2-1/本2-2相当、計115頁)を`pdfimages`で画像抽出し、
   目視で内容を把握(300dpi、コンタクトシート形式で概観 →
   個別ページを高解像度で確認)。
2. 上記の発見(3.3節が既に解決済み)を確認。
3. ユーザーに「3.2節(同時複数顧客/待ち行列、サンプルレイアウト読み込み、什器
   attention差別化)に新規タスク番号を割り振って着手するか」を確認 →
   まず「UIギャップ修正を優先」の回答を得たため、3.2節はいったん対象外のまま
   タスク#35に着手。
4. **タスク#35**(STORE STATUSパネルのUI表示ギャップ解消、前回記録3.1節):
   `vertical_slice_simulation.gd`の`snapshot()`が既に返している
   `star_rating`/`popularity`/`town_population`/`town_store_count_including_
   rivals`/`land_value_yen`を、`main.tscn`のSTORE STATUSパネルに新設した
   ラベルペア(`RatingTitle`/`RatingValue`、`TownTitle`/`TownValue`)で表示する
   よう`main.gd`を配線した。シミュレーション側のロジックは一切変更していない。
   決定書0104。PR #205として作成、CI green確認後ユーザーがready化しマージ済み。
5. ユーザーから「進めて」の指示を受け、3.2節の1件目に着手する判断とした。
   ブランチはPR #205マージ後に`origin/main`から作り直した。
6. **タスク#36**(同時複数顧客・チェックアウト待ち行列、前回記録3.2節1件目):
   `reference_sim/conveni_sim/checkout.py`の`CheckoutStationRuntime`が既に
   複数顧客同時待機・非FIFO強制のサービス選択を実装済みだったことを発見。
   `CustomerRoster`に`can_admit_concurrent()`(新規、容量ベース)と
   `all_settled()`(新規、「入店中の客が0人」)を追加し、既存の単一顧客判定
   `can_admit()`は自動デマンド来店(`demand_admit_if_due()`)専用として温存。
   `start_explicit_customer()`と`start_next_customer()`(「Admit next
   customer」ボタン)の両方が`can_admit_concurrent()`経由で複数客を受け入れる
   ようになり、プレイヤーが通常のプレイ操作でも同時複数客を実際に見られる
   ようにした。`step()`を客ごとの状態遷移と`_dispatch_checkout_queue()`
   (単一レジの直列化、FIFO、REMAKE_BALANCED_DEFAULT)に分離。レイアウト編集の
   安全確認8箇所は`all_settled()`へ移行(`can_admit()`のままだと複数客が
   同時に存在しうる状況で誤動作するため)。決定書0105。PR #206として作成、
   CI green確認後ユーザーがready化しマージ済み。
7. ユーザーから再度「進めて」の指示を受け、3.2節の2件目に着手する判断とした。
   ブランチはPR #206マージ後に`origin/main`から作り直した。
8. **タスク#37**(サンプルレイアウト読み込み機能、前回記録3.2節2件目):
   研究ノート(`docs/research/ss-layout-entrance-register-and-chain-
   cannibalization-2026-09-06.md`第3節)は「サンプルレイアウトが存在し、
   読み込みは簡単には元に戻せない」ことをB+/B級で確認しているが、サンプルの
   具体的な中身・数・正確な取り消し/売却の仕組みは一切未確認。このため
   「メカニズム自体」(読み込み・検証・破壊的上書き)をCONFIRMEDな要件として
   実装し、「サンプルの具体的な中身」(2件: `default_layout`=現状の初期配置と
   同一、`with_bench`=同じ配置+ベンチ1台)はこのプロジェクト独自の
   REMAKE_BALANCED_DEFAULTプレースホルダーとして明示的にタグ付けした。
   `try_load_sample_layout()`は既存のID(什器)を再利用する場合は無料、
   新規追加分のみ通常価格で課金(「正確な売却比率」という別の未確定要素を
   発明せずに済む設計)。取り消し(undo)・売却機能は研究ノートの指針
   (「別々の未解決課題として扱うこと」)に従い実装していない。在庫が
   孤立する組み合わせ(仕入れ済み商品を持つ什器をサンプルが含まない場合)は
   拒否する。`main.tscn`にOptionButton+Buttonを追加し、実際のプレイ操作から
   到達可能にした。決定書0106。
