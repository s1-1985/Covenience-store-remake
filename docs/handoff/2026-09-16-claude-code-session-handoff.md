## 3. 現時点で残っているタスク

### 3.1 8公式の実際の組み込み方針が未決定(設計判断が必要)

決定書0079では「`store_runtime.py`に配線する」という前提で書いたが、**このセッション終盤に
再調査した結果、その前提が誤りだったことが判明**した。`store_runtime.py`は実は中央
オーケストレーターではなく、`promotion.py`/`month_boundary.py`/`monthly_report.py`/
`visitor_milestone.py`などと同様、「呼び出し元が外部で組み立てる」独立モジュールの一つに
過ぎない(該当箇所を`grep`した限り、`store_runtime.py`自身もpromotion/month_boundaryを
importしていない)。つまり:

- `store_value.py`/`store_rating.py`/`store_events.py`(PR #194で新規追加)は、実装・
  テストは完了しているが、**どこからも呼ばれていない**(意図的にそうなっている。他の
  standaloneモジュールと同じ設計)。
- 「いつ、どの呼び出し元が、どういう順序でこれらを呼ぶか」は、まだ決まっていない設計判断
  であり、次のセッションで着手する場合は実装作業ではなく**設計相談**から始めるべき。

### 3.2 万引き判定に使う「顧客マナー値」の実データ源が未確定

`store_events.py`の`shoplifting_is_possible(customer_manner_value, store_security_value)`
は実装済みだが、`customer_manner_value`をどこから取ってくるかが未解決。理由は3.3参照
(`behavior_stats_raw`が分解されていないため)。

### 3.3 顧客の10列行動データは分解できない(仕様上の限界、要再挑戦なら別の手段が必要)

`CustomerVisitProfile.behavior_stats_raw`(ス/素/マ/集/買/価/距/サ/平/休の10項目)は、
**列の意味は完全に確認済み**(`models.py`のdocstring参照、書籍頁134の凡例⑦〜⑰から転記)
だが、行ごとの実データの桁数を数えるたびに結果が変わる(同じ客層の隣接行で9個・11個など
不一致)。これは2回(それぞれ別の日、別の読み方)試みて同じ壁にぶつかっており、**現在の
スキャン解像度では原理的に信頼できる分解ができない**と考えられる。次に試すなら:
- より高解像度のスキャンを入手する、または
- 印刷物側で該当ページの拡大コピーを別途撮影してもらう
のいずれかが必要。今の画像をどう工夫して読んでも解決しない可能性が高い。

## 5. アーキテクチャに関する重要な理解(このセッションで判明)

`reference_sim/conveni_sim/`には**中央オーケストレーターが存在しない**。チェックアウト、
清掃、月次境界、社員成長、プロモーション、そして今回追加した8公式まで、全ての仕組みは
「独立して実装・テストされ、外部の呼び出し元(将来のGodot統合や統合テスト)が組み立てる」
という設計で一貫している。`store_runtime.py`はグリッド/顧客/店員/在庫/チェックアウト/
交通/清掃/customer_share/経済/購買/営業時間/マネージャー雑誌イベントの一部だけを合成した
ものであり、promotion/month_boundary/monthly_report/visitor_milestoneや新規8公式モジュール
は含まれていない。次にこの領域で作業する際は、この前提を踏まえること。
