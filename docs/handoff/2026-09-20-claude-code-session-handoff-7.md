## 2. このセッションでの方法論の是正(最重要、必ず読むこと)

タスク#58〜#59完了後、私はユーザーへの状況報告で以下のように述べた:

> 特に、この規律(証拠のない数値は発明しない)の性質上、原作の一部の
> 仕様は永久に「証拠待ち」のまま残る可能性もあり、その意味で従来の
> 「100%完成」という概念自体がこのプロジェクトには馴染みにくい

ユーザーはこれを明確に誤りだと指摘した。理由:

`CLAUDE.md`自身が3段階の優先順位を定めている:
1. 確認済み証拠
2. **確認済みの関連データからの類推**(バケット2)
3. **本プロジェクト自身のREMAKE_BALANCED_DEFAULTプレースホルダー**
   (バケット3、「最後の手段だが、常に利用可能」)

つまり、証拠が完全には揃わなくても、バケット2(類推)またはバケット3
(タグ付けされた投機的な仮置き)が常に利用可能であり、「証拠が見つかる
まで永久に未着手のまま」という状態はこの規律と根本的に矛盾する。実際、
既存の`land_value_policy.gd`の地価成長式や`remake_rival_policy.py`の
ライバル判断ロジックは、まさにこの手法(確認済みの関連要素から式全体を
バケット2/3で組み立てる)で既に実装済みだった。

**この是正の実務的な意味**: 「関連する仕組み(空間モデル・複数店舗機構
等)がまだ存在しない」ことは、`reference_sim`側でその公式・ロジック
自体を実装することを妨げる理由にはならない。妨げるのは「Godot版
(`game/`)へ実際にプレイヤーが触れる形で配線すること」だけである。
このセッション後半(タスク#60・#61)は、この区別を明確にして進めた:
**reference_sim側の公式実装は類推ベースで積極的に進める。Godot側への
UI配線は、対応する新しいゲームメカニクス(複数店舗配置・施設誘致等)が
必要になるため、既存の境界(決定書0095)通り別タスクとして先送りする。**

次のセッションも、この区別を踏襲すること:「まだ仕組みがない」を理由に
**reference_sim側の実装自体**を止めてはならない。type 2/3の類推・
投機的仮置きを積極的に使い、タグ付け(コード内コメント+evidence_note+
テストアサーション、`CLAUDE.md`のタグ付け規律)を徹底すること。

## 5. 次セッションへの引き継ぎ・残っている候補

`PROJECT_MEMORY.md`第21.3/21.4節を参照。このセッションでreference_sim
側の主要な公式(土地購入費・治安施設ボーナスの空間探索)は実装できたが、
以下は依然として未着手:

- **`game/`(Godot版)への配線一式**: タスク#60(土地購入)・#61(治安
  施設)ともに、reference_sim側の公式は実装済みだが、Godot版には
  「複数店舗を配置する」「施設を誘致・配置する」という土台となる
  ゲームメカニクス自体が存在しない。これらは単なるバックエンド関数の
  追加では済まず、新しいUI・新しい状態管理(店舗位置のロースター、
  施設配置のロースター)を要する、より大きな作業になる見込み。着手
  する場合はまずどちらを先にやるか(土地購入 or 施設誘致)、あるいは
  両方を支える「複数店舗管理」の土台を先に作るかをユーザーと相談する
  のが望ましい。
- **ライバル店の実際のスポーン・行動ロジック**: `_rival_stores`
  (Godot)・`remake_town_spatial`の各関数(reference_sim)ともに、
  位置・保有許可は呼び出し元(設定ファイルやテスト)が供給する前提の
  ままで、このプロジェクト自身がライバル店を生成・移動・行動させる
  ロジックは依然として存在しない。類推ベースでの実装余地はある
  (`remake_rival_policy.py`の判断ロジックは既に存在するため、
  「いつ・どこにライバル店が出現するか」というスポーン規則をバケット
  2/3で組み立てることは可能なはず)。
- **未解決のまま残る矛盾点**(複数セッションから持ち越し、再検証を
  試みたが解決できなかった): 天候テーブルの列名、営業時間③の終了
  時刻、駅の買物人口、成長/怒りペナルティマトリクスの列対応。これらは
  類推では埋められない純粋な「どちらの資料が正しいか」という事実確認
  の問題であり、より高解像度のページ再スキャンが必要。
