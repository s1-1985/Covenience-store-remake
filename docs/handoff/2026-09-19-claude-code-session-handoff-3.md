### 指令1: 再現忠実性(逸脱の禁止)

> ねえ、初代ザ・コンビニの再現ていうのを忘れるなよ？わけのわからない
> オリジナルゲームに向かうなよ

**意味**: 本プロジェクトは1997年発売の『ザ・コンビニ ～あの町を独占せよ～』
(PS/セガサターン)の忠実な再現であり、それにインスパイアされた別のオリジナル
ゲームを作るものではない。`CLAUDE.md`冒頭に明記済み。

### 指令2: 確認済みデータからの類推を、独自発明より優先せよ(CLAUDE.md新設の直接の契機)

> あのさあ、claude.mdに書かれてるのか分からないんだけど、このプロジェクトは
> 初代ザ・コンビニを再現するものであって、攻略本とかから解読しきれなかった
> 情報であっても、他のデータを元とする類推で進めるものであり、勝手な
> オリジナル要素はまだ加えてはならないからな。なんか先ほどから勝手要素を
> 加えている気がしてならないんだけ。大丈夫？そのへんよくわきまえながら続けて

**背景・経緯**: この指摘が出た時点で、プロジェクトルートに`CLAUDE.md`が
存在しなかった(このセッション中に確認済み)。直接の引き金は、タスク#39で
全25新規商品カテゴリの`initial_stock_units`を一律`10`にしていたこと
――各カテゴリの同じソース行に既にCONFIRMED_OFFICIALな`max_capacity`が
存在し、そこから類推できたにもかかわらず、である。この指摘を受けて:

1. `CLAUDE.md`を新設(タスク#42、決定書`0111-initial-stock-units-analogy-
   correction.md`)。
2. `initial_stock_units`を各カテゴリ自身の`max_capacity`から再導出する形へ
   修正。
3. 以後、確認できない値を埋める際の優先順位を明文化: **(1)確認済み証拠 →
   (2)他の確認済み関連データからの類推 → (3)このプロジェクト独自の発明
   (最終手段)**。(3)に飛ぶ前に、同じソース行・同じ対象の他のCONFIRMED
   フィールドに使える数値がないか必ず確認すること。

この優先順位ルールは、タスク#48(スキル成長の発火係数)・タスク#49
(チェックアウト怒りの発火閾値)でも一貫して適用された(詳細は4節)。

### 指令3: システム面を先に完成させよ(画像・音声は最後)

> システム面を先に全て作って、最後に画像生成、音声生成、そしてシステムと
> 画像・音声の紐付けを行う。システムの作り込みを進めて

**意味**: 画像生成・音声生成・それらとシステムの紐付けは、システム面

## 2. 確立された運用ルール・禁止事項

このセッションで実際に運用され、今後も踏襲すべきルール。「禁止事項」は
太字で明示する。

1. **禁止**: 確認済みデータからの類推(優先順位2)が可能な場面で、
   いきなり独自発明(優先順位3)に飛ぶこと。1節・指令2を参照。
2. **禁止**: 初代『ザ・コンビニ』の再現から逸脱し、無関係な独自ゲーム要素を
   追加すること。1節・指令1を参照。
3. **禁止**: このプロジェクト独自の発明(REMAKE_BALANCED_DEFAULT)を、
   以下3箇所すべてにタグ付けせずにコードへ混入させること:
   (a) 使用/定義箇所のコードコメント、(b) `game/data/vertical_slice.json`の
   該当`evidence_note`フィールド(またはreference_sim側の同等
   docstring)、(c) タグ文字列の存在自体を検証するテストアサーション
   (`reference_sim/tests/test_game_vertical_slice_contract.py`または
   `game/scripts/headless_smoke.gd`)。決定書やPR説明文だけに書いて満足
   しない(過去にタスク#38でこの抜けが発生し、是正された。PR #209)。
4. **必須**: `reference_sim`の`pytest`フルスイートと、実Godot 4.3バイナリ
   での`game/scripts/headless_smoke.gd`の両方がPASSしない限り、変更を
   「完了」とみなさない。
5. **必須**: 実装前にブランチを`origin/main`の最新へ再起動する
   (`git fetch origin main && git checkout -B <branch> origin/main`)。
   マージ済みPRの上に積み上げない。
6. **必須**: 確定事実(CONFIRMED_*)と、このプロジェクト独自の推論・発明
   (REMAKE_BALANCED_DEFAULT)を常に書き分け、`evidence_note`等の記述が
   実装の変化に対して古くなっていないか、新しいタスクに着手するたびに
   監査する(タスク#43・#46・#47で実際に複数の陳腐化記述を発見・是正した
   実績あり――「前回確認したときは正しかったが、その後の実装変更で嘘に
   なった記述」は繰り返し発生するパターンなので、次のセッションでも
   同様の監査を習慣化すること)。
7. **推奨**: 次のタスク候補が2つ以上ある場合は`AskUserQuestion`で提示し、
   ユーザーに選ばせる(このセッションを通じて一貫して踏襲したパターン。
   例外は、直前の調査で既にユーザーへ共有済みかつ異論のなかった明白な
   継続タスクのみ、確認なしで着手した――タスク#46→#47の遷移がこの例外に
   該当)。
8. PRは常にdraftで作成し、作成直後に`subscribe_pr_activity`で監視を
   開始する。CI失敗は都度診断し、本PRの差分と無関係と確認できた場合のみ
   「既知のflakyテスト」としてコメントし、可能なら再実行する(このセッション
   では`test_certain_purchase_buys_cheapest_priced_offer`という未シードの
   RNGに起因するflakyテストに複数回遭遇した。自己権限では
   `rerun-failed-jobs`が403で拒否されるため、後続の些細なpush――ドキュメント
   のみのフォローアップコミットなど――がCIを再実行させ、結果的に解消する
   ケースが多かった)。

## 4. 決定事項とその採択背景(横断的なまとめ)

3節の個々の経緯に加え、複数タスクをまたいで一貫していた判断パターンを
まとめる。

### 4.1 「確認済み証拠からの類推」を優先する具体例

- タスク#42: `initial_stock_units`をカテゴリの`max_capacity`から導出
  (是正)。
- タスク#45: 什器`capacity`とカテゴリ`max_capacity`が競合する場合、
  小さい方を採用(第三の数字を発明しない)。
- タスク#49: チェックアウト怒りの発火閾値を、タスク#33で確立済みの
  `CheckoutTiming`基準所要時間への倍率として表現(無関係な絶対時間を
  発明しない)。
- タスク#49: ペナルティの下限値(フロア)を、このコードベースが既に
  全スキルフィールドに課している非負制約(`>= 0`)の再利用とした
  (この機能専用の新しい数字を発明しない)。

### 4.2 「陳腐化したevidence_note」の発見と是正パターン

タスク#43(service/security/cleaning_skill)・タスク#46(35什器の
maintenance_yen_per_day)・タスク#47(staff_candidates_evidence_note)で、
いずれも「以前は正しかったが、その後の実装変更に追従せず嘘になった
evidence_note」を発見し是正した。**次のセッションでも、新しいフィールドを
配線する前に、関連するevidence_noteが現状を正しく記述しているか確認する
ことを推奨する**(これは事実の記録というより、Claude自身の推奨事項――
推論であることを明示する)。

### 4.3 スコープを意図的に絞った判断(対象外にした理由の型)

- タスク#44: reference_simの天候/ライバル希釈・不明要素の再正規化は、
  `demand_policy.gd`が既に下流で希釈を適用しているため意図的に移植せず
  (二重適用の回避)。
- タスク#46: `salary_yen_per_day_24h`の未消費を発見したが、当該タスクの
  依頼範囲外として先送り(→タスク#47で対応)。
- タスク#47: 実労働時間による按分は、勤務時間追跡の仕組み自体が
  このクライアントに存在しないため対象外。確定額をそのまま日額として
  使うほうが、按分の仕組みと「実労働時間の仮定」という二重の発明を
  避けられる、という判断。
- タスク#48: 店長教育ボーナス(マネージャー指定データなし)・清掃タスク
  成長(清掃タスク自体が未実装)を対象外。

  `reset()`がスキルを起点値へ復元するよう拡張(save/load時の「config
  起点へ戻す」という既存の契約を守るため)。ただしスキル成長自体を
  セーブ/ロード形式へ含める作業は別スコープとして対象外にした
  (save_state()のコメントに明記)。
- タスク#49: スタミナ/休憩室に絡む関連メカニクス
  (`checkout_pre_service_departure.py`)は、休憩室什器・スタミナ追跡が
  このクライアントに一切存在しないため対象外(タスク#41からの既存の

## 5. 残っているタスク・次の候補

`reference_sim`側で既に確定/定義済みだが`game/`側に一切配線されていない
候補を、このセッション終盤に横断的に調査した結果(2026-09-19時点、

- **月次レポート表示**(`reference_sim/conveni_sim/monthly_report.py`):
  演算式を持たない単なる記録・表示機構。ただしreference_sim自身の中でも
  一切呼び出されておらず、優先度は低いかもしれない(推論)。

### 5.2 前提となる別メカニクスが未実装のためブロックされている候補

- **スタッフのスタミナ/休憩室帰還**
  (`checkout_pre_service_departure.py`、`staff_rest_recovery.py`等):
  休憩室什器(`break_room_1`/`break_room_2`)自体がタスク#41で対象外に

  (a) 交番・消防署などの警備施設が什器カタログに一切存在しない、
  (b) 顧客の「マナー値」に相当するデータをこのクライアントの顧客モデルが
  一切持たない、という2つの前提が欠けている。
- **施設誘致**(`inducement.py`、交番/消防署/大学等を町へ誘致):
  店外・町マップへの空間配置システム自体がこのクライアントに存在しない。

### 5.3 数式自体が存在せず、発明の余地が大きい候補

- **季節需要**(`seasonal_demand`、"summer"/"winter"タグ):
  reference_sim自体にも数式が一切存在しない(REMAKE_BALANCED_DEFAULTの
  叩き台すらない)。ゲーム内の「季節」概念自体も未定義。

### 5.4 新規メカニクス・UIとして規模が大きい候補(データは移植済み)

- **スタッフ雇用・解雇UI**: 35名のCONFIRMED_OFFICIAL候補プールは

  UI/フローが一切存在しない(staff-1/staff-2の2名固定)。
- **店舗サイズ選択UI**: 小/中/大の建設費データ(18,000,000円等)は
  確認済みだが、複数サイズを選べる新規出店UI自体が存在しない。
- **ライバル店AI**(`remake_rival_policy.py`): 現状`town.
  store_count_including_rivals`という需要希釈用の単一の数値のみで、
  実際に意思決定する(出店/撤退/価格変更等の)ライバル店エンティティは
  存在しない。

### 5.5 明確に対象外・恒久的な割り切り(再検討不要)

### 6.2 バックエンドに存在するがUIから触れない、または部分的な実装

  ―程度はあるが、プレイヤーが能動的に操作したり、町側が能動的に
  意思決定したりする仕組みはない。

### 6.4 Claudeによる総合評価(推論)

「画像・音声を除いたシステム面」を、(a)1店舗・1日のコアループ、
(b)経済/スタッフ/評価システム、(c)町・ライバル・シナリオといった
メタゲーム層、の3層で見ると:

- (a) 1店舗の日次コアループは**かなり作り込まれている**と評価する
  (来店から会計まで、経済的帰結を伴う形で一通り動く)。
- (b) 経済/スタッフ/評価システムも、**主要な確認済みメカニクスの大部分が
  配線済み**(このセッションだけで11タスク分を配線した)。ただし
  スタッフの雇用・解雇という「入口」のUIが欠けているため、スタッフ
  システムは「動くが固定メンバーでしか遊べない」状態。
- (c) 町・ライバル・シナリオといったメタ層は、**個々の確定済み数式・
  数値(地価変動式、施設誘致の取引ロジック等)はPython側
  (`reference_sim`)に相当数実装されているが、Godotクライアント側への
  移植はごく一部(地価の表示のみ)**。ここが現状もっとも手薄な層である。

この評価はClaude自身の主観であり、次セッション開始時にユーザー自身が
実際にプレイして確認することを推奨する。
