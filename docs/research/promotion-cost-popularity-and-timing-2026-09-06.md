# 宣伝：費用・人気上昇量・発生日時

調査日: 2026-09-06
対象: 1997年 PS/SS版『ザ・コンビニ ～あの町を独占せよ～』のみ

## 結論

初代PS/SS専用攻略Wikiの「宣伝」ページから、5種類の宣伝について費用、全店舗への人気上昇量、実際の発生日時を回収できた。

この資料はトップページで「プレイステーション・セガサターン用」「PC版では無い」と明示されているため、後続作の宣伝値は混入させない。

## 証拠レベル

- B+ / FIRST-TITLE-DEDICATED-COMMUNITY-DATA
- 数値・日時が明示され、初代専用Wiki内で体系的に整理されている。
- ただし説明書や原作画面そのものによる一次確認ではないため A にはしない。

## 宣伝データ

| 種類 | 費用 | 人気上昇 | 発生日時 |
|---|---:|---:|---|
| ダイレクトメール | 100,000円 | +12 | 2日目 10:00 |
| 新聞広告 | 500,000円 | +20 | 2日目 07:00 |
| 飛行船 | 1,000,000円 | +30 | 3日目 15:00 |
| ラジオ | 3,000,000円 | +50 | 1日目 17:00 |
| TV | 5,000,000円 | +100 | 1日目 19:00 |

出典: https://wikiwiki.jp/theconveni1/%E5%AE%A3%E4%BC%9D

## 宣伝の作用範囲

同資料では、宣伝を実行すると「出店している店全て」の人気が上がり、店舗数が増えても宣伝費は変わらないとされる。

したがって、宣伝は店舗ごとに購入する処理ではなく、少なくともプレイヤーチェーン全体へ作用する施策として扱うのが自然である。

実装境界の候補:

```text
PromotionCampaign {
  type
  cost_yen
  popularity_delta
  trigger_day
  trigger_time
  applies_to = all_player_stores
}
```

## 人気上限

同ページでは人気パラメータの上限は100とされ、宣伝で上げても100を超えない。

よって宣伝適用時は概念上、

```text
store.popularity = min(100, store.popularity + promotion.popularity_delta)
```

とする実装が資料と整合する。

ただし内部値が100で完全clampされるのか、表示のみ100で内部余剰値を持つかは直接確認できていないため、内部表現の最終固定は一次観測待ちとする。

## 月内実行回数

宣伝方法ごとに月1回実行でき、それぞれ決まった日付・時刻にイベントが発生するとされる。

重要なのは「宣伝を選択した瞬間に人気が上がる」のではなく、予約された宣伝イベントが指定日時に発火する構造である点である。

したがって、UI操作と効果発生は分離する必要がある。

```text
request_promotion(type)
  -> reserve event for type-specific day/time
  -> on event fire: apply popularity bonus to all current player stores
```

## アイドル1日オーナーイベント

同資料では、全店舗の累計来店者数が1万人増えるごとに、無料でアイドルの1日オーナーイベントが発生するとされる。

確認できた仕様:

- 判定対象: プレイヤー全店舗の来店者数合計
- 閾値: 累計1万人ごと
- 費用: 無料
- 効果: TV宣伝と同じ人気+100
- 発生タイミング: 「来店者数が○万人になりました」の通知が出た次の日の0:00
- 効果範囲: 全店舗

証拠レベル: B+ / FIRST-TITLE-DEDICATED-COMMUNITY-DATA

これにより、来店者数について少なくともチェーン累計カウンタを持つ根拠が強まる。

```text
chain_total_visitors
next_idol_threshold = 10000, 20000, 30000, ...
```

通知到達後、翌日0:00へイベントを予約する方式が候補となる。

## 新規出店との相互作用

専用Wikiでは、アイドルイベント発生前に新規出店しておくと新店舗も人気上昇を受けられるとされる。

これは宣伝/アイドルの対象店舗集合が「予約時点の店舗一覧」ではなく、少なくとも効果発生時点の出店店舗一覧から取得される可能性を示す。

この挙動は実装上重要なので、イベント予約時に対象store_id一覧を固定する設計は避ける。

候補:

```text
onPromotionEventFire:
  stores = current_active_player_stores()
  for store in stores:
      apply popularity bonus
```

ただし、臨時休業中の店舗、建設中店舗、売却処理と同tickの店舗が対象かは未確定。

## 既存研究との接続

既存研究では人気が顧客独占率の入力であり、低い総合評価では日次で最大15低下することが確認されている。

今回の宣伝データにより、人気システムは少なくとも以下を分離して実装できる段階になった。

- popularity state: 0..100 表示範囲
- natural/evaluation-driven decay
- paid promotion event
- milestone idol event
- customer-share calculation input

## 未確定

- 同じ種類を同月に再選択した時のUI挙動
- 翌月予約の可否
- 人気100到達時の内部clamp方式
- 臨時休業店への宣伝効果
- アイドル閾値到達が同月複数回起きた場合のキュー処理
- 1万人ちょうどではなく閾値越えでも確実に発火するか

## 実装開始可否

宣伝システムについては、データ定義、月1回制約、予約イベント、全店適用、アイドル累計来店者マイルストーンの構造実装は開始可能。

一方、申込締切、支払タイミング、同tick競合などは一次観測がないため固定しない。
