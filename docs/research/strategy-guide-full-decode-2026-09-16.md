## 0. 取り扱い方針

このファイルは、今回提供された攻略本スキャン4ファイルから、**画面・表で数値が明示されているものを優先して機械実装向けに転記**したものである。

-   初代『ザ・コンビニ
    ～あの町を独占せよ～』PS/SS版の資料のみを対象とする。
-   続編由来の情報を混ぜない。
-   攻略本に明記された値と、攻略本文の助言・推奨値を区別する。
-   数値表は「実装候補の確定データ」、攻略上のコツは「ロジック証拠」として分離する。
-   スキャン上で判読が怪しい箇所は `UNCERTAIN` とし、勝手に補完しない。
-   既存コードの値と衝突する場合、既存値を自動上書きせず
    `research/decision` で差分を確認すること。

主な出典: - 本1.pdf:

# 5. 社員・店長能力システム

攻略本で確認できる主要能力: - 体力 - レジ - 清掃 - 補充 - サービス -
接客（表によって名称要再確認） - その他、店長/社員候補データ表の能力群

能力値は概ね0〜100スケール。

攻略本文から確認できる境界: 1.
仕事をさせると、その仕事に対応するパラメータが成長する。 2.
仕事を失敗すると能力がダウンする場合がある。 3.
店長の教育次第で社員能力を伸ばせる。 4.
店長能力が低いと教育効果が十分出ない。 5.
仕事中のパラメータ変化は、レジ・清掃・補充等の仕事種別に対応している。
6. 休憩室は社員のスタミナ/サービス運用に関係する。

# 6. 営業時間

攻略本から確認できる事項:

-   営業時間は24時間営業を含めて設定可能。
-   例として `7:00〜11:00営業` が存在。
-   臨時休業が存在。
-   営業時間外は客の入店を止める。
-   既存の動画/researchで確認済みの「閉店中も店員作業は継続し得る」「運営費の一部は停止」と攻略本を統合すること。
-   営業時間設定は顧客層・売上・維持費とのトレードオフ。

攻略本の時間帯説明: -
朝の5:00〜9:00など、時間帯によって来店する顧客層が異なる。 -
24時間営業は客数機会を増やすが維持費等の負担も増える。 -
正確な時間帯別来店係数は、顧客データ表（本2
pp134-143）をデータ化して使用する。

# 7. 顧客システム

攻略本で顧客ごとに以下のパラメータが定義されている。

-   名前/顧客タイプ
-   来店時間帯
-   所持金
-   欲しい商品カテゴリごとの嗜好値（0〜100系）
-   店舗評価要素に対する反応
-   天候/曜日/時間帯との関係（本文・表から確認）

顧客行動: 1. 店へ入る。 2. 欲しいものを買う。 3. 店内を回遊する。 4.
アンケートに回答することがある。 5.
不満が大きい場合は買わずに帰ることがある。 6.
顧客個人データを観察できる。 7.
顧客タイプごとに欲しい商品・来店時間・所持金が大きく違う。

重要: - 本2
pp134-143に**顧客別の時間帯・所持金・商品嗜好の巨大マトリクス**が掲載されている。 -
このマトリクスは実装価値が非常に高いが、スキャン表が高密度なため、誤転記を避ける目的で今回の自動実装用ファイルでは「原画像を再照合してからCSV化するデータ」とする。 -
Claude側で一括OCR推測はしないこと。画像を拡大して行単位で二重確認すること。

# 10. ライバル

攻略本本文から確認できる戦術・挙動:

-   ライバル店には本店/支店がある。
-   ライバル店の客を奪うには、商圏の重なり、価格、品揃え、人気、サービス等が関係する。
-   ライバル店の地価を上げ、移転/撤退を促す戦術が記載されている。
-   支店を買収可能。
-   ライバルの経営状態を確認できる。
-   ライバル店は価格を下げる等の対抗を行う。
-   ライバル店を撤退させても再出店し得る既存動画証拠と矛盾しない。

実装方針: - 攻略本が示す戦術を、そのままAI優先度式へ変換しない。 -
`RivalPolicyInputs`
として、価格、人気、サービス、商圏重複、資金、地価等を入力可能にする。 -
閾値/重みは表または追加証拠が出るまで外部データ。

# 12. 価格設定

攻略本の価格設定章から確認: -
全商品一括価格設定と個別商品価格設定がある。 -
ライバル価格を参照できる。 -

# 19. 攻略本文から復元できるゲームロジック（全ページ再読版）

> この章は「表の数値」ではなく、攻略本文・POINT・Q&A・レイアウト例・マップ攻略・キャプションから、
> **ゲーム内部で成立していなければ説明できない因果関係**を実装仕様へ変換したものである。
> 攻略上の推奨値そのものと、ゲーム仕様として確定できる事実は分離する。

## 19.1 出店候補地・商圏・立地

### 攻略本から確定できること

-   出店位置には「商圏」が存在し、店舗を中心とした一定範囲の人口・施設・ライバルが経営結果に影響する。
-   商圏は単なる表示ではなく、来店候補となる人口を拾うための空間的な範囲として扱われる。
-   立地選択時には周辺人口、地価、ライバル店、誘致施設、将来性を同時に見る必要がある。
-   駅・学校・住宅・オフィス等は同じ人口を発生させる施設ではなく、顧客属性と来店時間帯を変える。
-   同一店舗でも立地によって適切な品揃え、営業時間、レイアウトが変わる。
-   ライバル店との商圏重複は競争状態を作る。

### 実装へ落とす境界

``` text
MapCell
  ├─ land_value
  ├─ population_sources[]
  ├─ facilities[]
  ├─ stores[]
  └─ security/fire_safety modifiers

StoreTradeArea
  = spatial area derived from store/location
  -> gathers candidate population sources
  -> applies rival overlap
  -> produces potential customer pool
```

### 推測禁止

-   商圏半径の内部計算式
-   距離減衰係数
-   商圏重複時の顧客分配率
-   地価から来店率への直接係数

これらは攻略本文だけでは数式まで確定しない。

## 19.2 顧客生成は「人口×属性×時間帯×商圏」で考える

攻略本の顧客データと町施設データを合わせると、顧客生成は単一のランダムスポーンでは不十分である。

### 確定できる構造

1.  町の建物・施設には人口/顧客供給源としての性格がある。
2.  顧客タイプごとに来店する時間帯が異なる。
3.  顧客タイプごとに所持金が異なる。
4.  顧客タイプごとに商品カテゴリへの嗜好が異なる。
5.  店舗の商圏に入っている人口が来店候補になる。
6.  営業時間外は当然来店できない。
7.  同一商圏にライバルが存在すると店舗選択競争が発生する。
8.  人気・価格・品揃え・サービス・店舗評価などが店舗選択に関係する。

### 推奨アーキテクチャ

``` text
PopulationSource
  -> CustomerArchetypeSupply(time)
  -> CandidateCustomer
  -> StoreChoice
  -> Visit
  -> InStoreBehavior
  -> Purchase / GiveUp
  -> Satisfaction / Survey
```

「マップ上に適当に客を生成して最寄り店舗へ送る」方式にはしない。

# 20. 顧客AI

## 20.1 顧客には目的商品がある

本文には、来店客が欲しい商品を探す行動が明記されている。
したがって顧客は入店時点で最低でも以下を持つ必要がある。

``` yaml
customer_visit_intent:
  primary_wanted_category: <category>
  budget: <yen>
  optional_secondary_purchase: true
```

商品が存在しない、棚に到達できない、価格等の条件に満足できない場合は「買わずに帰る」状態が必要。

## 20.2 ついで買い

攻略本文には目的商品以外を購入する「ついで買い」が存在する。
これは最初から複数の商品を買う顧客とは分離すべきである。

``` text
enter
 -> seek primary item
 -> acquire primary item
 -> optional impulse/secondary selection
 -> register
 -> exit
```

ついで買いの確率式は攻略本からは確定しないため係数は `UNKNOWN`。

## 20.3 店内回遊

-   顧客は入口から商品棚、レジ、出口へ移動する。
-   欲しい商品を探すために店内を移動する。
-   通路が狭い、動線が悪い、設備配置が悪い場合は店舗運営上不利になる。
-   レジ前・入口付近は特に混雑しやすい。
-   円形に回れるレイアウト、袋小路を減らす配置が攻略上推奨されている。
-   客と社員が同じ通路を利用するため、社員作業動線も混雑へ関係する。

よって経路探索は見た目だけではなくシミュレーションに接続する。

## 20.4 アンケート

顧客へアンケートを実施すると、その客の個人データと店舗への不満を取得できる。
したがってアンケートは単なるフレーバーテキストではなく、
内部の顧客評価状態を可視化するデバッグ窓に近い。

候補となる不満要因: - 欲しい商品/品揃え - 価格 - 店舗サービス - 清潔さ -
混雑/レイアウト - 営業時間等

ただし、不満文言から各係数を逆算して固定値にすることは禁止。

# 21. 商品・棚・品揃え

## 21.1 商品カテゴリと棚の互換性

DATA2には、各設備に対して各商品カテゴリを置けるかどうかの互換表がある。
したがって `Fixture.supported_categories`
はコード分岐ではなくマスターデータ化する。

``` yaml
fixture:
  id: ...
  supported_categories:
    cold_drink: allowed
    hot_drink: prohibited
    ...
```

表中の記号は原本の凡例を確認してそのまま enum
化し、意味を推測で置換しない。

## 21.2 棚の能力

設備には少なくとも以下が独立パラメータとして存在する。

-   購入価格
-   維持費
-   収納力
-   注目度
-   大きさ
-   設置可能場所
-   商品互換性

したがって「大きな棚=収納量だけ増える」というモデルは不十分。
注目度と維持費のトレードオフを持つ。

## 21.3 売れ筋

攻略本文では、商品別の売上/売れ筋を確認しながら品揃えを変更することが推奨される。
つまり商品カテゴリごとの販売履歴を保存し、UIから参照できる必要がある。

``` text
SalesHistory[store][category][time_bucket]
```

最低でも店舗単位・商品カテゴリ単位で追跡可能にする。

## 21.4 欠品

欲しい商品が棚にない場合、顧客満足/購買機会へ悪影響がある。
補充作業と在庫量を顧客AIから独立させず接続する。

# 22. 価格決定

## 22.1 全体価格と個別価格

攻略本には、 - 全商品一括の価格設定 - 商品ごとの個別価格設定
の双方が存在する。

したがって販売価格は、

``` text
effective_price(category)
 = individual_override if present
   else global_price_policy(category/base)
```

のように解決可能にする。

## 22.2 価格が複数システムへ影響する

本文では高値/安値が単純な利益額だけでなく、
客の反応、売れ行き、人気、評価、人口/商圏競争などへ関係することが示される。

ただし攻略本は価格弾力性の数式を公開していない。

よって、

``` text
PriceResponsePolicy.evaluate(
  customer_type,
  category,
  store_price,
  reference_price,
  rival_price
) -> UNKNOWN-compatible result
```

の境界だけ作り、係数を捏造しない。

## 22.3 ライバル価格

ライバル対策として価格を確認・対抗する記述がある。
店舗選択/商品購入には絶対価格だけでなく競合価格との比較を渡せる設計にする。

# 23. 営業時間

## 23.1 営業時間は客数だけでなく客層を変える

攻略本では時間帯によって来店する顧客層が異なる。
したがって営業時間延長は、

``` text
open longer => same demand × longer duration
```

ではない。

時間帯別に顧客供給を計算する。

## 23.2 24時間営業

24時間営業は可能だが、社員の勤務・体力とのバランスが必要。
閉店中にも社員作業を行わせる運用が攻略本文に存在するため、

``` text
store_open_to_customers
staff_work_enabled
```

を同一フラグにしない。

## 23.3 臨時休業

臨時休業の仕組みが存在する。
顧客受付停止と社員処理、時間進行を別イベントとして扱う。

# 24. 社員AI・成長

## 24.1 能力値

攻略本では社員の能力が複数軸に分かれている。
少なくとも、体力、レジ、清掃、補充、サービス等が別々に扱われる。

社員を単一の `skill` 値で表現しない。

## 24.2 作業による成長

実際に担当した仕事に対応する能力が伸びる。

``` text
WorkCompleted(employee, work_type)
 -> growth opportunity(work_type)
```

とする。

失敗時には能力が下がる場合があるという記述もあるため、
成功/失敗イベントを成長処理へ渡す。

## 24.3 店長による教育

店長の能力/教育が社員成長へ影響する。
店長を単なるプレイヤーアバターにしない。

``` text
employee_growth
 = base_work_growth
 + manager_training_effect
```

ただし係数は UNKNOWN。

## 24.4 スーパースタッフ

攻略本クイックリファレンスには能力80を超える社員を特別視する説明がある。
実装時は「80以上/80超」の境界を原画像で最終確認してから固定する。

## 24.5 体力・勤務

長時間勤務、24時間営業、新店への応援配置等が社員運用と結びつく。
体力は表示だけではなく作業効率/勤務継続に影響する状態値として扱う。

## 24.6 新店へのベテラン投入

新規支店へ経験済み社員を投入することが攻略上有効とされる。
これは能力値が店舗に依存せず社員個体へ保存され、異動後も維持されることの強い証拠である。

# 33. レイアウトシミュレーション

## 33.4 商品の位置

# 34. レイアウト実例集から得られる設計証拠

本2-1/本2-2の多数のレイアウト例は、単なるデザイン集ではなく、
以下のシステムがゲーム結果へ影響することの反復証拠である。

-   顧客層に合わせた商品カテゴリ構成
-   入口位置
-   レジ位置
-   通路幅
-   回遊動線
-   駐車場数
-   ベンチ/噴水等サービス設備
-   若者向け、高齢者向け、女性向け、学生向け、ビジネスマン向け等のターゲティング
-   観光/スポーツ/未来都市等、周辺施設に合わせた店舗設計
-   大型店では混雑分散が必要
-   小型店では移動距離短縮と商品絞り込みが有効

# 37. 「攻略上のコツ」と「内部仕様」の区別

Claude実装時に最も重要。

例: - 「通路を広くするとよい」→ 混雑/移動が存在する証拠。 -
「価格を下げると客が来る」→ 価格応答が存在する証拠。 -
「ライバルの近くへ出店する」→ 商圏競合が存在する証拠。 -
「ベテラン社員を新店へ」→ 社員能力が異動後も保持される証拠。 -
「広告を打つ」→ 指定時刻に人気が増える数値表あり。 -
「このレイアウトが最強」→
そのレイアウト自体をAIルールとして固定してはいけない。

攻略文章をそのまま if 文へしない。
背後にある観測可能なゲーム状態へ分解する。

# 38. Claude向け実装データ分類

``` yaml
evidence_classes:
  EXPLICIT_NUMERIC:
    description: 攻略本の表・UIで数値が直接明記
    action: 原則マスターデータ化

  EXPLICIT_BEHAVIOR:
    description: 本文でゲーム挙動が明記
    action: 状態/イベント/インターフェースとして実装可能

  STRATEGY_EVIDENCE:
    description: 攻略法から内部因果が存在すると分かる
    action: 因果の境界だけ実装。係数は作らない

  EXAMPLE_ONLY:
    description: レイアウト例・プレイ例
    action: テストケース候補。一般則として固定しない

  UNKNOWN:
    description: 数式・確率・係数・丸め等が資料から不明
    action: UNKNOWN保持
```

# 43. provenance仕様

本文由来:

``` yaml
source:
  document: 本1.pdf
  pdf_page: 14
  printed_page: 32-33
```

``` yaml
source:
```

# 44. Claudeへ渡す最終指示

以下をそのままClaudeへ渡してよい。

> 初代PS/SS版『ザ・コンビニ ～あの町を独占せよ～』の忠実再現を行う。
> この資料では攻略本の数値表だけでなく、本文・POINT・Q&A・レイアウト例・マップ攻略から復元した
> ゲーム内部の因果関係を仕様証拠として整理している。
>
> 最新main、既存tests、docs/decisions、docs/researchを先に確認し、既存実装と重複させないこと。
> `EXPLICIT_NUMERIC` はデータ駆動のマスターへ格納する。
> `EXPLICIT_BEHAVIOR` は既存runtimeへ状態/イベント境界として接続する。
> `STRATEGY_EVIDENCE`
> は内部因果が存在する証拠として扱うが、攻略文に書かれていない係数・確率・式を発明しない。
> `UNKNOWN` はUNKNOWNのまま保存する。
>
> 特に、顧客生成を単純ランダムスポーンにしない。 町施設/人口源 →
> 顧客属性 → 時間帯 → 商圏 → 店舗選択 → 店内行動 → 購買/離脱
> のパイプラインを維持すること。
>
> 人気と店舗評価を同一変数にしない。
> 店舗営業中フラグと社員作業可能フラグを同一にしない。
> 社員能力を単一skillにしない。
> レイアウトを見た目だけにせず、経路・混雑・商品探索へ接続可能にする。
> ライバルを固定障害物にせず独立店舗状態として保持する。
>
> 数値表をコードへ直書きせず、stable ID + data file + provenance
> で管理する。
> 攻略本値と既存動画証拠が衝突した場合はどちらかを黙って上書きせずresearch
> noteへ記録する。 PS/SS差が疑われる場合はvariantを分ける。
>
> 実装順は、 1. 数値マスター 2. データロード/validation 3.
> 既存runtimeへの接続 4. 本文から確定した挙動境界 5.
> UNKNOWN係数を必要とするロジック とする。
>
> 既存の月進行、代表日1〜4日、compressed month
> tail等の既存証拠を壊さず統合すること。

# 46. 重要な設計結論

この攻略本から見える初代『ザ・コンビニ』は、
「客がランダムに来て棚から商品を買うだけ」のゲームではない。

少なくとも設計上は、

``` text
町
 ↓
人口源・施設・時間帯
 ↓
顧客属性
 ↓
商圏・ライバル競争
 ↓
店舗選択
 ↓
入口・動線・混雑
 ↓
目的商品探索
 ↓
価格・在庫・品揃え
 ↓
ついで買い
 ↓
レジ
 ↓
サービス/満足
 ↓
売上・人気・店舗評価
 ↓
地価・町の発展・支店・ライバル
```

という相互接続された経営シミュレーションとして復元する必要がある。

攻略本で式が公開されていない部分まで「それらしい値」で埋めることは、
忠実再現ではなく別ゲーム化につながる。
したがって、**存在が確定した因果は実装し、係数が不明な因果はデータ境界まで作ってUNKNOWNを維持する**
ことを本プロジェクトの基本方針とする。
