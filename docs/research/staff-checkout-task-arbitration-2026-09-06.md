# 店員AI：レジ応援・タスク競合・会計順序の追加調査 2026-09-06

対象: 1997年PS/SS版『ザ・コンビニ ～あの町を独占せよ～』のみ。

目的:
- 店員AIのうち、レジ待ち発生時にどのタスクを優先するか、複数店員が同時にレジへ向かった場合どうなるか、待ち客の会計順序がFIFOであるかを整理する。
- 後続作のAI仕様を混ぜず、初代PS/SS専用攻略資料の観測のみを記録する。

## 証拠レベル

- **B+ / FIRST-TITLE-DEDICATED-COMMUNITY-OBSERVATION**: 初代PS/SS専用攻略WikiのFAQで、具体的な再現挙動として記録されている。
- **UNKNOWN**: 内部優先度値、確率、待ち時間、発生条件の厳密式など、画面またはコードから未確認のもの。

主要出典:
- 初代PS/SS専用攻略Wiki FAQ: https://wikiwiki.jp/theconveni1/FAQ

---

## 1. レジ待ち客がいても、補充などの既存タスクをぎりぎりまで継続する場合がある

初代専用FAQでは、レジに客が並んでいる状態でも、店員に補充など別タスクが残っていると、店員がすぐにはレジへ向かわず、かなり遅い段階まで既存タスクを続ける場合があると報告されている。

証拠レベル: **B+**

### 実装上の意味

店員AIを次のような単純な常時割込みにしない方が安全である。

```text
if checkout_queue_nonempty:
    cancel_current_task()
    go_to_checkout()
```

原作互換の境界としては、少なくとも以下を分離できる構造が必要。

```text
current_task
current_task_commitment
checkout_demand
checkout_interrupt_threshold
```

ただし `checkout_interrupt_threshold` の正確な値・時間・キュー人数条件は未確定である。

---

## 2. 複数店員が同時にレジへ向かうと、片方がレジ担当にならず休憩室へ戻る場合がある

FAQでは、2人の店員が同時にレジへ向かうと、一方がレジ打ちを開始し、もう一方がなぜか休憩室へ戻ってしばらく出てこないことがあると記録されている。

証拠レベル: **B+**

### 重要な境界

これは単純な「空いているレジへ各店員を割り当てる」方式では再現できない可能性がある。

安全なモデル候補:

```text
1. 複数店員が同じ checkout-demand を検知
2. 同時に checkout task を予約/移動開始
3. 先着または内部選択された1人だけが checkout owner になる
4. 競合に負けた店員は通常タスクへ即復帰せず、breakroom/idle 系状態へ遷移する場合がある
```

ただし、以下は **UNKNOWN**:
- 必ず休憩室へ戻るのか
- 同一レジへの競合時だけか、複数レジでも起こるか
- 休憩室滞在時間
- 体力値が遷移条件に関係するか
- PS/SS双方で完全同一か

---

## 3. レジ担当店員の体力が少ないと、会計開始直後または直後に休憩へ入り、レジが無人になる場合がある

同FAQでは、レジ打ちを始めた店員の体力が残り少ない場合、その店員もすぐ休憩室へ戻り、しばらくレジが無人になるケースが報告されている。

証拠レベル: **B+**

既存研究で確認済みの「作業で体力が減り、0になると休憩室で回復する」という一般則と整合するが、今回の観測は特に **レジ担当確定後にも休憩遷移が優先され得る** ことを示す。

### 実装上の意味

checkout task の獲得時点で、その店員を会計終了までロックしない。

```text
ASSIGNED_TO_CHECKOUT
  -> START_CHECKOUT
  -> stamina check / task progression
  -> RETURN_TO_BREAKROOM  # 会計需要が残っていても遷移し得る
```

会計中断が客単位の途中で起きるのか、1人分終了後なのかは未確定。

---

## 4. 会計順序は厳密FIFOではない

FAQでは、店員がレジ打ちを始めた際、後から並んだ客を先に会計してしまう場合があり、それによって先に並んでいた客が怒ることがあると記録されている。

証拠レベル: **B+**

### 確定できる境界

原作互換実装では、待ち客を単純な1本のFIFOキューとして処理すると不一致になる可能性がある。

最低限、選択ポリシーを差し替え可能にする。

```text
CheckoutSelectionPolicy
- fifo
- observed_original_compatible
- explicit_observation_replay
```

既存の観測再生系では明示的な選択順を注入できる設計が進んでいるため、今回の研究結果はその方向性と整合する。

ただし原作の通常ランタイムで「誰を優先するか」の式は **UNKNOWN**。候補として距離、レジへの接触位置、到達セル、内部客ID、レジ向きなどが考えられるが、いずれも現時点では仮説であり固定しない。

---

## 5. 顧客の怒りはレジ処理速度だけでなく、タスク裁定・会計順序からも発生し得る

既存研究では低レジ能力による極端に遅い会計が顧客怒りの主要因として確認済みだが、今回のFAQ観測から、怒りの原因を少なくとも以下へ分解する必要がある。

```text
checkout_anger_causes:
- excessive_wait_due_to_slow_service
- checkout_unattended_after_staff_departure
- delayed_staff_response_due_to_other_tasks
- queue_order_overtake / non-FIFO selection
```

証拠レベル:
- 各原因が怒りへ結び付くこと: **B+**
- 個別閾値・待ち時間・怒り判定式: **UNKNOWN**

---

## 6. baseline実装への判断

### 実装開始可能

以下は構造として実装開始してよい。

- 店員タスクに「現在タスク継続度/割込み可否」を持たせる
- レジ需要を検知しても即時割込み固定にしない
- 複数店員が同じレジ需要へ反応できる
- checkout ownership 競合を表現できる
- 競合敗北後の遷移先をポリシー化する
- 会計客選択をFIFO固定にしない
- 顧客怒りの原因を複数種に分ける

### まだ固定してはいけない

- レジ優先度の数値
- 何人待ちで割込みが発生するか
- 競合敗北時に必ず休憩室へ戻るか
- 休憩室へ戻る時間
- 会計順序選択式
- 客が怒る待ち時間閾値
- PS版とSS版の細部差

---

## 7. 次の検証優先度

1. 原作動画で「客がレジへ並ぶ→店員が補充継続→レジへ移動」の時刻をフレーム単位で採取する。
2. 2人の店員が同じレジへ向かうケースを直接観測し、敗北側の移動先・滞在時間・体力を記録する。
3. 後着客先会計のケースで、各客の待機セル・到着順・レジとの距離・選択順を記録する。
4. PS/SS双方で同一挙動が出るか確認する。

これらが取れれば、店員AIの `task arbitration` と顧客側の `checkout selection / anger timing` を、観測再生だけでなく通常runtime規則へ段階的に昇格できる。
