### 保存ファイル

- カード内名：BISLPS-00782CONV（16文字＋NUL）。
- 既知のパス：bu00:BISLPS-00782CONV。
- 比較関数7B7C0はNULを含む17バイトを比較したと記録されている。
- ファイル全長114688バイト＝14×8192。先頭4バイトは53 43 13 0E。
- 先頭512バイトはタイトル・パレット・3アイコンフレーム。
- タイトル文字列は先頭+4のShift-JIS「コンビニ」8バイト＋NUL。
- +13..95は残存スタック内容を含むとの過去観測。ゼロ埋め済みと仮定しない。
- パレット+96..127、アイコン+128..255、+256..383、+384..511。
- ペイロード104364バイトはファイル+512から。
- 先頭104360バイトの各バイトの加算値を、ペイロード+104360に32bit little-endianで格納。
- 残り9812バイトは残存RAM由来。元の入出力範囲を保つには捨てない。
- mode 0：ファイル[512,90112)、128バイト×700。
- mode 1：ファイル[90112,114688)、128バイト×192。
- mode 0/1は同じファイルの前後半であり、カードスロット番号ではない。
- 新規作成openフラグ0xE0200。14ブロック指定、create bit9有効、async bit15は無効。
- 機能アドレス：7B1F8初期化/状態、7B45C読込準備、7B5C4書込準備、7B8A4作成、
  7BC14ヘッダ、7B920ディレクトリ、7AB2C読込、7ADF8書込。
- BIOS境界：7E4EC open、7E4FC seek、7E50C read、7E51C write、7E52C close。
- 制御試験で使ったVSync境界89CA4、ヘッダ生成時スタック801D0000。
- 実機の高位スタック/メモリーミラー、GPU/SPU/IRQをこの記録から検証済みにしない。

### 空き容量とイベント

- 元のディレクトリ取得構造は40バイト、名前+0、サイズsigned i32 +24と記録されている。
  これはカード上の128バイトdirectory frameとは別の構造である。
- 対象ファイルが存在すると状態0。存在しない保存時は他ファイル使用<=1ブロックで2、
  >=2ブロックで1。対象なし読込時は使用量によらず2、との過去制御試験。
- ディレクトリ失敗-1/-2/-3は状態3/4/5に対応したと記録されている。
- 7A92Cは2クラス×4specの8イベントを登録・有効化する。
- クラスF4000001 / F0000011、spec順4 / 8000 / 100 / 2000、mode2000、callback0。
- RAMハンドル位置：CD908/90C/910/914、CD918/91C/920/928。
- 7C110/7C1F4は4イベントを順に調べ、戻り値1だけを成功扱いし0..3を返す。
- 7C2D8/7C340は4イベントを各1回調べる。ループで全将来通知を消す処理ではない。
- 以前の論理BIOS試験の55イベント例等は今回の検証件数に加算しない。
- 正の短いI/O結果64バイトを返した過去試験は人工的な故障注入であり、
  実BIOSが128バイト要求に64を返すことを確認した証拠ではない。
- 保存UIの応答待ちは乱数を進める。乱数まで不変と記述しない。
- 保存UI→タイトル→読込の全経路を同一CPUで通した証明と、
  分離CPUでのタイトル読込試験を混同しない。

## 今回の追加調査と検証

### 3つの形式

| 形式 | バイト数 | 内容 |
|---|---:|---|
| rawカード全体（例.mcr） | 131072 | 8192バイトのシステム領域＋15データブロック |
| ゲームの論理ファイル | 114688 | 14ブロック、先頭SC |
| 単独セーブMCS | 114816 | 最初のdirectory frame 128バイト＋論理順の14ブロック |

カードのdirectory frameは128バイト。state u32 +0、size u32 +4、
next u16 +8、filename +10、XOR checksum +127。
nextは次の物理データブロック番号から1を引いた値で、終端FFFF。
先頭51、中間52、末尾53。1ブロックファイルは先頭51のみ。
断片化ファイルは隣接領域を読むのでなく、このリンクを追う。
MCSの移入時は保存元のリンクをそのまま再利用せず、移入先で再構築する。

DuckStationのraw単独セーブ移入は外側のファイル名（拡張子を除く、最大20文字）を内部名にする。
その実装経路ではBISLPS-00782CONV.binなら既知のゲーム照合名と一致する。
TOWN0001-...のような解析用名をそのまま取り込むと一致しない。
MCSはdirectory frame内の名前を使う。
これは公開ソースの仕様と既知のゲーム比較条件からの推論であり、今回の原ゲーム読込試験ではない。

### ファイル内領域（終端はexclusive）

| 領域 | 開始 | 終端 | 長さ |
|---|---:|---:|---:|
| ヘッダ | 0x0 | 0x200 | 512 |
| チェックサム対象データ | 0x200 | 0x199A8 | 104360 |
| ゲームの加算チェックサム | 0x199A8 | 0x199AC | 4 |
| 保持する末尾 | 0x199AC | 0x1C000 | 9812 |

ヘッダとペイロードだけなら13ブロックに入るが、元の処理のファイル長は14ブロック。
末尾9812バイトは第13ブロックの残り1620＋第14ブロック8192。
ヘッダ4セクター＋mode0 700セクター＝最初の11ブロック、
mode1 192セクター＝残り3ブロック。
チェックサムは論理セクター819の+40、保持末尾は同セクター+44から始まる。
末尾には76個の完全な128バイトセクターも含まれる。

### 今回再構成して実行した検査

- 正常な14ブロックチェーン180通り。
- 長さの境界13例。
- 構造破損7例を拒否。上記合計200件。
- 別途、先頭ブロックと未使用ブロックを網羅する210配置、188160セクターを照合。
- MCSサイズ・内部名・データ位置の検査。
- ヘッダ/末尾の変更はゲームの加算チェックサムが保護しないことを確認。
- 同一セクター内の2バイト入替はゲーム加算値と通信XORの両方を保つ合成例を確認。
- 4イベントの非空ready組合せ15通りで探索順を確認。
- 同一イベントの重複通知が1つのready状態にまとまることをモデル検査。

モデルのイベント状態はBIOS仕様に合わせたラッチであり、件数付きFIFOではない。
クリア処理が自分のイベントを調べた後に新通知が来る場合、その通知は残り得る。
今回のモデルは原ゲーム命令列の実行ではなく、過去に得た処理順の再構成である。

### 実装と実機の区別

調査時のDuckStation memory_card.cppは書込みデータを逐次更新し、
WriteChecksum状態で受信チェックサム不一致を判定せず成功終端を返す。
そのため、この実装の成功だけを実機の不正チェックサム処理の証拠にできない。
psx-spxは通信チェックサム不一致の終端4Eと通常成功47を記録している。
不正セクター応答、割込みタイミング、障害後の実カード内容は未検証。

## 次に進める順序

1. r2 ZIPを展開できる環境で原EXE/BINハッシュ、同梱README、コード、実在スナップショットを再確認する。
2. 会話だけに残ったr3情報をr2から再実行し、復旧できた値と異なる値を記録する。
3. 実在する論理保存ファイルからMCSまたはrawカードを生成し、
   内部名、14ブロックチェーン、完全バイト列、ハッシュを検査する。
4. 原ゲームのタイトルから読ませ、ロード後のclock/資金/店舗/従業員を比較する。
5. イベントモデルをラッチ仕様と照合し、人工的故障注入と実BIOS由来の失敗を分ける。
6. カード互換試験が済んだら年次評価・ライバルAIなど未解析のゲーム処理へ戻る。
7. 以後、節目ごとにこの専用ブランチへ記録・コード・検証結果をコミットする。
   この補助記録のみを完全ZIP相当と見なさない。
