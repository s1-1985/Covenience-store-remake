# 初代ザ・コンビニ PS版 — アルゴリズム解析 第2報・会計／購入／万引き追補付き

提供ディスクの起動プログラム `SLPS_007.82` を逆アセンブルし、総合評価、店舗評価の増減の中心部分、人口集計、乱数、評価イベントの日付条件を解析した。復元したPythonの式を、元のMIPS機械語を実行した結果と照合した。

**評価等1,037件、会計等400件、購入等660件、合計2,097件の記録が一致。** 今回は価格・実際の棚在庫・万引き条件を追加解析した。前報の「在庫 +8」は「客の所持金 +8」へ訂正した。詳細は末尾の購入追補に記す。 これは選定した命令区間と入力に対する検証である。ゲーム全体をPS1で起動した試験や、すべての入力の数学的な等価性証明ではない。未解析の経営・行動処理は残っている。

## 1. 総合評価の計算式

画面の項目名は、プログラム内の独自文字列 `0x800B949C` を原作フォントで復号して確認した。順番は「店舗数／累積来客数／年商／町人口／店舗評価／総合評価」。計算ルーチンと表示ルーチンで同じ変数を参照している。

総合評価の材料は次の5項目である。

|項目|0点|4点|8点|12点|16点|20点|
|---|---:|---:|---:|---:|---:|---:|
|累積来客数|5万人未満|5万人以上|10万人以上|20万人以上|40万人以上|50万人以上|
|年商合計|1億円未満|1億円以上|2億円以上|3億円以上|4億円以上|6億円以上|
|町人口|3,000人未満|3,000人以上|8,000人以上|14,000人以上|18,000人以上|20,000人以上|
|店舗評価の平均|10未満|10以上|30以上|50以上|70以上|90以上|

店舗数の得点は別の刻みで、**対象店舗数×2点**。走査する店舗スロットは10個であり、有効フラグが非0、かつ属性の `0x8000` ビットが立っていない店舗を対象にする。対象外のビットの全用途は未解読だが、少なくともこの集計からは除外される。

```text
素点 = 店舗数×2
     + 累積来客数の得点
     + 年商合計の得点
     + 町人口の得点
     + 店舗評価平均の得点

総合評価 = 素点が96以上なら100、それ以外は素点
```

平均は整数除算で、通常の正の評価値では小数点以下を切り捨てる。年商合計には正数どうしの加算が32bitの上限を超えた際、2,147,483,647へ丸める処理がある。

**重要な結果：他の4項目がすべて20点なら、8店舗で96点となり、総合評価100へ到達する。** 10店舗でなければ100にならない、という式ではない。7店舗では同条件でも94点となる。到達可能性には資金・出店条件など未解析の要素が別途関係する。

評価の表示側では各項目の得点を4で、総合評価を20で整数除算した値を表示用関数へ渡している。星の個数との厳密な対応は、その表示用関数の解析を継続する必要がある。

根拠：計算 `0x8003F7FC–0x8003FE84`、表示 `0x8006C8B0–0x8006CDDC`。対象店舗ゼロでは、この区間は除数ゼロになる。ゲーム側がそれを避ける前提条件は未解析なので、復元関数で勝手に0点へ変更していない。

## 2. 店舗評価の増減

評価更新の中心部分は、**価格・サービス・セキュリティ・清潔さ・売上**の5条件を使う。名称は、条件に未達のとき選択される原作の助言文字列とも対応する。

- 「もっと商品の値段を安くすると」
- 「もっとサービスを良くすると」
- 「もっとセキュリティを良くすると」
- 「もっと店内を清潔にすると」
- 「もっと売り上げを伸ばすと」

現在の店舗評価を20で割り、0〜5に収めた段階を使って、判定基準を変えている。評価が高いほど、さらに改善するための条件が厳しくなる。

### 改善条件

|内部指標|評価0〜19|20〜39|40〜59|60〜79|80〜99|100|
|---|---:|---:|---:|---:|---:|---:|
|価格指標：以下なら達成|99|95|90|85|80|70|
|サービス指標：以上なら達成|50|60|70|80|90|100|
|警備指標：以上なら達成|70|75|80|85|90|100|
|清潔さ指標：以上なら達成|80|85|90|95|100|100|
|売上フィールド：以上なら達成|3,000,000|5,000,000|7,000,000|9,000,000|10,000,000|15,000,000|

5条件のうち**3条件以上を達成すると5点加算**。全条件を達成しても、この加点自体は5点である。

### 悪化条件

|内部指標|評価0〜19|20〜39|40〜59|60〜79|80〜99|100|
|---|---:|---:|---:|---:|---:|---:|
|価格指標：超えたら減点|100|100|100|100|100|100|
|サービス指標：未満なら減点|30|40|50|60|70|80|
|警備指標：未満なら減点|50|55|60|65|70|80|
|清潔さ指標：未満なら減点|75|80|85|90|95|100|
|売上フィールド：未満なら減点|500,000|1,000,000|1,500,000|2,000,000|2,500,000|3,000,000|

**悪化条件1件につき1点減点**。改善の達成数と減点は独立して判定される。そのため、例えば3条件で改善を達成し、残り2条件で悪化していれば、差し引き3点の上昇となる。最後に評価値を5〜100の範囲に収める。

```text
段階 = clamp(整数除算(更新前評価, 20), 0, 5)
良好数 = 5つの改善条件の達成数
減点数 = 5つの悪化条件の該当数
更新後評価 = clamp(更新前評価 − 減点数 + (良好数≥3なら5、他は0), 5, 100)
```

**解釈上の制限：** 価格指標を販売価格の円額や「定価比○％」と断定するところまでは至っていない。サービス等も、画面に出る値と全く同じ尺度かを別途追跡する必要がある。売上に使うフィールドは店舗構造体の `+0xD48` であり、月内の倍率適用前の累計であることが追補の解析で分かった。月の締めや8倍補正より前に読まれるので、月次報告の金額と直接比較してはいけない。

また、この中心部分の直前に `+0x118C` が非0なら1点下げる処理がある。今回、この値は万引き被害額と判明した（購入追補参照）。中心部分の検証モデルは、その減点後を入力とする。店舗評価の増減をすべて網羅したという意味ではない。助言の生成では店長側の値と乱数も使用されるが、そちらは今回の検証対象に含めていない。

根拠：中心部分 `0x800282FC–0x80028A94`、閾値表 `0x80099580–0x8009966F`、助言のポインタ表 `0x8009973C`。実装は `recovered.py` の `store_rating_core`。

## 3. 総合評価は年始のイベントとして予約される

イベント予約処理には、次の条件がある。

```text
分 = 0、時 = 0、月内段階 = 1 のとき：月次報告イベント（種別2）
さらに月 = 1 のとき：総合評価イベント（種別3）
```

予約関数に渡した種別3は、イベント処理側で総合評価の計算区間へ分岐する。**毎月の報告と、年始の総合評価は別イベント**である。原作の評価周期について、以前の動画からの推定をコードで裏付けることができた。

ただしイベントはキューへ登録される。実際の画面表示が予約と同時になるか、ほかのイベント待ちで遅れるかは別問題である。また、全体の時間進行ループや初回開始時の呼び出し順は未解析。

内部時刻カウンタ `t` からの変換関数も復元した。

|項目|計算|
|---|---|
|年|`t // 69120 + 1`|
|月|`(t // 5760) % 12 + 1`|
|月内4段階|`(t // 1440) % 4 + 1`|
|時|`(t // 60) % 24`|
|分|`t % 60`|

これは内部の周期を示している。月内段階を現実の暦の「日」と同一視したり、実時間で1年が何分かと換算したりはしていない。確認試験はカウンタ約100年分の範囲内であり、32bit全域での除算式の等価性を保証するものではない。

根拠：時刻変換 `0x80019EB4–0x8001A09C`、予約 `0x8003CEAC–0x8003CF40`、種別分岐 `0x8003F4C0–0x8003F524`。

## 4. 町人口の集計

町人口は、街の60×50区画を走査して集計する関数から得ている。

1. 各8バイトレコードの `+6` にある符号付き16bit番号を読む。
2. 番号が−1の区画は除外。
3. 引数が0以外なら、レコード `+4` の値が引数に一致する区画だけを選ぶ。
4. 番号を使って `0x8009FF1C + 番号×20` の表を読む。
5. 表には5組の16bitペアがあり、各ペアの先頭が−1でなければ、その次の値を人口へ加える。

4つの実マップそれぞれで、全体集計と2種類のフィルタ集計、合計12件を元命令の実行結果と照合した。表番号がどの建物名・住民属性を表すかの完全な対応表は未解読である。生のマップファイルを集計した値は、起動後の初期化・成長処理を含む実ゲームの初期人口と同一とは限らない。

根拠：関数 `0x80020498–0x800206A8`。総合評価側は引数0で呼び出す。

## 5. 乱数生成

元プログラム内の乱数関数は次の式である。

```text
seed = (seed × 1103515245 + 12345) mod 2^32
戻り値 = (seed >> 16) & 32767
```

状態は `0x800D6270`。関数は `0x8007E648`、シード設定は `0x8007E678`。戻り値は0〜32767である。シード1の最初の戻り値は16838。

6種類の初期シードから各20回、計120回を元コードと照合した。原作と同じ出来事の順番まで再現するには、乱数の式だけでなく、どの処理がどの順序で乱数を消費するかも合わせる必要がある。

# 会計・売上・在庫処理の追加解析

元プログラムの更新箇所まで追跡し、会計部分を追加で400件検証した。すべて元のMIPS命令の出力と一致した。既存の1,037件と合わせ、記録した比較は1,437件となる。

## 売上は三段階の帳簿に分かれる

各帳簿は20バイト＝32bit整数5個で、費用4項目と収入1項目を持つ。費用4項目の正確な表示名はまだ対応付けていない。

|店舗構造体内の位置|意味|
|---|---|
|+0xD88〜+0xD98|現在の内部日サイクルの帳簿。最後の項目が収入|
|+0xD38〜+0xD48|月内の累計。締め処理までは倍率適用前|
|+0xCE8〜+0xCF8|年内の累計。月の締めで補正後の金額が加わる|
|+0xD4C〜+0xD5C|直前月の帳簿。+0xD5Cが直前月の収入|
|+0xCFC〜+0xD0C|直前年の帳簿。+0xD0Cが直前年の収入|

**総合評価の「年商」は、現在年の途中売上ではなく、保存された直前年の収入を使う。** 第2報で特定した `+0xD0C` が、年の切り替え時に移動される先であることを確認した。

各帳簿は現在分と過去3期間分の4枠。締めで古い枠を一つずつ後ろへ移し、現在分を0に戻す。

## 月の締めには8倍の補正がある

内部時刻が月内段階1の0時0分になると、日サイクルの締めに続いて月の締めが行われる。月内累計の**費用4項目と収入をすべて8倍**にする。

通常の売買では、すでに資金へ1倍分が反映されている。月の締めでは残り7倍分を資金へ加減算する。

```text
補正前利益 = 月内収入 − 費用1 − 費用2 − 費用3 − 費用4
資金 += 補正前利益 × 7
月内帳簿の5項目をそれぞれ8倍
年内帳簿へ補正後の5項目を加算
補正後の月内帳簿を直前月の履歴へ移動
現在月の帳簿を0に戻す
```

例えば、補正前収入100万円、費用合計60万円なら補正前利益40万円。月の締めで資金に追加されるのは280万円で、履歴には収入800万円・費用480万円が残る。個別売買で反映済みの40万円と合わせると320万円となる。これは理解用の入力例で、ゲーム中の実績値ではない。

内部月は4つの24時間サイクルで構成されるため、8倍補正との組み合わせは4×8＝32サイクル相当の金額になる。ただし設計者の意図や現実の暦への換算まで断定するものではない。

## 店舗評価と月次報告は、同じ売上値をそのまま使わない

更新ルーチンでは次の順序が確認できる。

1. 時刻情報を更新。
2. すでに予約されたイベントを処理。
3. 店舗評価の更新を含む処理 `0x800275F8`。
4. 別の処理 `0x80029020`。
5. 日・月・年の会計締め `0x80029334`。
6. 後続の処理を経て、月次・年次イベントを予約。

店舗評価の中心部分は `+0xD48` を参照し、**月初の締め・8倍補正より前**に実行される。その時点では、現在終わろうとしている日サイクルの `+0xD98` を月内累計へ移す処理も、まだ行われていない。

したがって、評価の閾値表の300万〜1,500万を、補正後の月次報告の売上と直接比較してはいけない。厳密な再現には、値だけでなく締めと評価の順番も必要になる。この順序は主更新経路の静的確認であり、実機での画面更新タイミングの検証はまだである。

## 収入・支出の計上

関数 `0x8001CA7C` は、店舗、金額、入出金の区別を受け取る。

- 収入の場合：現在日サイクルの収入 `+0xD98` と、その店舗が属する側の資金へ金額を加える。
- 支出の場合：費用のうち `+0xD94` に金額を加え、同じ側の資金から引く。
- 店舗属性の `0x8000` ビットで資金口座の添字0/1を切り替える。

この関数だけですべての収入・費用が計上されるわけではない。ほかの費用項目には別の更新処理がある。

利益取得関数 `0x8001CCC0` は、日・月・年と履歴番号を受け取り、どの期間でも「収入−費用4項目」を返す。利益の式にここで別の税率をかける処理は見られないが、ゲーム全体に税等の処理がないという意味ではない。

## 購入金額には即時計上と後の精算の分岐がある（訂正）

前報は客レコードの `+8` を在庫、`+0xA` を未計上数量と解釈していたが、客詳細画面の参照先と「所持金」の表示から、**所持金と未精算の購入金額**であると判明した。数量とした値は単価であった。命令区間の算術検証は一致していたが、フィールドの意味付けを訂正する。

`0x80034AE8–0x80034B84` は所持金から単価を引き、モード1なら単価×数量係数を即時収入とする。それ以外では未精算金額へ単価を足す。`0x80035E64–0x80035EBC` は未精算金額×数量係数を収入計上して未精算金額を0にする。実際の棚在庫処理は今回の購入追補に記載した。

# 購入・棚在庫・万引き処理の追加解析

## 前報の訂正

前報で「在庫フィールド +8」「未計上数量 +0xA」と記した客レコードの値は、それぞれ**所持金**と**未精算の購入金額**であった。命令の加減算を確かめても、その値の意味まで確定するわけではない。前報の意味付けが誤っていたため、該当本文と検証コードの変数名を訂正した。既存80件の算術結果は変わらない。

根拠は客詳細画面 `0x8004B684–0x8004B7AC`。店舗先頭から `0xF04 + 客番号×32` の客レコードを選び、その `+8` を数値表示へ渡す。直後のメッセージID360は原作の「所持金」である。客初期化 `0x80032A7C–0x80032AB0` でも、客種別テーブルから所持金を設定し、`+0xA` を0にしている。

## 客レコードと価格

|客レコード内の位置|今回確認した用途|
|---|---|
|+1、符号付き8bit|この購入経路で対象とする商品番号|
|+2、符号付き16bit|客種別テーブルの添字|
|+8、符号付き16bitで参照|残りの所持金|
|+0xA、符号付き16bitで参照|未精算の購入金額|
|+0xC、+0xD、+0xE|位置と方向。前方の棚を調べるために使用|
|+0x1E、符号付き8bit|在庫減算数量。売上・被害額にも掛ける数量係数|

最後の数量係数が「ひとりの買う個数」か「客の集約人数」かはまだ確定していない。所持金はこの係数を掛ける前の単価だけ減るため、勝手に一般的な買い物モデルへ置き換えてはいけない。

購入経路 `0x8003473C–0x80034800` の式は次のとおり。

```text
基準値 = int32[0x8009CE08 + 商品番号×88]
係数   = int32[0x8009CE0C + 商品番号×88]
店舗設定値 = int32[店舗 + 0xC7C + 商品番号×4]
単価 = signed16(ゼロ方向切捨て(signed32(基準値×signed32(係数+店舗設定値)) / 100))
```

先頭商品では基準値110・係数50。店舗設定値50なら単価110、設定値40なら99になる。これは実データを使った計算例であり、店舗設定値を画面から何単位で変更するかは未解析である。

## 所持金と乱数による分岐

ここへ到達した購入候補について、次の順番になる。

1. 所持金が単価未満なら、所持金不足の経路へ進む。この判定では乱数を消費しない。
2. 所持金が単価以上なら、既報の乱数から `乱数値 % 100 + 1` を作る。
3. その値が `signed8[0x800A09E2 + 客種別×24]` 以下なら在庫処理を呼ぶ。超えると今回の処理では状態を維持して戻る。
4. 在庫処理が成功すると、所持金から単価を引く。
5. モード1なら `単価×数量係数` を即時収入にする。それ以外の通常購入側では、客の `+0xA` に単価を足す。

別の精算区間 `0x80035E64–0x80035EBC` は、`未精算金額×数量係数` を収入計上して未精算金額を0にする。

乱数は0〜32767の整数を100で剰余するため、1〜100の完全な一様抽選とは僅かに異なる。原作再現では同じ剰余処理と乱数消費順を維持する。以上は購入確率全体の式ではない。商品番号7には先行する別判定があり、商品の選択や来店自体の条件も今回の範囲外である。

## 実際の棚在庫と、残量による見た目の変化

呼び出し列は `0x800340FC → 0x8003B420 → 0x800209F8`。中間の関数は客の前方の棚を求め、数量係数を負にして在庫処理へ渡す。

在庫処理が座標を正規化した後の棚データは、`店舗 + 0x178 + Y×112 + X×4` の32bitワードにある。

|ビット|今回確認した用途|
|---|---|
|24〜30|在庫数。7bitで抽出|
|12〜21|商品表示の番号。3段階の残量表示を含む|

減算部分 `0x80020FBC–0x800212E0` は、棚の商品と要求商品が違えば失敗値2を返す。一致しても `在庫数−要求数量 < 0` なら失敗値2。これらの失敗経路では棚ワードを書き換えない。成功時は残量を棚へ書き戻し、戻り値1となる。中間関数は、この戻り値2を購入側の失敗値1へ変換する。

残量表示の段階は容量から次のように決まる。

```text
区切り = 容量 / 3 のゼロ方向切捨て
残量 <= 区切り       → 段階2
残量 <= 区切り×2     → 段階1
それ以外             → 段階0
表示番号 = (元の表示番号 // 3)×3 + 段階
```

容量100なら境界は33と66である。棚が複数セルにまたがる場合は、設備の幅・高さを使い、対象セルへ残量と表示段階を反映する。これにより、原作の棚の見た目を「品切れか否か」だけでなく3段階で再現する根拠が得られた。どの画像が各段階に対応するかの実画像照合は残っている。

今回は座標・設備の探索後から始める減算区間を検証した。補充側、配置変更側、座標探索を含めた関数全体の動作検証はまだである。

## 所持金不足から万引きへ進む条件

所持金不足側の `0x80034BA8–0x80034CA8` に以下の経路がある。

```text
モード == 0
かつ 防犯値 < 100 − signed8[0x800A09E3 + 客種別×24]
かつ 在庫処理が成功
    → 被害額[店舗+0x118C] += 単価×数量係数
    → グローバルフラグに0x10を立てる
    → 状態5を返す
```

この区間には別の乱数抽選がない。防犯値と客種別値の境界比較である。ただし、客の生成・商品選択など上流の乱数や条件まで存在しないという意味ではない。モード0の具体的な設備分類は未確定である。

被害額の用途は月次側の通知から確認できた。`0x80028214–0x800282F8` は被害額が非0なら店舗評価を1下げ、通知を出す経路で「今月、」に続けて被害額と「分 万引きされてしまいました」を表示し、その後被害額を0に戻す。文字列の所在は `0x80098E1C` と `0x80098E24`。従来、用途未確定だった店舗評価の事前減点を、万引き被害と結び付けられた。

この被害額加算区間には収入計上関数の呼び出しがない。原作を再現する際は、販売の入金と同一処理にしてはいけない。
