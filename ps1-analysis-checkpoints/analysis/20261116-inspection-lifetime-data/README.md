# 店舗の調査済み状態：月初消去の接続

2026-11-16 JST。前回の買収解析で残していた「調査済みフラグの有効期間」を、原の通常営業メイン処理へ結び付けた。通常経路の残件R03を解明として記録する。CPU営業更新は0回。

## 結論

店舗レコード+2の「調査済み」状態は、通常営業で**月初の午前0時に0へ戻る**。月内の他の日の午前0時では、この消去を行わない。

| 場面 | フラグ | 原UI/費用 |
|---|---:|---|
| 未調査 | 0 | 調査・買収・何もしないの選択画面。調査は500,000 |
| 調査を受理した後 | 1 | 詳細情報を表示する経路。表示上の再調査費は0 |
| 同じ月の別の日の午前0時 | 1を維持 | この月初消去処理は通らない |
| 翌月の区分1・時0・時刻内区分0 | 0へ消去 | 未調査時の選択画面へ戻り、再調査を受理すれば500,000 |
| 保存・読込 | 保存時の値 | 通常更新で月初条件を通る場合は、その後に消去される |

前回確認した「調査済み時のUI子関数は詳細を表示して既定値2を返す」という事実と矛盾しない。状態が永久に続くという推測は不要で、月替わりの消去が不足していた接続である。

## 原コードの根拠

通常メイン0x80023438内の店舗走査で、以下を順に判定する。

- 0x8002359C～0x800235A8：時刻内区分CE618が0。
- 0x800235B0～0x800235BC：時CE614が0。
- 0x800235C4～0x800235D0：日/月内区分CE610が1。
- 0x800235E0：その店舗の+2へ0を書き込む `sb zero,2(v0)`。

店舗走査は原の順序配列から最大10件、終端−1まで進む。この消去範囲には所有ビットの条件がないため、原走査順に含まれるライバル店舗にも適用される。

同じ月初の枝は27商品について+0x1198と+0x119Cを消去する。3番目の+0x11A0はこのループでは消去しない。調査フラグのためだけに全店舗レコードや商品実績を丸ごと初期化する移植は避ける。

調査受理時の1代入は0x800611BC、全店舗の原保存/読込みは0x8006BBB0/0x8006BFD0。保存ペイロード内の位置は `0x8858 + 店舗枠×5080 + 2` であり、月初以外にも読込みのたびに消去するという仕様にはしない。
