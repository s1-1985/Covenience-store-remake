# 自然営業で得た人物レコードから原描画パケットへ

2026-11-12。前回 `20261112-actor-display` で入力から到達した本店・2店目の人物レコードを、そのまま原 `80018A5C`（フレーム描画）と `80084830`（スプライトパケット）へ渡した。今回は人物グループだけを有効化した描画診断であり、営業を212更新進めたという意味ではない。

| 対象 | 元の人物レコード構築 | OTバッファ条件 | 描画診断 | 原パケット |
|---|---:|---:|---:|---:|
| 本店 | 46 | 2 | 92 | 184 |
| 2店目 | 60 | 2 | 120 | 360 |
| 合計 | 106 | 2 | 212 | 544 |

全件でパケット全バイト、書込先、書込ポインタ、深度9のOTリンク、後続16バイトの未使用領域、入力人物プールの不変を確認した。記録していた座標・UVだけを計算して合格としたものではなく、原命令が書いた24バイトのGPUコマンド列と既存独立式 `render_control.packet` を比較した。

## 確認した接続

- 人物表示グループのマスクは `0x200`、配列先頭は `800DA990`、件数は `800CDA2C`。
- ディスパッチャーは人物レコードを **末尾→先頭** に処理し、OT深度9へ追加する。OTは先頭挿入なので、CPUの処理順とリンクをたどる順は区別する。
- 今回の論理描画原点 `(160,120)` では、描画座標は人物レコード座標に `(160,120)` を加えた値となった。
- グリッド由来の人物は基本 `(8x,8y+22)`。右隣の什器補正がある場合はXを8減らす。休憩専用レコードは `(8x+8,8y+30)`。前回確認した位置決めの差はパケットにも残る。
- 全544個でサイズ16×16、UVは前回取得した原レコードと一致した。24バイトの実パケット、元レコードへの対応、入力ファイルのハッシュを `results.json.zlib`（zlib圧縮したUTF-8 JSON） に記録した。

これは座標・向き→人物レコード→描画コマンドの接続確認である。今回の経路では元のレコード座標がそのままコマンド座標へ渡るが、これだけでゲーム全体に歩行補間や足踏み画像切替が存在しないとは断定しない。

```sh
python verify-packets.py /absolute/path/to/algorithm-analysis
```

入力は前回の `../20261112-actor-display/first-store-results.json` と `second-store-results.json`。両ファイルのSHA-256を結果内に保持する。原EXEは `SLPS_007.82`、SHA-256 `d6a167a1c9e0fe98d7e44e12968caa489ac3eb7ed3b9e46012a188af8432b1fd`。

SDKの同期・送信境界はアーカイブの `BackgroundCategoryRunner` を再利用した。2つのOTバッファとも論理原点 `(160,120)` を与えており、実画面の上下交互バッファオフセット、GPUの画素化、VRAM画像の読出し、実時間の歩行速度、実音声は今回の検証外。元の営業RAM・時計・乱数やmain・Android本体を変更していない。
