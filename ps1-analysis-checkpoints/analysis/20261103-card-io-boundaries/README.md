# 原カード読書き：短いI/O戻り値の境界試験

原7AB2C（読込）と7ADF8（書込）を、同梱の限定MIPS実行系と論理BIOS境界で実行した。
自然な営業ケースの追加ではなく、I/O境界の診断24入力である。

## 入力と結果

最初の128バイト要求に対して一度だけ -1 / 0 / 127 / 128 を返し、その後は通常の128バイト転送へ戻す。
カードのイベント通知は成功のままにする。127ならファイル位置も127進めるという、明示した同期I/Oモデルである。

- r2実ペイロード＋試験末尾A5の16入力（読込/書込×mode0/1×4戻り値）。
- 値 (バイト位置×73＋19) mod 256 の書込み8入力で、内容の偏りを除いた。
- 24入力とも原関数の最終戻り値は0。
- 最初の -1 と0は、次の転送で一致した。
- 127の短い読込みはmode0/1とも最終データが不一致だった。
- 実ペイロードを反転した書込みではmode0の差が偶然隠れ、mode1に差が残った。
- 規則的な値での書込みはmode0/1とも1バイトの差が残った。mode0は本文+127、mode1は本文+89727で、期待74に対して19だった。
- 正常128の入力はすべて一致した。

全24入力中5入力で、成功戻り値と要求データの一致が一致しなかった。
これは上記の境界モデルでの結果であり、実機BIOSが127という短い戻り値を実際に返すことを示す証拠ではない。

## 再試行で差が残る理由

記録したI/Oでは、最初の127バイト転送でファイル位置が進む。
直後の再試行は同じRAM位置を使うが、ファイル位置を最初へ戻さず、進んだ位置から128バイトを転送する。
次の通常区画では絶対位置へseekするため、先頭区画のずれだけが残る条件がある。
したがって、原関数の戻り値だけを完全なデータ一致の根拠にしてはいけない。

## 保存形式と再現

fault-probe.py / fault-pattern-probe.py の引数は復元したr2 ZIP。
出力1行目が要約JSON、2行目が詳細JSONをzlib圧縮してbase64にしたもの。
保存済みsummary.jsonに要約、*.evidence.json.zlib.b64に詳細がある。

詳細各行のtrace_zlib_base64を展開すると、最初の故障を含む全I/Oトレースを復元できる。
展開したバイト列のSHA256をtrace_sha256と比較する。
output_patchesは、コードに記載した期待データに適用する本文絶対位置の差分であり、各結果のデータを復元できる。
data_sha256は試験したmodeの対象範囲全体のSHA256。最初の20差分だけのハッシュではない。

原本ZIP SHA256：afd46b32e0a24e3f2d75723a0c4a3fecc120d80b07993c2e73236e55cf3d54cd
原EXE SHA256：d6a167a1c9e0fe98d7e44e12968caa489ac3eb7ed3b9e46012a188af8432b1fd

SP=801D0000、GP=800CD6C4。原本来のファイル/イベント待ち/ディレクトリ処理は実行し、BIOS関数・通知・VSync・memcpyを論理境界に置く。
物理カードの通信、BIOS本体、全ゲームやPS1の完全再現を意味しない。
