# 原カード読書き：短いI/O戻り値の境界試験

原7AB2C（読込）と7ADF8（書込）を、同梱の限定MIPS実行系と論理BIOS境界で実行した。
自然な営業ケースの追加ではなく、I/O境界の診断24入力である。

## 入力と結果

最初の128バイト要求に対して一度だけ -1 / 0 / 127 / 128 を返し、その後は通常の128バイト転送へ戻す。
カードのイベント通知は成功のままにする。127ならファイル位置も127進めるという、明示した同期I/Oモデルである。

- r2実ペイロード＋試験末尾A5の16入力（読込/書込×mode0/1×4戻り値）。
- 値 (バイト位置×73＋19) mod 256 の書込み8入力で、内容の偏りを除いた。
- 24入力とも原関数の最終戻り値は0。
- 最初の -1 と0は、次の転送で一致した。
- 127の短い読込みはmode0/1とも最終データが不一致だった。
- 実ペイロードを反転した書込みではmode0の差が偶然隠れ、mode1に差が残った。
- 規則的な値での書込みはmode0/1とも1バイトの差が残った。mode0は本文+127、mode1は本文+89727で、期待74に対して19だった。
- 正常128の入力はすべて一致した。

全24入力中5入力で、成功戻り値と要求データの一致が一致しなかった。
これは上記の境界モデルでの結果であり、実機BIOSが127という短い戻り値を実際に返すことを示す証拠ではない。

## 再試行で差が残る理由

記録したI/Oでは、最初の127バイト転送でファイル位置が進む。
直後の再試行は同じRAM位置を使うが、ファイル位置を最初へ戻さず、進んだ位置から128バイトを転送する。
次の通常区画では絶対位置へseekするため、先頭区画のずれだけが残る条件がある。
したがって、原関数の戻り値だけを完全なデータ一致の根拠にしてはいけない。

## 保存形式と再現

fault-probe.py / fault-pattern-probe.py の引数は復元したr2 ZIP。
出力1行目が要約JSON、2行目が詳細JSONをzlib圧縮してbase64にしたもの。
保存済みsummary.jsonに要約、*.evidence.json.zlib.b64に詳細がある。

詳細各行のtrace_zlib_base64を展開すると、最初の故障を含む全I/Oトレースを復元できる。
展開したバイト列のSHA256をtrace_sha256と比較する。
output_patchesは、コードに記載した期待データに適用する本文絶対位置の差分であり、各結果のデータを復元できる。
data_sha256は試験したmodeの対象範囲全体のSHA256。最初の20差分だけのハッシュではない。

原本ZIP SHA256：afd46b32e0a24e3f2d75723a0c4a3fecc120d80b07993c2e73236e55cf3d54cd
原EXE SHA256：d6a167a1c9e0fe98d7e44e12968caa489ac3eb7ed3b9e46012a188af8432b1fd

SP=801D0000、GP=800CD6C4。原本来のファイル/イベント待ち/ディレクトリ処理は実行し、BIOS関数・通知・VSync・memcpyを論理境界に置く。
物理カードの通信、BIOS本体、全ゲームやPS1の完全再現を意味しない。

## 再試行の原命令と継続失敗

retry-loop-words.jsonに読込2か所・書込2か所の原命令列とハッシュを保存した。
比較は8007AC88 / 8007AD84 / 8007AF60 / 8007B05Cで、いずれもBNE V0,V1、V1=128である。
不一致では同じI/O要求準備へ戻り、その間にファイル位置の巻戻しはない。
各試行の後、原80089CA4へ引数2で呼び出す。試験ではこの待ちを明示した境界として供給する。

persistent-probe.pyでは、-1または0を継続して返す読込/書込×mode0/1の8条件を確認した。
いずれも20万命令の試験予算内では戻らず、I/O要求は9,478〜9,479回だった。
これはテスト側のinstruction_budget_exhaustedであり、ゲーム側のエラー終了やタイムアウトではない。
物理時間・実カードの待ち時間の測定ではなく、イベントが成功のままI/O結果だけが失敗する明示した制御条件である。

## 区画末尾の追加16条件

last-chunk-probe.pyでは、各modeの最後の128バイト要求だけに故障を入れた。
mode0の最後はファイル+89984、mode1の最後は+114560である。
mode1の127バイト転送後は、残り1バイトの読込み、またはファイル範囲外への書込みが再試行され、20万命令で試験側が打ち切った。
mode0の短い書込みでは、次のmodeの区画にもはみ出し得る。選択したmodeの比較だけでなく、全ファイルの差分・SHA256も記録した。
outside_mode_patchesは期待ファイル全体に対する、対象modeの外側のファイル絶対位置差分である。
最後の書込で範囲外エラーとなった再試行もwrite_errorとして全I/Oトレースへ残す。

## open・seek・closeの追加24条件

endpoint-probe.pyでは各端点が-1を一度だけ、または継続して返す条件を、読込/書込とmode0/1で確認した。
openとseekの一度だけの失敗は再試行して戻り、継続失敗では20万命令の予算内で戻らなかった。
closeの失敗は8入力とも再試行せず戻り、論理ファイルモデルにハンドルが1個残った。
待ち関数80089CA4は0を返す明示したモデルであり、この条件で原関数の最終戻り値も0だった。実SDKの全ての戻り値を主張するものではない。
この試験の既存論理ファイルは114688バイトのゼロ列であり、ゲーム内容の正しさは対象にしていない。

## 証拠の整合検証

診断は最初の24＋末尾16＋継続失敗8＋各端点24＝72入力。
verify-evidence.pyで、64本の全I/Oトレース、データ差分213バイト、16本のファイル全体、4か所の原再試行命令列を検証した。
evidence-validation.jsonが実行結果である。
これは記録の完全性と期待した診断結果の照合であり、72入力のゲーム処理がすべて正常終了したという意味ではない。

python verify-evidence.py /path/to/r2.zip
