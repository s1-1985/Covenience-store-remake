# 読込み入口の違い：祭り再計算・待ち通知・結果分岐の3接続

2026-11-18 JST。**［確実］同じ保存ペイロードを復元した限定入力で、タイトル読込み末尾は祭りスイッチを保持して客枠を変更し、営業中の読込み末尾は先にスイッチを消して客枠を変更しなかった。待ち通知の保持にも差があった。** 通常のカード操作全体を通した比較ではない。

## 今回の3点と既知の区別

| 調査 | 接続した結果 |
|---|---|
| 祭りスイッチ解除と需要再計算の順序 | タイトル末尾はスイッチ1のまま集計→需要。営業中末尾は先に0へし、その後に集計→需要。同じ入力で前者だけ店2・先頭客状態0→1 |
| 保存された待ち通知 | タイトル末尾では予約済み通知の枠1と全8000バイトが保持された。営業中末尾では50枠の有効バイトを0へし、通知状態・時間・添字を0へ戻した。残りの通知データ159バイトずつは消さない |
| 読込み結果の分岐 | 原624B8で戻り値が1以外なら625C4へ分岐し、デコード・通知解除・祭り解除・再集計の枝を通らない。共有末尾の設定・音処理とは別である |

単独の保存形式・カードUI・営業中ロードの基本挙動は既存r2と[保存読込み試験](../20261105-play-save/README.md)にある。[直前の祭り保存解析](../20261118-festival-load-order/README.md)はタイトル末尾と営業開始の接続に限定していた。今回の新規部分は、同一入力での2入口の比較と、その差を読込み結果の条件へ結び付けた点である。既知の通常ロードを新機能として数えない。

## 同じペイロードを両側へ渡す

元入力は原TOWN0001の初期店、ライバル1・2の営業時間を診断用に0、時計44640、祭りスイッチ1、乱数seed2。暦は原集計で［1,8,4,0,0］へ導出した。店2の先頭客レコードは全0である。

原3ECD8で、種別2・パラメータ0・音29・mode1の待ち通知を枠1へ予約した。空の原文字列は40FF終端を置き、後の文字列解釈や描画は実行していない。原6B81Cがチェックサムの一致するペイロードを生成した。その同一バイト列から、両側とも原6BC40で復元した。

保存スイッチ1・営業時間・乱数・通知は指定条件であり、通常操作でこのセーブを作れた証拠ではない。原ファイル本文のSHA256と、元通知160バイトの前後値を[結果](results.json)へ記録し、大量の新規RAMやカードファイルは保存していない。

## 1. 需要再計算前に解除するかで差が出る

タイトル側は原12D44～12D68を通し、原23C20・2619Cを実行した。営業中側は原6BC40の後、初期化624D0～62588と、再構築62598～625B4を実行した。両区間の間のBGM復元、各入口の画像・カード処理は実行していない。子関数の返り値を置換して経路を通したものでもない。

| 観測 | タイトル末尾 | 営業中末尾 |
|---|---:|---:|
| 復元直後の祭りスイッチ | 1 | 1 |
| 需要再計算時の祭りスイッチ | 1 | 0 |
| 先頭客状態の前→後 | 0→1 | 0→0 |
| 原26868の客状態書込み | 2バイトの1を1回 | なし |
| 最終の予約済み通知枠 | 1 | なし |

営業中の原62560がCDA00を0へしてから、原625A4が集計、原625ACが需要再計算を呼ぶ。タイトル側には、この再計算までに同じ解除がない。

これは前回の「タイトルで書込みが済んだ後、営業開始5CD84でスイッチだけ0になる」経路と矛盾しない。**営業開始と、営業中ロードの解除を同じタイミングとして扱わない。** 一方、営業中ロードが保存済みの既存客を修復するという結果でもない。今回の元客レコードは正常な全0である。

## 2. 待ち通知は入口で扱いが異なる

タイトル末尾では通知キュー8000バイトが全バイト一致した。営業中の原6251Cは、枠0～49の各160バイト先頭だけを0へ書く。原書込み監視で50回・サイズ1バイト・値0を記録した。

各通知の残り159バイト、種別・音・本文等はメモリに残った。通知を完全に160バイト消去する処理とは異なる。また原62548/62550/62558で、表示時間1398B8・表示状態1398B4・添字1398B0を0へする。

この初期化区間では店プール50800バイトは全バイト保持した。待ち通知を消すことと、客・店舗データを消すことを混同しない。

タイトル側でもロード開始前には通知リセットがあるが、既存 `title_load_control.py` の順序はリセット→デコード→末尾である。ペイロードから通知が戻った後に、今回と同じ解除はしていない。原の「保存対象」と「復帰時に残すもの」は同一ではない。

## 3. 非1の結果へ読込み後処理を広げない

原62484はまず現状をエンコードし、メニュー4EEB8を呼び、戻り値を保存してから音処理65000を呼ぶ。原624B8の命令は `bne v0,v1,625C4` で、v1は1である。

戻り値1だけが624C0のデコードから始まる枝を通る。非1は直接625C4以後の共有末尾へ進み、そこに6BC40・23C20・2619Cの直接呼出しはない。

非1すべてが取消だとは解釈しない。今回の実験ではカード/メニューの結果を取得しておらず、この分岐は原命令を読んだ結果である。「取消時は一切無変化」も主張しない。共有末尾には設定反映と音関係の呼出しがある。
