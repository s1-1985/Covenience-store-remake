# 補充対象・補充完了・商品取得失敗のデータ接続

2026-11-14。初代PS版SLPS_007.82の元ディスクを静的解析した。今回は店員の補充候補選択、実際の補充、客の商品取得、店長への報告をつなぎ、商品を扱う41什器の容量と移植用仕様へまとめた。

## 今回の追加

- 補充候補を選ぶ店員の+0x20と、実際の補充成功・数量に使う+0x1Fを分けた。
- 棚を選ぶ時点の残量閾値と、作業開始後の満杯までの補充を区別した。
- 他の店員が補充中の棚は常に占有されるのではなく、その店員の補充能力による抽選で候補から外すことを接続した。
- 客の商品取得失敗回数と、商品別の未充足需要人数の2種類を別データとして保存した。
- 全53什器のうち商品指定がある41件の容量を読み、12種類の容量と各閾値に対応付けた。

個々の在庫・店員目標・購入アルゴリズムは以前の復元モデルにもある。今回の追加は実マスター・能力欄・呼出し間の意味をつなぎ、数値例と原命令を保存した点にある。原CPUの営業更新や長期シミュレーションは行っていない。

## 2つの能力欄を混ぜない

| 店員レコード | この経路で使う内容 |
|---|---|
| +0x20 | 営業中・閉店処理中の補充候補の残量閾値 |
| +0x1F | 補充動作の成功抽選、成功時の要求数量 |
| 他店員の+0x1F | その店員の補充先を重複候補から外す抽選 |

+0x20には、この解析だけで確証のない能力名を新しく割り当てていない。同じ「補充能力」という1変数で全てを計算しない。

## どの棚が対象になるか

原 `0x80038D6C` は、設置アンカービットが立ち、什器IDが53未満、商品画像が非0の棚を調べる。

```text
在庫率 = trunc(在庫数 * 100 / 容量)
店舗状態1・2：閾値 = trunc(店員+0x20 * 2 / 3)
店舗状態0・3：閾値 = 99
在庫率 <= 閾値なら補充候補
```

店舗状態は0=閉店、1=営業、2=閉店処理、3=開店処理である。状態0・3でも、この関数へ到達した場合の閾値は99となる。常にその状態で店員作業が起きるという追加のスケジュールは仮定していない。

容量40、+0x20が100なら閾値66。在庫26は整数在庫率65で対象、27は67で対象外。残り3分の1まで待つ規則でも、全員が常に66％で始める規則でもない。能力値と整数丸めによって変わる。

対象量の最大値は、通常の非負値では `((閾値+1)*容量-1)//100`。12種類の容量それぞれについて、能力値0・25・50・75・100の境界をJSONへ保存した。

商品画像が非0なら、数量0の棚も対象となる。前回確認した通り、数量0では画像を描画しないが画像コード自体は残る。一方、まだ商品を指定しておらず画像コードも0の什器を、自動的に何かの商品で埋める処理ではない。

## 残量順に並べる処理ではない

候補を作った後は、使える什器の側面に目標マークを置き、経路探索へ渡す。候補を在庫の少ない順にソートする処理ではない。到達可能性、距離層、グリッドの走査・方向順が目標に影響する。

別の店員が状態2（補充）なら、その店員ごとに乱数を引き、`roll1..100 <= 2*その店員の+0x1F` で有効な補充先の側面を候補から除外する。能力50以上ならこの抽選条件は全てのrollで成立するが、低い場合は成立しないことがある。必ず有効な排他ロックとして実装すると原版と異なる。

店員の作業選択自体は、体力不足なら休憩を優先し、それ以外は条件を満たすレジ業務→補充→清掃→休憩の順に選ぶ経路がある。すでに保持している補充目標を、毎フレームこの順番で取り直すという意味ではない。

## 補充を始めたら満杯を目指す

目標へ到着し向きが揃うと、原3B278で実際の補充へ進む。

1. `rand()%100+1 <= 店員+0x1F` なら補充動作へ進む。失敗時は在庫・費用を変えず戻り値1。
2. 要求数量は `trunc(店員+0x1F/10)+1`。
3. 空き容量が足りなければ、入る分だけへ要求数量を減らす。
4. 実際に追加した数量×仕入単価を計上し、所有側の資金から差し引く。

在庫更新の戻り値1なら、補充量が不足して満杯ではない場合も、動作抽選が失敗した場合も、親は目標を保持する。戻り値0で満杯になれば目標を解除し、能力成長と音声フラグ0x0800へ進む。戻り値2のエラーでも目標は解除される。

つまり候補閾値は「仕事を始める棚を選ぶ値」で、補充後の目標在庫率ではない。一度着手した棚を66％などで打ち切らない。

### 原データによる数量・費用例

什器13（冷蔵ワゴン）の容量40、商品0（冷たい飲料）の仕入単価55、在庫26、補充能力+0x1Fが100の場合：

| 成功した補充 | 要求 | 実追加 | 在庫 | 費用 | 在庫更新の戻り値 |
|---:|---:|---:|---:|---:|---:|
| 1 | 11 | 11 | 37 | 605 | 1 |
| 2 | 11 | 3 | 40 | 165 | 0 |

37まで増えた後は新規候補の閾値を超えているが、保持した目標への仕事を続けて40にする。この表は原式から導いた例であり、今回実プレイを連続記録したものではない。

費用は店舗+0xD94へ加え、資金から引く。この局所的な呼出し経路には、資金残高が足りないという理由で補充を拒否する分岐はない。ゲーム全体の資金不足時の処理まで存在しないと断定したものではない。

## 客の取得はグループ単位で一括

原3B420は、客レコード+0x1Eのグループ数量を負の追加量として在庫更新209F8へ渡す。要求より在庫が少なければ、途中まで渡すことなくエラーとなる。

| 在庫 | 要求する人数分 | 結果 |
|---:|---:|---|
| 2 | 3 | 取得失敗。在庫は2のまま |

この失敗呼出しでは、店舗+0x12E2を1増やす。人数3や不足分1を加算する式ではない。カウンターは符号付き127未満の場合だけ増加し、127で止まる。取得失敗の理由には在庫不足以外に、対応する商品や什器が一致しない場合も含まれる。

## 商品別の未充足需要とは別集計

購入制御340FCで目的地の検索が失敗し、商品が-1ではなく、その商品の店舗サマリー在庫が0の場合は、`店舗+0x119C+商品ID*12` にグループ人数を加える。

| 記録 | 増やす単位 | 主な条件 |
|---|---|---|
| +0x12E2 | 失敗した取得呼出し1回 | 原3B420で商品取得が失敗 |
| +0x119C+商品ID×12 | グループ人数 | 目的地検索失敗かつ当該商品のサマリー在庫0 |

両方を同じ「品切れ数」として扱うと、店長の報告と商品別の需要記録が変わる。目的地検索失敗時に別の店へ客を再配分するという追加挙動は、この記録から導いていない。

## 店長の報告は「超過」で判定

商品取得失敗のカウンター+0x12E2について、助言3B570の閾値は `trunc((100-店長指導力)/4)+5`。報告候補になる比較はカウンターが閾値を**超える**場合であり、以上ではない。

| 指導力 | 閾値 | 他のリセットがなければ最初に超える回数 |
|---:|---:|---:|
| 100 | 5 | 6 |
| 0 | 30 | 31 |

カウンターには既存の4時間区切り、助言発生後、別の稀な処理のリセットがある。必ず失敗6回目などで報告が出るという時間経過の保証ではない。

## 保存物と再抽出

- `restocking-capacity-masters.json`：商品を扱う41什器の容量、境界値、能力0～100の補充数量。
- `android-restocking-stockout-bridge.json`：選択・作業継続・予約判定・費用・2つの失敗記録。
- `source-derived-examples.json`：容量40の境界と満杯までの補充、人数分一括取得の例。
- `source/*.bin`、`restocking-readers.asm`：原データと関連命令。

```sh
python -m pip install capstone==5.0.7 Pillow==13.0.0
python extract-restocking.py /path/to/SLPS_00782.BIN
```
