# 祭り：保存・読込み再集計・営業開始・通知乱数の4接続

2026-11-18 JST。**［確実］指定した保存状態では、客枠が正常なまま原形式で保存・復元した後、タイトル読込み末尾の需要再計算で客状態へ書込みが起こった。後続の営業開始処理が祭りスイッチを0へ戻しても、その客状態は復元されなかった。** カード操作や祭りを自然に進めた観測ではない。

## 既知と今回の追加

既存r2には保存ペイロードの対応表、タイトル読込み・営業開始の単独処理、通知の原モデルがある。祭りの範囲外需要と先頭客枠の別名対応も[境界解析](../20261116-festival-profile-boundary-data/README.md)で既知だった。

今回は、それらを次の4点で接続した。保存式や乱数式そのものを新発見とは数えず、直近の指定位置での会計・退出試験も繰り返していない。

| 調査 | 新たに接続した結果 |
|---|---|
| 祭りスイッチの保存・復元 | 原6B81Cがスイッチ1をペイロード+14EC8へ保存し、原6BC40が実メモリへ1を戻した |
| タイトル読込み末尾 | 原12D44～12D68の集計→需要再計算が、保存時には全0だった店2の先頭客枠を状態1へ変更した |
| 営業開始の解除順序 | 原5CD84は祭りスイッチを0へするが、既に変更された客状態1と店舗プール全体を保持した。再構築フラグは原5CD9Cが1にした |
| 客処理前の乱数位相 | 原3CEACを1回通すと、店・通知キューを保持したまま乱数が1回進んだ。孤立した客ループと同じ乱数位相とは扱えない |

## 1. 原保存対象に祭りスイッチが含まれる

元入力は原TOWN0001の初期店データ。ライバル1・2の営業時間を診断用の0にし、時計44640、祭りスイッチ1、現在の乱数seed2を指定した。暦［年1、月8、期4、時0、分0］は原23C20に時計から算出させ、暦値そのものを祭り値へ書き換えていない。保存時の店2の先頭客レコードは32バイトすべて0である。

原6B81Cで104364バイトのペイロードを生成した。原BBCCが祭りスイッチを+14EC8へ書く。末尾の原チェックサム1942271は、先頭104360バイトの合計と一致した。

その後、実RAMの祭りスイッチを0、先頭客状態を診断マーカー0x77へ変え、原6BC40でデコードした。原6BFECが祭りスイッチ1を復元し、客レコードも全0に戻った。コード上の対応表だけでなく、今回生成したペイロードから実際に復元した結果である。

カードUI・BIOS入出力・原ロードのチェックサム受理分岐は実行していない。自然な祭りの最中にメニューからこのファイルを作れた証拠でもない。バイナリ本体を追加保存せず、SHA256・サイズ・チェックサムを結果JSONへ残した。

## 2. 客状態の変更は読込み後の再構成で起きる

次に、原タイトル読込みの末尾12D44～12D68を実行した。この区間は表示店舗番号0・再構築フラグ1を設定し、原23C20の集計、原2619Cの需要再計算を呼ぶ。最後の描画再構築41A08の直前で停止した。

集計前には、非保存の派生暦5欄をすべて−99にしておいた。原デコードはそこを復元せず、原23C20が保存された時計44640から［1,8,4,0,0］へ再算出した。これは派生値の再構成を確かめるマーカーであり、需要処理へは元の暦が渡っている。

原26868が店2の先頭客枠へ2バイトの値1を書いた。デコード直後の全0レコードは、先頭1バイトだけ1、残り31バイト0となった。したがって、今回の客状態の変更は「元ファイルに壊れた客が保存されていた」ためではない。

この呼出しはタイトル読込み末尾の無条件の需要再計算であり、営業の時計更新や客生成を1回進めた実験ではない。ただし今回の保存時計はもともと境界時刻なので、境界以外の日時で成立するという追加結論は出していない。

タイトルのカードUI・資源読込み・画像再構築等、12D44へ至る前の全処理は実行していない。「通常ロード画面を最後まで通して発生した」とは表現しない。

## 3. スイッチ解除と客データの修復は別

上記の直後、原営業開始5CD60～5CDCCを通し、最初の画面/BGM関連呼出しの前で停止した。

| 項目 | 原営業開始前 | 後 |
|---|---:|---:|
| 祭りスイッチCDA00 | 1 | 0 |
| 店2・先頭客状態 | 1 | 1 |
| 再構築フラグ1398BC | 1 | 1（原から設定） |
| 表示店舗13796C | 0 | −1 |
| 店プール50800バイト | 比較元 | 全バイト一致 |

祭りスイッチの書込みは原5CD84の1回のみ。ここでスイッチを0へしても、需要再計算が先に変更した客データを巻き戻す処理はない。Androidで読込み後のリセットを単一処理へまとめると、元の呼出し順との差を隠してしまう。

原営業開始に再構築フラグの設定経路があること自体は既知の `mainplay_entry.py` にもある。今回の追加は、前回指定値で済ませていたフラグの原書込みを、読込み・祭りスイッチ解除・変更済み客枠と接続した点である。ここから先の最初の主更新・決算・祭り演出は未実行である。

## 4. 通知処理は何も起きなくても乱数を進める

主更新は需要の後に原3CEACを呼び、その後に各店の準備・客処理へ進む。今回の状態から原3CEACを1回だけ通すと、乱数は次のように変わった。

`0x3F17399B → 0xD952F138`

原乱数7E648の入口は1回、店プール50800バイトと通知キュー8000バイトはすべて保持した。この入力は期4なので年次・月次の通知予約枝を通らず、その後の既知の抽選に原乱数を使った結果である。

原6B81C/6BC40を通した際の現在乱数seed2も、今回の往復では変わらなかった。この保存コピー表には乱数D6270が含まれていないことは既存 `save_codec.py` に記録済み。今回のseed2を「セーブから復元された乱数」と取り違えない。

これは実際の最初の主更新を丸ごと再現したものではない。前の手順から省略された画面/BGMや決算の影響を含めず、通知と客処理の間に乱数位相の差が生じ得る1例として記録する。前回の孤立ループで入店成功が何回目だったかを、そのまま自然な営業更新数へ換算しない。
