# 商品名・什器対応・在庫画像のデータ解析

対象は初代PS版 SLPS_007.82。2026-11-13。ディスクの静的抽出と原命令の読解を行った。営業シミュレーションの延長は行っていない。

## 今回の新しい確定事項

- 商品レコードの先頭は `0x8009CDF0`、1件88バイト、27件。従来の価格中心の読解では `0x8009CE08` を基準にしていた。24バイト前に商品名があり、名前・価格・画像・季節コードを一つの構造として抽出できる。
- 未識別の内部商品ID26は、元EXEのShift-JISで **「現金」**。対応する什器ID43・44は、既存MSG00復号文の **「キャッシュディスペンサー」** とつながる。以前の「特殊商品」「特殊商品棚」という仮称を解消した。
- 27商品と53什器から、販売可能な組合せ172組を抽出。4方向分の配置規則688件と、各月の画像選択をスマホ版向けJSONへ整理した。
- 売却・消費時は、各マスに記録済みの絵柄を維持し、在庫量に対応する画像段階だけを更新する。補充・商品変更時には、その時点の月と什器の向きから絵柄を選び直す。既存の在庫更新モデルから、この状態保持の意味と月跨ぎの移植差分を具体化した。

価格式・在庫更新関数・画像変換自体は以前の復元モデルにも存在した。今回は商品名との結合、全対応表、描画用の移植データ、現金の識別が主な追加であり、全アルゴリズムを新発見したという意味ではない。

## 商品レコード

| バイト位置 | 型 | 読解 |
|---|---|---|
| +0 | Shift-JIS[24] | 商品名、NUL終端 |
| +24 | i32 | 基準価格 |
| +28 | i32 | 原価率 |
| +32 | i32 | 初期価格設定値 |
| +36 | i32[12] | ディスク上の画像ID |
| +84 | i32 | 季節コード（数値を保存） |

初期化関数 `0x8001B0C8` は `0x8009CE10 + id*88` を読み、店舗 `+0xC7C + id*4` に初期価格設定値として保存する。全27件で原価率と初期設定値の和は100。販売単価は在庫更新関数において `基準価格*(原価率+店舗設定値)/100`、仕入単価は `基準価格*原価率/100`。符号付き整数計算・ゼロ方向への除算を行う。初期設定値そのものを最終売価として扱わない。

原表の画像IDは起動時 `0x8005C858` で `id*3+360` に変換される。`-1` はそのまま。通常の絵柄候補は最初の `-1` までである。コピー用紙・現金には位置11にも非負の値があるが、通常の並びには含めない。この位置11の全用途は未確定。

両什器は1×1。方向0～3の画像基準は `[612,603,606,609]`。これらは紙幣画像というより機械に重なる小さな表示部として見える。画像内容だけで内部の金銭挙動を推測しない。

通常客の購買プロフィール144件×4商品枠には、ID26の指定が一件もない。したがって、名称と対応什器は確定したが、「客が現金を引き出す」「手数料が発生する」「容量50は50万円」などの動作・単位は今回の証拠からは確定できない。スマホ版で架空の収益処理を追加しない。

## 在庫画像の状態

原関数 `0x800209F8` は在庫数をアンカーから読み、容量との比較で画像段階を選ぶ。

```text
t = capacity // 3
phase = 2 if quantity <= t else 1 if quantity <= 2*t else 0
image_code = image_base + phase
```

数量は各描画マスにも同じ値が複写される。各マスの数量を合計して在庫数としない。消費時は既存の `image_code//3*3` を基準にする。数量0でも段階2のコードは残るが、描画関数 `0x8005643C` は数量0の商品を表示しない。

補充・商品変更時の絵柄選択は以下の通り。

| 商品 | 選択規則 |
|---|---|
| 通常商品 | `(月-1+マス通番) % 最初の-1までの画像数` |
| イベント商品24 | 画像枠 `月-1`、12か月分 |
| 現金26 | 方向番号0～3 |
| 宅急便申込書21 | 向きに応じた端のマスは枠0～3、内部は枠4 |
| コピー用紙20 | 通常は枠0。什器36では向きと端位置から枠1・2・3 |

方向2・3では什器の幅と高さを交換。ここでは元の方向番号を保持し、根拠のない東西南北の命名を避けた。マス通番は行優先で進む。

例：什器0・商品3（弁当類）・方向0では、1月補充の基準画像は387。2月になってから販売しても基準387を保持し、残量の段階だけを変える。2月に補充すると基準390へ切り替わる。これは表と分岐から導いた例であり、実プレイを連続記録した動画ではない。

## スマホ版への反映点

調査した `chatgpt/android-analysis-integration-20261105` の `game/scripts/store_view.gd` は、描画のたびに現在月から絵柄を作り直している。この方式では月変更後の売却前後に原版と異なる絵柄になる可能性がある。商品ごと・什器ごとの数量に加え、描画マスの画像基準を保持し、補充・商品変更で更新する必要がある。

また、商品26と什器43・44の仮称を元名称へ置き換える。今回の成果は解析・移植用データであり、このコミットでアプリ本体の変更やAPK再ビルドはしていない。

画像ページは `SYOP_S00/01/02.TIM`。原描画の比較は `code<=256`、`code<=512`、それ以降でページ9・11・13を選ぶ。UVは `((code&15)*16, code&240)`。256・512境界を通常の単純な `code//256` に置き換えない。これは既知の描画規則であり新規バグ発見として数えない。

## 保存ファイル

- `product-fixture-data.json`：全商品・什器、元アドレス、元ワード、対応商品。
- `android-stock-bridge.json`：方向・月ごとの画像基準と在庫段階の更新規則。
- `products.csv`：商品27件の一覧。
- `product-images.png`：原TIMから切り出した画像。各組は在庫多・中・少。列番号は画像枠。位置11も省略せず掲載するが、通常使用は断定しない。
- `source/*.bin`、`stock-readers.asm`：関連する元データ・命令とSHA-256。
- `extract-product-stock.py`：ディスクから再抽出するコード。
