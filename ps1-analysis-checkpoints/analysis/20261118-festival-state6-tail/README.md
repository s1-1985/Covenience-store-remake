今回は祭り需要生成を繰り返さず、成立済みの状態6を後段の診断入力にした。通常ループ・座標反映・空き枠探索の式自体はr2のcustomer_loop.py、customer_position.py、customer_spawn_core.pyで既知である。今回増えた根拠は、異常状態6に対する後段の分岐・全店舗バイトの保持・次の空き枠選択を、原命令で接続した結果である。

## 末尾は占有セルを消さない経路を通る

原客ループはまず現在のx・y・向きを作業欄へコピーする。状態6は状態1～5の処理を呼ばず、末尾の座標比較へ進む。処理が作業座標を変えていないので元座標と一致し、0x80032D58から次の客枠へ進む。移動時の旧セル消去・新セルへの画像書込み・変更フラグ更新へは入らない。

| 限定入力／確認箇所 | 結果 |

数値・座標・占有セルは、後段の違いを観測するための人工入力である。自然に到達した客や実際の映像ではない。[入力の32バイト、分岐、差分、ハッシュ](state6-results.json)を保存した。未決済額が保持されたからといって、全イベントを含めた永久未決済や損失額が確定したとは扱わない。

## 空き枠として再利用されない

原空き枠探索0x800330E4は、各客枠の状態が厳密に0のものだけを返す。先頭が6、次から0という同じ店舗入力では、返り値は枠1で、先頭枠0は飛ばされた。

従って、状態6は通常ループと空き枠探索だけでは、行動する客にも空き枠にも戻らない。これは他の書込みが介在しない場合の局所的な保持規則である。日次初期化、店舗の改装・撤退、次の祭り需要加算等を含めた全ライフサイクルで永久に残るとは断定しない。

人物画像番号が格納された店内セルを消さないことまでは確認したが、描画フレームを実行・撮影した結果ではない。「画面が必ず固まる」「クラッシュする」とは主張しない。
