# 天候値・月別表示・来客フィルターの接続

2026-11-16 JST。原ディスクから天候の数値範囲、月別の画面表示、144購買型の天候上限、4マップの客構成人数を結び付けた。通常生成80値×144型の11,520判定をビット表として保存し、元マップの構成を天候別320行へ集計した。CPU営業更新は0回。

天候生成式、季節処理、月別定数は既存の回収結果である。今回の追加は、生成範囲と表示境界の違い、実客構成の天候通過数、カレンダー上の祭りフラグとフィルター迂回の接続である。

## 天候は数値のまま来客判定へ使う

通常生成は最初の `RNG%100+1` を月別累積しきい値と比べ、次の範囲を選ぶ。

| 生成分岐 | 天候値 | 消費する天候用乱数 |
|---|---:|---:|
| 最初のしきい値以下 | 0 | 1回 |
| 2番目のしきい値以下 | 1～19 | 2回 |
| 3番目のしきい値以下 | 20～39 | 2回 |
| 4番目のしきい値以下 | 40～59 | 2回 |
| それより大きい | 60～79 | 2回 |

一方、画面の表示境界は **0／1～19／20～49／50～79／80以上**。生成の40～59という分岐は表示上の2区分にまたがる。来客判定へ渡す前に数値を「晴れ/曇/雨」だけへ丸めてはいけない。

| 月 | 生成用の累積境界4値 | 表示50～79 | 表示80以上 | 月内区分1～4の来客率選択 |
|---:|---|---|---|---|
| 1 | 30 / 60 / 80 / 95 | [雪　] | [大雪] | 1 / 0 / 0 / 1 |
| 2 | 30 / 60 / 70 / 90 | [雪　] | [大雪] | 0 / 0 / 0 / 1 |
| 3 | 30 / 60 / 80 / 95 | [雨　] | [大雨] | 0 / 0 / 0 / 1 |
| 4 | 30 / 60 / 80 / 95 | [雨　] | [大雨] | 0 / 0 / 0 / 1 |
| 5 | 40 / 70 / 80 / 95 | [雨　] | [大雨] | 1 / 1 / 0 / 1 |
| 6 | 1 / 10 / 40 / 90 | [雨　] | [大雨] | 0 / 0 / 0 / 1 |
| 7 | 20 / 40 / 70 / 90 | [雨　] | [雷雨] | 0 / 0 / 0 / 1 |
| 8 | 30 / 60 / 80 / 90 | [雨　] | [雷雨] | 0 / 1 / 0 / 1 |
| 9 | 20 / 50 / 70 / 80 | [雨　] | [台風] | 0 / 0 / 0 / 1 |
| 10 | 40 / 70 / 80 / 90 | [雨　] | [台風] | 0 / 0 / 0 / 1 |
| 11 | 40 / 70 / 80 / 95 | [雨　] | [大雨] | 0 / 0 / 0 / 1 |
| 12 | 30 / 60 / 80 / 95 | [雪　] | [大雪] | 0 / 0 / 1 / 1 |

来客率選択0は原購買型+21、1は+22を参照する。この48個の値を独自の曜日カレンダーで置き換えない。

表示80以上には大雪・大雨・雷雨・台風があるが、**今回追った通常生成関数は79までしか生成しない**。これは生成元を限定した結果で、他の書込み・保存状態まで含めてゲーム全体で絶対に表示されないと断定したものではない。

[12か月の生成/表示表](monthly-weather-hud.json)に各1～100ロールの区間個数と原メッセージ番号を保存した。区間個数をそのまま厳密な発生確率と呼んでいない。原RNGは15bit値に剰余を取るため、1～100が完全に均等ではなく、2回目の乱数との独立性も仮定していない。

## 144購買型と原マップの人数

通常の天候条件は `購買型の符号付き+13値＋20 >= 天候値`。同値なら通る。通過後に、主商品の季節条件、区分別の来客率、営業時間・在庫・距離等を使う店選びが続く。

| 原マップ | 天候0を通る有効構成人数 | 天候79を通る有効構成人数 | カタログ外参照の人数（別保持） |
|---|---:|---:|---:|
| TOWN0001 | 2,177 | 1,523 | 2 |
| TOWN0002 | 1,879 | 1,441 | 1 |
| TOWN0003 | 1,424 | 956 | 0 |
| TOWNPS | 2,838 | 1,950 | 1 |

これは原セルの客構成に記録された人数の重みであり、観測した人物数でも、その日の来店数や売上予測でもない。天候以外の条件を通過した結果は含めていない。曜日別/休日別の重み付きしきい値合計もJSONに残したが、実際の来客期待値とは扱わない。

[map-weather-cohorts.json](map-weather-cohorts.json)に天候0～79の全320行、[profile-weather-limits.json](profile-weather-limits.json)に144型の上限、[weather-profile-eligibility.bits](weather-profile-eligibility.bits)に判定ビット表を保存した。

## 祭りの日は最初の3条件を迂回する

財務処理は午前0時ごとに0x800CDA00を0にし、月8・区分4の祭り通知後だけ1へ変える。その後に呼ばれる需要再構築がこの値を読み、**天候・主商品の季節・区分別来客率**の3条件をまとめて飛ばす。通常日の判定と同じ扱いにしない。

天候そのものの生成、町セルの走査、需要領域の初期化、店選びや在庫/営業時間等の条件は続けて実行する。祭りだから全員が必ず入店するという仕様ではない。原の静的な呼出し順・代入・分岐を結び付けた結果であり、今回新しく8月まで自然営業を進めた記録ではない。

## 既知のカタログ外参照と今回の境界

前の客データ解析で、電気屋の客構成136に購買型144という範囲外参照があり、その人数を町人口から消すと合計が変わることを確認済みである。今回の表でも原人口と有効購買型の人数を分けた。

今回、以前は到達可能性を追っていなかったフィルター迂回フラグを、祭りのカレンダー条件へ接続した。迂回後の購買型144が店選びでどう処理されるかは未確定であり、通常営業のクラッシュや破壊を観測したとは主張しない。[境界記録](out-of-catalog-context.json)を保存し、Androidでは隣の原バイト列を架空の人物として読み込まない方針を維持する。
