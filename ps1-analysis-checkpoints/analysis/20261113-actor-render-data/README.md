# 通常店内の人物描画・向き変更・更新タイミング

2026-11-13。初代PS版SLPS_007.82の原ディスクを静的解析した。既存の「4方向画像」「人物座標」の読解から一段進め、人物描画経路の読み出しフィールド、休憩表示、ルート終端時の向き、入力と営業更新の順番を移植契約として整理した。

## 今回の結論と範囲

通常店内の客・活動中の店員について、位置反映→人物レコード構築→描画ディスパッチ→GPUパケット構築の経路では、**整数の0.5マス座標と向き4枚を使って描画する**。追った画像式に歩行フェーズはなく、パケット構築関数にも座標補間・UVの自動切替はない。

この経路の再現に、未発見の足踏み用画像を待つ必要はない。一方で、ゲーム全体の全場面に歩行演出が存在しないと断定したものではない。実時間の速度、特殊演出、他の描画経路は範囲外である。

以前の176方向画像や営業枝の観測を再び新発見として数えてはいない。今回の追加は、描画関数がどのレコードフィールドを実際に読むか、休憩時の固定方向、ルート切替時の表示と入力による更新抑制を具体的なデータへした点にある。原CPUの営業更新は実行していない。

## 原コードの接続

| 段階 | 原アドレス | 内容 |
|---|---|---|
| 店員のマス移動 | `0x80037734` | ルートを1単位進め、区間が終わると次の方向を先取り |
| 店員の位置反映 | `0x80037A34` | マス座標・向きを占有グリッドの人物画像コードへ反映 |
| 客の位置反映 | `0x80032C68` 以降 | 客の外見・向きから同じ人物画像コードへ反映 |
| 店内の再構築 | `0x80041218` | 床、什器・商品、人物の順に各構築関数を呼ぶ |
| 人物レコード構築 | `0x80056A3C` | グリッド上の人物と休憩中の店員を列挙 |
| 描画ディスパッチ | `0x80018A5C` | 人物マスク0x200、OT深度9、レコード末尾から処理 |
| パケット構築 | `0x80084830` | 保存済みXY・UVへ描画原点を加えて出力 |

人物レコードは `0x800DA990`、件数は `0x800CDA2C`、1件36バイト。初期化 `0x80013448` は33件のテンプレートを用意し、各画像を16×16、ページ5、パレット参照Y=493として設定する。33はテンプレート数であり、人物構築関数が不正な件数を33へ自動制限するという意味ではない。

## 拡縮・回転のような末尾フィールドを読んでいない

パケット構築関数 `0x80084830..0x800849AC` は入口で人物レコードのポインタをt3に置く。t3からのロード命令を列挙すると、読み出す先頭位置は以下だけである。

`0,4,6,8,10,12,14,15,16,18,20,21,22`

先頭のフラグ、XY、幅・高さ、画像ページ、UV、パレット参照、RGBに相当する。**+24～+35の末尾は読まれない**。レコードの初期化には末尾の0や4096という変換用に見える値も存在するが、通常人物のこのパケット関数がそこから補間・回転・拡縮を実行しているわけではない。

`packet-record-accesses.json` に15本のロード命令と元アドレスを保存した。ほかのポリゴン描画関数まで同じ仕様だと一般化しない。

## 活動中と休憩中は位置・向きが違う

### グリッド上の人物

- グリッドの下位10bitが0、人物画像コードが640～819なら列挙対象。
- 画像コードは `外見ID*4+[1,0,2,3][方向]+640`。
- 右隣が店内幅に収まり、その下位10bitに什器コードがあればXを8減らす。
- レコード座標は原則 `(8*x-160,8*(y-1)-90)`。

### 休憩中の店員

- 配属スロットが有効、店員の状態+40が0、X・Yがともに-1以外なら別途列挙。
- 画像コードは `外見ID*4+640`。方向オフセットを読まないため、既知の方向表では**下向き画像で固定**となる。
- レコード座標は `(8*x+8-160,8*(y-1)+8-90)`。

例えばグリッド座標(4,3)、描画原点(160,120)の場合は次のようになる。

| 条件 | 原レコードXY | 最終パケットXY |
|---|---|---|
| 通常の人物 | (-128,-74) | (32,46) |
| 右隣に什器 | (-136,-74) | (24,46) |
| 休憩中の店員 | (-120,-66) | (40,54) |

この8ピクセル差を歩行中の揺れ・補間と取り違えない。例は元の算式から生成した位置例であり、実ゲームのスクリーンショットではない。実際の描画原点はパケット関数への環境入力として扱う。

## 人物の列挙順と描画順

構築順は、グリッドを上→下・左→右に走査した人物、その後に休憩中の店員スロット2→1→0。CPUは人物レコードを末尾→先頭でパケット化するが、OTへの登録は先頭挿入のため、そのバケット内のリンクをたどる順は再びレコード0→末尾になる。

単に「CPUが逆順で呼ぶから画面も逆順」と扱わない。休憩中の店員をグリッド走査へ混ぜて独自の並べ替えをすると、同一深度の重なり順が原版と異なる可能性がある。

## 区間の最後の移動で、次の向きを先取りする

店員ルートは、上位2bitが方向、下位6bitが移動回数、0xFFが終端。空いた通路を移動する分岐では、残り回数を減らして0になるとルートを詰め、次の区間があればその向きを同じ更新内で新しい姿勢に入れる。

外見38の店員が(4,3)から「右へ1、その後上へ2」と進む元算式の例：

| 更新 | 座標 | 表示方向 | 人物画像コード |
|---:|---|---|---:|
| 0 | (4,3) | 右 | 795 |
| 1 | (5,3) | 上 | 793 |
| 2 | (5,2) | 上 | 793 |
| 3 | (5,1) | 上 | 793 |

右へ到着した時点ですでに上を向く。常に「今の移動ベクトルから向きを決める」というアプリ側の方式ではここが違う。これは障害物のない区間の例であり、迂回時には別の分岐がある。

## 表示回数と営業更新は一致しない

通常ループ末尾 `0x8005D4B0` 以降には、次の順番がある。

1. 補助更新3FF00、描画18A5C。
2. 描画後の入力スナップショット `0x800CD9CC` が0なら、もう一度描画18A5C。
3. その分岐内で一時停止値 `0x800CD7F4` が0なら、営業更新23438。

入力割込み1310Cと更新13DDCの接続も確認した。13DDCは入力の新旧から押し始めビットを計算し、CD9CCを新しいスナップショットへ更新する。したがって、最初の描画後にも入力が押されたままなら、この末尾から営業更新へ入らない。2回目の描画中に入力が変わった場合は、この入力ゲートをもう一度評価せず先へ進む。

描画関数は `0x800193B8` で引数0のVSync関数89CA4を呼ぶ。しかし、これだけで実際の固定FPSや一律の歩行ピクセル毎秒は確定しない。通知・音声ラッパー内の追加描画も既知であり、描画回数と営業時計を直接同一視しない。今回の成果は条件と呼出し順で、実機の速度測定ではない。
