# 実保存ペイロードの原命令再照合（2026-11-03）

## 結果

r2 ZIP内の2本の実保存ペイロードを用い、原6B81Cの生成、6BC40の復元、
5188Cの受理判定（内部で6DB4Cを実行）を限定MIPSインタプリタで再実行した。
これは既存の保存形式解析を、新たに復旧した別の実行手段で照合し直したものである。
新規にゲーム全体の保存・ロード互換性を証明したという意味ではない。

| 対象 | 実行数 | 確認内容 |
|---|---:|---|
| 生成6B81C | 2 | 元ペイロード104364バイトと完全一致、37元領域と乱数を保存 |
| 復元6BC40 | 2 | 故意に壊した37領域を原ペイロードから全バイト復元 |
| 受理5188C | 10 | 各元データ＋3種類の1ビット破損＋加算値を保つ入替 |
| 不正チェックサムの直接復元6BC40 | 2 | 呼出側の受理判定を迂回すると、そのまま37領域をコピー |

## 原の受理判定

2本とも次の結果になった。0はこの受理関数の受理、-1は拒否である。

| ペイロード | 原関数の戻り値 |
|---|---:|
| 保存されていた元データ | 0 |
| 保存フィールド+0x3Cの1ビット破損 | -1 |
| 余白+3の1ビット破損 | -1 |
| チェックサム欄の1ビット破損 | -1 |
| 2バイトの入替（加算値不変） | 0 |

余白も加算対象である。一方、値を入れ替えると加算値は保たれるため、このチェックだけでは識別できない。
入替で受理されたデータの内容がゲーム上も妥当であると保証したわけではない。
入替位置・変更前後の値・全ペイロードSHA-256をresults.jsonに記録した。
元のペイロードはGitに保存済みr2 ZIPに含まれ、変更例は記録されたパッチから全バイト再構成できる。

6BC40自体にはこの受理判定がないことも再照合した。
したがって、保存を扱う実装で復元関数だけを呼び出すことと、
原ゲームの受理判定を通すことは区別する必要がある。
今回、不正データを原ゲームの通常UIからロードできたという意味ではない。
