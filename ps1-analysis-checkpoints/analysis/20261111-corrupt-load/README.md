# 営業画面からの破損セーブ読込み・復帰

2026-11-11。原EXEと通常営業の main-17（時計17760、累積8888更新）を復元し、前回はチェックサム関数単体で調べた3枚の変更カードを、営業中の実入力から原メニュー・原カード読込みへ接続した。

## 確認結果

| 入力 | 原チェックサム | 原デコード | 復帰時計 | 自社資金 |
|---|---:|---:|---:|---:|
| 本文1ビット変更 | -1・拒否 | 0回 | 17766 | 99,005,641 |
| チェックサム1ビット変更 | -1・拒否 | 0回 | 17766 | 99,005,641 |
| 合計を保つ2バイト交換 | 0・受理 | 1回・37領域一致 | 17646 | 99,005,440 |

全3条件で、原読込関数 `8007AB2C` は128バイト×892回の本文読込を完走した。3条件合計2676転送。ゲーム側の保存・読込・チェックサム命令やメニューの戻り値は書き換えていない。ディレクトリXORが正常でも、本文の加算値が異なれば原ゲームは拒否する。

拒否後は読込確認画面を継続し、×入力で取消し、設定画面に戻り、START入力で設定を終了して営業へ戻る。`80051524` の試行直前・直後で保存対象37領域がすべて同一だった。デコーダー `8006BC40` は呼ばれていない。比較した4営業ループのうち最初のメニュー処理は時計17760、残り3更新で17766となる。

合計を保った交換は、保存ファイルの先頭データと自社資金の下位バイトを交換した既存試験入力である。原ゲームはこのデータを受理して37領域に復元し、保存時の時計17640から営業を再開した。資金は99,005,641から201小さい99,005,440になる。これは原作の加算チェックサムと読込み経路の挙動であり、不正値全般の安全性を示さない。

## 検証と再現

[results.json](results.json) は、原UI経路、原読込み回数、原チェックサム・確認画面の戻り値、37領域の保全、原デコード到達、復帰時計・資金をまとめた別の監査である。各条件フォルダーには完全な比較記録、生カード、読込ファイル、物理転送対応、CPU再開RAM・メタデータを保持する。原命令の逆アセンブルとハッシュは `instruction-source.json` と3本の `.asm` にある。

`restore-latest.py` で復元した `algorithm-analysis` を `ALGO` とする。main-17がまだ配置されていない場合は、`20261105-card-image/evidence/source/opened-snapshots-20261028/` の main-17 のJSONとRAMを配置する。前回の `raw_card.py`、原カード入力3枚、native-file参照コード、native-title-card-chain.pyもGit内の相対参照で使う。

```sh
python play-corrupt.py ALGO payload-bit-flip
python play-corrupt.py ALGO checksum-bit-flip
python play-corrupt.py ALGO byte-swap-preserving-sum
python render-messages.py ALGO
python audit.py
```

最初の試行では、エラー後にもう一度設定選択関数へ戻るため入力列が不足した。次の試行では設定終了を×と想定したため入力を使い切った。原 `8004F54C` 以降がSTARTビット `0x800` を調べていることを原命令で確認し、入力を修正した。失敗ログを `development-*.log` に残した。ゲーム側を変更して成功扱いにしたものではない。

## 範囲

BIOSファイル・カードイベント・物理ブロック割当、SDK/GPU/SPU/IRQ等の外部境界は前回までのモデルである。実BIOS・SIO通信・実機の描画や音を検証したものではない。比較ペアはUnicornと原子関数を共有する。この3枝は意図的にカードを変更した診断であり、通常営業の累積更新や最新再開点に加算しない。mainとゲーム本体の変更は行っていない。
