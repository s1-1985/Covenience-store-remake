# 季節・来店判定・追加購買データの接続

2026-11-13。SLPS_007.82の元ディスクを静的解析した。今回の中心は、既知の季節関数を商品名・144購買型・入店時の初期化へ接続し、スマホ版で使えるデータにまとめることである。営業シミュレーションの長期延長や、既存の季節関数の再検証は行っていない。

対象は原表の有効な144購買型。主目的は各レコードの+8、追加は+9～+11。枠数は人数・販売数・来店頻度ではない。

温かい飲料・おでん・中華まんは追加枠にだけ存在する。したがって、この原表と通常の来店先選択では、これらの商品だけを在庫に持つ店を主目的として来店する購買型は存在しない。実際の店への来店には主目的の品揃え、距離、営業時間、評判など別の条件も必要であり、「季節商品を置けばそれだけで新規来客が増える」という独立した集客量を追加しない。

## 季節コードの意味と適用箇所

| コード | 優先期：戻り値1 | 逆期：抽選で戻り値2 | その他：戻り値0 |
|---|---|---|---|
| 0 | なし | なし | 全月 |
| 1 | 6・7・8月 | 12・1・2月 | 3～5・9～11月 |
| 2 | 12・1・2月 | 6・7・8月 | 3～5・9～11月 |

原関数 `0x80027328` は商品IDが0～26以外なら2を返す。逆期は `rand()%100+1<=90` で2、それ以外は0。優先期は乱数を使わず1を返す。季節コード0も乱数を使わず0である。

この数式自体は以前の `extended.py` に復元済み。今回の追加は、元命令の直接呼出し2箇所と、その前後のデータの流れを結びつけた点にある。

| 呼出し元命令 | 場面 | 季節関数の結果の扱い |
|---|---|---|
| `0x80026680` | 町の建物・購買型から来店候補を割り当てる処理 | 主目的の商品を判定。2なら候補を飛ばす。0・1ともその後の曜日別割合判定へ進む |
| `0x80034268` | 店内で新しく追加の商品候補を選ぶ処理 | 2なら飛ばす。1なら集中度判定を省略。0なら集中度による抽選を行う |

直接呼出しの走査範囲は `0x80010000` から `0x70000` バイト。直接 `jal` の列挙であり、間接呼出しが絶対にないという証明ではない。

### 主目的の商品には店内判定を二重に掛けない

入店処理 `0x800319AC` の成功分岐は、購買型+8の商品を客レコード+1へ直接入れる。店内購入処理 `0x800340FC` は、客+1がすでに商品を持っている場合、追加候補選択のブロックを通らず目的地探索へ進む。

したがって、通常の主目的商品は来店候補側の判定を受けた後、店内で同じ季節・集中度抽選を重ねない。追加商品は、客+1が-1になって新候補が選ばれたタイミングだけ判定する。移動中や毎描画フレームで抽選し直さない。

### 追加商品の集中度

購買型+20の符号付き値をthresholdとする。季節関数の結果が0なら、新たな乱数を1回使い、`rand()%100+1<=threshold` のときその商品を飛ばす。優先期の結果1では、この抽選自体を行わない。

例えば購買型0は主目的がパン類、追加が冷たい飲料、集中度10である。追加の冷たい飲料を選ぶ場面に到達すると、6～8月は季節・集中度による除外を受けない。12～2月はまず逆期の除外抽選があり、通過した場合だけ集中度10の除外抽選へ進む。これらの通過は購入完了を意味しない。在庫、目的地、所持金、購入動作などが後に続く。

乱数は15ビットLCGの出力を100で剰余しており、1～100が完全に等頻度になる方式ではない。さらに連続する乱数は同じLCGの系列である。端数を無視した独立確率の掛算を「原版の正確な購入率」として保存せず、分岐と乱数呼出し順を橋渡しJSONに保存した。

### 表に指定があっても追加購入できない2枠

購買型108・109は商品枠2にイベント商品24を持つが、集中度が100。イベント商品の季節コードは0なので季節関数は常に0を返し、続く `roll<=100` が必ず成立する。この2枠は、元表を用いる通常の追加候補選択では必ず除外される。

これはデータと分岐の接続によって今回判明した到達制限である。商品表にあるという理由で買わせる補正を追加しない。既に選択済みの商品を外から書き換えた場合など、別の入力経路まで不可能と証明したものではない。`extra-candidate-exclusions.json` に該当枠と条件を保存した。

## 月別の天候閾値と曜日選択

元の月別天候閾値 `0x800994B0`（12×4整数）と、カレンダー `0x80099D88`（12×4バイト）も抽出した。

天候値は0、1～19、20～39、40～59、60～79の5群で生成される。最初の抽選値が4閾値のどこに入るかで群を選び、0群以外は追加の乱数で群内の値を決める。これらに「晴れ」「豪雨」といった名称は今回割り当てていない。

通常の来店割当では `購買型+13+20 < 天候値` なら除外する。その後、主目的商品の季節判定と、購買型+21または+22の割合判定へ進む。カレンダー0なら+21、1なら+22。特定のバイパスフラグが有効な経路ではこの一連の除外を省略するため、通常経路の規則を無条件で全経路へ適用しない。

## 現金について進んだ範囲

前回、商品26は現金、什器43・44はキャッシュディスペンサーと特定した。今回は店舗走査 `0x80023F48` の `0x800240A8` で、画像から商品26と判定された什器が価格評価の加算数・合計から除外されることを名称に接続した。基準価格0の商品を単に平均へ加え、店の価格評価を下げる実装にしない。

什器43・44は下位カテゴリー5であり、即時決済判定 `0x800360A0` の対象カテゴリー2・3・5に入る。ただし、それは「仮にその什器で購買が発生すれば即時決済扱いになる」という分類にとどまる。

144購買型の全4商品枠には現金指定がなく、追った通常の入店・商品選択・決済経路から所持金不足時のATMへの切替は確認できなかった。**現金引出しや手数料の発生は引き続き未確定**。コード全体に存在しないとは結論しない。
