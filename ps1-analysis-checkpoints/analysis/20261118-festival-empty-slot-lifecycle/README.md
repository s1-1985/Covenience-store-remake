2026-11-18 JST。R02の未確認範囲だった客ハンドラ以後を、既存の初期TOWN0001入力に原処理をつないで調べた。**［確実］限定入力では、人数0のまま客枠が活動し、所持金500円・商品4が設定され、位置の占有情報まで書き込まれた。** 祭りを普通にプレイして起きた記録ではない。

## 既知と新規

既知：[前回の客状態分岐](../20261117-festival-customer-state-data/README.md)は、原2619Cの範囲外需要144の加算が店2の先頭客状態へ重なること、状態1～5のどのハンドラへ分岐するかを確認していた。そこでハンドラの実行前に停止していた。通常の客生成・入店・位置反映の単独モデルもr2に保存済みである。

今回の追加は次の3件の接続であり、新しい通常ゲーム規則を3個発見したという意味ではない。

## 1. 実際に入店処理へ進む

既存の原初期マップ読込とランタイム表変換を使用。活動中のライバル1・2の営業時間を診断用に0へ変更し、月8・期4・時0・分0、祭りスイッチ1、乱数seed2を指定した。先頭客枠の状態や他のフィールドは注入せず、初期の全0レコードをそのまま使った。

原2619Cから、原26868が店2の先頭客枠へ16ビット値1を書いた。レコードは `01` に続いて31バイトの0となり、通常の客生成初期化は起きていない。

店2を選択し、元の主更新23670～238ACで作業グリッドと開店処理を準備した。新規マップの診断RAMから開始するため、再構築フラグ1398BC=1を指定した。準備後、通常生成を除いた原の後半客ループ32814～330E4を3回だけ実行した。

| 後半ループ | 実ハンドラ | 後の状態 | 位置 | 所持金 | 人数 |
|---:|---|---:|---|---:|---:|
| 1 | 入店 | 1 | (0,0,0) | 0 | 0 |
| 2 | 入店 | 2 | (0,1,3) | 500 | 0 |
| 3 | 購買状態2 | 2 | (0,0,0) | 500 | 0 |

最初の入店試行は失敗し、次の試行で成功した。これは一般的な入店待ち時間の上限ではない。時計自体は初期値0のまま、プロフィール0の滞在120を加えて期限120になる。暦だけ祭り条件を与えた診断であり、自然経過した祭り日時とは扱わない。

## 2. 通常の人数割当を通っていない

上記3回を通じ、人数+30、店の累積来客+1188、原店舗集計+20はすべて0だった。後半ループ中、通常144プロフィールの需要配列も変わらなかった。

比較には、同じ準備後RAMから先頭枠を全0へ戻し、seed0で原319ACの通常生成を1回だけ通した。原32814の後半ループ直前で停止し、入店位置処理は含めていない。

| 項目 | 範囲外書込みで活動した枠 | 通常生成直後の対照 |
|---|---:|---:|
| プロフィール番号 | 0（初期値の残存） | 41（原選択） |
| 人数 | 0 | 1 |
| 累積来客 | 0 | 1 |
| 店舗集計内人数 | 0 | 1 |
| 目的地 | (0,0,0) | (−1,−1,−1) |
| 経路10バイト | 全0 | 全FF |
| 容姿番号 | 0（初期値の残存） | 3（原選択） |

通常生成のプロフィール41の需要は1減った。この対照は「同じプロフィールで1人分を再現した」実験ではない。異常経路で欠ける人数・経路初期化・集計を比較するための、原処理の正常な一例である。

主更新全体では異常枠とは別に通常の客が生成される可能性がある。今回、後半ループだけを隔離しているため、「祭りの日には全店の来客数が増えない」という結論にはしない。

## 3. 人数0でも占有値が書かれる

成功した入店の後、目的地と経路は通常生成が置くFFへ変わらず0のままだった。3回目のループでは原340FCを実行し、既存の目標・経路から位置を更新した。原の共通位置反映は人数0を理由にスキップしない。

- 2回目：原32E40が旧(0,0)を0にし、原330A0が(0,1)へ占有値2633728を書いた。2688バイトの床・占有領域の変化は2バイト。
- 3回目：同じ原処理が旧(0,1)を消し、(0,0)へ占有値2625536を書いた。同領域の変化は4バイト。

客としての占有データが存在することと、描画した画面で見えたことは別である。描画・動画は確認していない。今回の所持金500は入店時の予算設定であり、ATM出金の証拠ではない。自社・ライバル資金はいずれも変化せず、購入・会計完了・売上発生までは確認していない。店+1の値も0を維持したため、占有反映が必ず汚れフラグを立てるとも扱わない。
