# 客の待機断念と全配属店員の能力低下

2026-11-17 JST。店員word16の追跡から、以前未接続だった能力成長モード-1の発生元を原コードへ接続した。CPU営業更新は0回。**word16の用途は未確定のまま保存し、解明済みへ数えない。**

## 今回の追加

原0x8003AA58への直接呼出し4箇所を原EXEのコード範囲から抽出し、モード-1が客の待機断念処理0x80035D58から呼ばれることを特定した。以前の独立モデルにあった減少式を、購買・レジ待ちの呼出し元、対象全員、会計処理へ接続したものである。

| 原呼出し位置 | 成長モード | 親処理 |
|---|---:|---|
| 0x80035F9C | -1 | 客の待機断念 |
| 0x80037534 | 2 | 補充完了 |
| 0x8003771C | 4 | 清掃成功 |
| 0x80038868 | 1 | レジサービス成功 |

これは0x80010000～0x80097FFF内の直接JAL命令の一覧であり、間接呼出しを含めた全プログラムの証明ではない。[抽出一覧](growth-direct-callers.json)を参照。

## 客が断念する条件

客の待機値は購買型+17から客+0x1Cへコピーされる。原144型の初期値は10～100で、[全144型](profile-patience.json)に値と分布を保存した。秒数への独自換算はしない。

待機処理は、毎回最初に1～100の抽選値Rを取る。強制指定があれば待機値を0へする。通常指定で待機値が正なら、追加の乱数で`rand()&3==0`のときだけ1減らす。まだ正なら続行を返し、以下の断念処理へは入らない。

| 呼出し元 | 指定 | 発生する場面 |
|---|---:|---|
| 0x8003501C | 通常 | 買物中の移動で回避移動も失敗した後 |
| 0x800351D0 | 強制 | 買物額が残っており、レジ目的地を設定できない |
| 0x800352AC | 通常 | レジ位置でサービス処理が失敗側を返した後 |
| 0x8003567C | 通常 | レジへ向かう移動で回避移動も失敗した後 |

従って単に「レジが混んだら必ず能力が下がる」という規則ではない。通常は待機値が残る間にこの分岐へ入らず、強制断念だけがその待機を省略する。

## 最大3人に同じ抽選結果を適用

断念が成立し、最初のRが3の倍数なら、店の3つの配属欄DD8/DDＡ/DDＣを順に走査する。-1の空き枠だけ飛ばし、店長を含む各人へモード-1を適用する。

| 能力 | 各人への変更 |
|---|---|
| レジ+0x1E | 2以上なら1減少 |
| 補充+0x1F | 2以上なら1減少 |
| 清掃+0x21 | 2以上なら1減少 |
| 警備+0x22 | 2以上なら1減少 |
| 接客+0x20 | このモードでは変更しない |

基本能力やword16も、この減少分岐の更新対象ではない。0や1をさらに減らさない。対象者を1人抽選したり、能力ごとに別の成功抽選を追加したりしない。

各人の成長処理の入口ではモード-1でも乱数を1回消費するが、その値は減少するかどうかの判定には使わない。能力が全て下限でもこの入口の乱数は消費される。

同じRが10の倍数で店のC68が6以上なら、C68も1減る。この分岐での下限は5。C6Cの知名度へ減算する処理ではない。

| R=1～100のうち | 該当する値の数 |
|---|---:|
| 店員能力低下 | 33 |
| C68の減少抽選 | 10 |
| 両方 | 3（30・60・90） |

[100値の対応表](shared-roll-table.json)は元式の厳密な対応で、乱数頻度を実測した表ではない。2つの独立抽選に置き換えると両者の関係と後続乱数が変わる。

## 断念時の買物額は売上へ加算される

断念側は通知フラグ0x20を立て、買物額+0x0Aが非0なら`買物額×客グループ人数+0x1E`を原1CA7Cのモード1へ渡す。このモードは**店の売上D98と、その所有会社の現金へ加算**する。その後、客の買物額を0にする。

この分岐自体には客の所持金を新たに減らす命令はない。名前や直感から返金・マイナス売上・全商品返品へ置き換えない。画面でどう見えるかの新規観測ではなく、原数値処理の読取りである。

断念件数の欄12E1も、符号付き値が127未満なら1増える。1回の呼出し単位の処理であり、同じ客への重複呼出しが全経路で絶対にないとまで主張しない。

## word16は未解明

全4マップ×35人を元データから再抽出した。139件は0、唯一TOWNPSの店員27は69120である。この例外値と所有0xFFFF自体は以前の全レコード抽出にも保存済みで、今回の新発見とは数えない。

原ローダーは保存54バイトレコードの+13から4バイトを実行時60バイトレコードの+16へコピーする。しかし69120を期間・経験・退職期限などと命名するだけの使用経路はまだ特定できていない。値と所有フラグが同じ人物にあることは、因果関係の証拠にならない。[140件の原値](word16-source-values.json)を保存し、R07を未解決のままとする。
