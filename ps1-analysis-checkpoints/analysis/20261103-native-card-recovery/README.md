## ファイル名の判定

名前は原EXEのポインタ800B9C04が参照する80010CD4に
BISLPS-00782CONV + NULとして存在する。
7B7C0は17バイトを比較した後、候補側+16がNULであることも確認し、一致時0、不一致時1を返す。
17バイトの各位置について、元と異なる255値、計4335例を原命令で実行した。
全例が不一致となった。+17以後だけが異なる3例は一致し、
+16が非NULで両者の17バイトが等しい3例も不一致となった。

## 誤った内部名を付けた場合

| ディレクトリ | 引数0（保存側） | 引数1（読込側） |
|---|---:|---:|
| 空 | 2 | 2 |
| 他ファイル1ブロック | 2 | 2 |
| 他ファイル2ブロック | 1 | 2 |
| 14ブロック、名前TOWN0001 | 1 | 2 |
| 14ブロック、正しい名前 | 0 | 0 |

0は対象ファイルが見つかった分岐であり、実データの読込みまで成功したことを意味しない。
同じ状態番号2でも、呼び出した側の文脈を分ける必要がある。
通常ディレクトリ40例で戻り値と800CD820の状態バイトを比較し、一致した。
検索パターンは原の文字列コピーを通したbu00:*である。

## 3段階の照会と再試行

原7B920は、初回照会info → 低位のload → 再照会postという経路を持つ。
以下の番号はそのイベント群の探索順0/1/2/3であり、全層共通のエラー番号と決め付けない。

全段階で一定の応答を与える64組を実行した結果：

| 初回info | post | 最終状態（対象ファイルなし） | 呼出回数 info / load / post |
|---|---|---:|---|
| 1 | 任意 | 5 | 3 / 0 / 0 |
| 2 | 任意 | 4 | 30 / 0 / 0 |
| 0 または3 | 0 | 2 | 1 / 1 / 1 |
| 0 または3 | 1 | 5 | 1 / 1 / 3 |
| 0 または3 | 2 | 4 | 10 / 10 / 30 |
| 0 または3 | 3 | 3 | 1 / 1 / 1 |

この表ではload側の4種類の通知で最終結果は変わらなかった。
低位loadの通知を受けた直後に、その結果だけで最終エラーを返す処理ではなく、
続くpostの結果を使うためである。
info=3も即座に失敗するとは限らず、loadとpostを経て成功側へ進む例がある。
実カードの通知が独立に自由な組合せで発生する、という主張ではない。

2回待ち応答後に成功、3回待ち応答後に外側を再試行して成功、という変化する応答3例も原命令で確認した。
いずれかの段階で完了通知を届けない3例は、各20000命令の上限まで戻らなかった。
これは待ち続けることの有限区間観測であり、数学的な永久停止の証明や成功扱いではない。
