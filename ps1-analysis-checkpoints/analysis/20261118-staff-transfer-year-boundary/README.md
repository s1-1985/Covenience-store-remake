## 配属確定を一つの共通処理にまとめない

既存の[同一店内配属確定70F48](../20261117-staff-assignment-lifecycle-data/README.md)では、枠が変わった旧人物の解除時に体力を最大へ戻し、再配属で経験を1増やした。

一方、原72774の店舗間異動も解除→再配属の二巡であるが、解除時の体力回復と再配属時の経験加算がない。今回、人物0と3を現在体力1、経験10と13に設定した2店で交換し、その値が維持されることを確認した。名前・能力・word16も持ち越す。両関数を同じ人事操作だからと共通化して回復・経験加算まで揃えると、確認済みの原挙動と異なる。

この72774の単独式は既保存の独立モデル`staff_transfer_binding.py`にもある。今回の追加根拠は70F48との相違、原の休憩位置設定まで含めた確認、次の取消経路との接続であり、関数自体の新発見とは扱わない。

## 店長不足エラー後の取消に復元はない

最初の配属は店0［0,1,2］、店1［3,4,−1］。原の交換処理72DBCで店0枠0と店1枠2を選ぶと、仮配属は［−1,1,2］／［3,4,0］になる。この段階では人物・店舗の実データは変化しない。

次に原72774で確定すると、実配属・人物の所属・画像・休憩位置を書き換えた後、72D0C以降で店長枠を調べ、店0が不足しているため1を返す。この時点で書込みは済んでいる。戻り値1は「一切変更せず拒否した」という意味ではない。

親の原コードでは、7220C～72298が戻り値を受けて不足店舗のメッセージを呼び、7229Cで入力処理へ戻る。取消は722E0の0x40判定→音声65040→722F4→7275Cの復帰であり、配属を戻すコピー処理を含まない。今回実行したのは音声後の取消末尾で、人物2100バイトと2店10160バイトは確定失敗後の値を維持した。

［確実］原交換と確定の合成により、店長不足エラーでも書込みが残ること、およびこの取消末尾が復元しないことを確認した。画面全体を再現していないため、通常操作で必ず店舗が壊れるという結論や、以後の影響の断定はしない。先にバリデーションして何も変更しない実装とは、この確認範囲で差がある。
