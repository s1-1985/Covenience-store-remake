# 祭り迂回後の購買型144：店舗選択と客レコードの境界

2026-11-16 JST。原ディスクから、通常フィルターを祭りが迂回した後の店舗選択・需要書込み・客生成の境界を解析した。CPU営業更新は0回。**R02は範囲を絞ったが、未解決を維持する。**

## 今回分かったこと

1. **初期4マップのライバル11店舗は全て、この不正な購買型を営業時間の判定で除外する。** 初期の営業時間番号は全店2。そのとき誤参照先の値は0なので、祭りで通常フィルターを飛ばしてもその店舗へは需要を割り当てない。これは原初期配置の結論であり、開業後・買収後・設定変更後の全店を保証するものではない。
2. 全7営業時間設定を原データと接続した。番号0・3・5では営業時間の誤参照値が非0で、この条件だけなら通り得る。後段の在庫値・到達距離・店舗評価等も必要なので、必ず店舗が選ばれるという意味ではない。
3. 店舗が選ばれた場合、需要144の加算先は**店レコード+0xF04、先頭客スロットの状態バイトと次のバイト**に重なる。通常需要0～143の合計には入らない。
4. 通常の客生成では候補番号を144で折り返すため、購買型144を正規の客として生成しない。ただし、上記の条件付き書込みが既存スロットへ与える間接的な影響までは未確定である。

## 人物データではなく文字列を読んでいる

購買型は0～143の144種類。144の計算上のアドレス0x800A1750は、以前の解析で「赤い女子大生」の文字列と分かっている。今回その文字バイトを、店舗選択が実際に使う符号付きの値へ接続した。

| 誤って人物欄として読む位置 | 読む値 | 店舗選択への影響 |
|---|---:|---|
| +2 | -126 | 営業時間行の126バイト手前を読む |
| +8 | -111 | 在庫配列の範囲外を読む |
| +12 | 0 | 到達範囲20の区分として扱う |
| +14～+16 | 全て0 | 価格・距離・防犯の加重項は0 |

これは架空の145人目の客の能力値ではない。所持金や商品の正規データとしてAndroidへ移植しない。[隣接文字列と誤参照値](adjacent-text-operands.json)に原バイトを保存した。

## 営業時間の判定

原0x80026C14でprofile+2を符号付きで読み、`0x80099DE5 + 45×営業時間番号 -126`を参照する。原0x80026C34は0以外なら通すため、負値-128も通過側である。

| 営業時間番号 | 誤参照先 | 原符号付き値 | この条件 |
|---:|---|---:|---|
| 0 | 0x80099D67 | -128 | 通過し得る |
| 1 | 0x80099D94 | 0 | 除外 |
| 2 | 0x80099DC1 | 0 | 除外 |
| 3 | 0x80099DEE | 1 | 通過し得る |
| 4 | 0x80099E1B | 0 | 除外 |
| 5 | 0x80099E48 | 1 | 通過し得る |
| 6 | 0x80099E75 | 0 | 除外 |

各番号の正常な営業フラグを解釈した表ではない。全て、文字列由来の負の添字による行外参照である。[営業時間の原参照](schedule-aliases.json)、[初期11店舗の設定](initial-store-boundary.json)を参照。

## 在庫参照と需要書込みは別の境界

店舗要約は0x800CE65Cから168バイト刻み。在庫判定は要約+0x2C+4×商品番号であり、-111を与えると当該要約の400バイト前になる。

| 店スロット | 参照する位置 |
|---|---|
| 0・1 | 要約配列より前の領域。値の意味は未特定 |
| 2 | 店舗順序配列の先頭0x800CE61C |
| 3～9 | 3スロット前の店の要約内、商品15の在庫欄 |

原0x80026CF0はこの誤参照した32ビット値が正かを判定する。実際の値は営業中のメモリ状態に依存するので、アドレス対応だけで自然発生を断定しない。[全10店スロットの対応](stock-aliases.json)を保存した。

店舗選択が成功した後の原0x80026868は`店+0xDE4+2×144 = 店+0xF04`へ16ビット加算値を書き込む。先頭客レコードと重なるため、**「生成処理が144を選ばないから全く影響しない」とは結論できない**。自然な祭りでこの書込みが実際に成立する状態や、その後の画面・購買・会計への影響は未観測である。

通常の客生成は0x80031B50～0x80031B5Cで番号144以上を0へ戻し、0x80031E78で選択番号を客へ保存する。したがって正規生成の候補は0～143。144の所持金・商品・会計仕様を新たに作る根拠はない。[境界仕様](boundary-rules.json)に条件と制限を記録した。

## Androidへの接続

人口計算は元のmix136の7人を保持する。一方、需要や購買では祭り中も`0 <= profile < 144`を確かめてから配列へアクセスする。隣接文字列や他店の在庫を客データとして扱わず、客レコードを需要の保存先としても使わない。

今回の成果は原コードが何を参照するかの解読であり、原作の不正メモリ参照を移植する指示ではない。R02は「変更後営業時間・営業中の値を含む自然到達と、先頭客への間接影響」を残件とする。台帳は7件中1件解明・6件未解決を維持する。
