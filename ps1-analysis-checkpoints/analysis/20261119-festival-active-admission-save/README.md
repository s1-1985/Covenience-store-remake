## 1. 通常生成済みの客も入店初期化を飛ばされる

［確実］TOWN0001を原ロード・原什器表変換で準備し、原の需要計算・店準備・通常客生成を通すと、店2の先頭へプロフィール60・人数2の入店待ち客が作られた。**客レコードのどのバイトも直接設定・コピーしていない**。営業時間0、時計44640、乱数種などは指定条件である。

この同一RAMから、祭りフラグ0/1を指定して原需要`2619C`を実行し、それぞれ元の客ループを1回だけ通した。

祭り側は原`26868`が先頭2バイトへ値2を書いた。状態以外の31バイトは需要前と同じであり、予算・位置・期限を設定する入店処理が呼ばれなくなる。ループ後も目的地・経路はFFのまま。**人数0の空き枠だけに起きる異常ではない**。

店の累計人数・派生現在人数は両側とも2。この試験は入店待ちの生成済み客を対象とし、既に棚で商品を取った客やレジ待ち客まで検証したものではない。元の需要分岐・通常生成・入店式自体は既知であり、新規点はそれらを同じレコードで接続し、入店初期化の欠落と具体的な前後値を確認したことである。永久停止や通常発生頻度は主張しない。

## 2. 祭りフラグは次の2分更新で解除されない

［確実］上記の客がいるRAMに対し、元の暦計算で年1・月8・期4・0:00を作り、**祭り演出から戻った直後**の`29444`から原決算末尾を通した。祭りフラグ1は原`2944C`が書く。演出自体・そこまでの自然営業は実行していない。

その後、原時計プロローグで44640→44642と進め、原暦計算・原決算を呼ぶ。暦は[1,8,4,0,2]。決算は分0条件を満たさず復帰し、フラグ1を保持した。次の解除端点は、指定した時計46078から原時計で46080へ進めた[1,9,1,0,0]で確認。原`29398`がフラグ0へ戻したところで停止している。

これは決算の時間条件と保存経路の接続であり、1日全体や全イベントを連続実行した試験ではない。他の読込・営業開始処理による解除は既知の別経路として残る。

## 3. 非境界時刻の保存→復元→タイトル再集計でも状態が変わる

時計44642・フラグ1のまま、元のメニュー**選択後**`60034`へ選択結果5を与えて入る。元の分岐表`10B40`→`601F0`→共通カード操作`62484`→原エンコーダ`6B81C`を通し、カード画面`4EEB8`の呼出し前で止めた。この区間は祭りフラグを解除せず、ペイロード時計+30=44642・祭り+14EC8=1を生成する。104364バイトのチェックサムも一致した。

その同一ペイロードを原デコーダで復元すると、先頭客は状態1・プロフィール60・人数2・未設定の予算/位置を保つ。乱数種2を**保存外の指定条件として**与え、原タイトル読込末尾`12D44..12D68`を実行すると、`26868`が状態1→2へ変更し、残り31バイトを保持した。

［確実］したがって、今回のタイトル側書込みは保存時計が0分ちょうどであることを必要としない。通常営業側の需要再計算は0時0分の条件付きだが、タイトル再集計はその条件を通さず呼ぶ。前回までの44640限定結果を44642の保存データへ接続した。

［未確認］通常のボタン操作から選択結果5を得る過程、通知が表示中の入力制限、メモリーカードの実書込み成功・読込画面全体、当該条件へ通常営業だけで到達する過程は未実行。**メニュー選択結果を指定した限定入口を、通常UIを通した保存成功と表現しない**。乱数種もセーブから復元された値ではない。
