# 店員35人の接客値と休憩復帰・清掃選択の時計位相
日付：2026-11-17 JST。対象：初代PS版 SLPS_00782 の通常店員処理。

今回の追加は、既知の個別条件を原35人・4マップの配属と結び、仕事選択が可能な時計位相を数値化した点である。原CPUの営業継続やAPK作成は行っていない。

## 新たに接続した結果

- 主更新 0x80023454 は時計を2加算する。満回復して状態0で休憩中の店員は、`(clock>>>1)%3 == staff_slot` のときだけ仕事を再選択する（0x80036F38–36F74）。
- 清掃候補選択 0x80039618 は `clock%100 >= 100-接客` を要求する。読み出すのは清掃能力+0x21ではなく、原名称「接客」の+0x20である。
- この2条件を同時に満たす位相は時計300、主更新150回で一巡する。各配属枠にはその間50回の再選択位相がある。偶数時計系列では清掃時間条件を通る位相数が `floor(接客/2)`、奇数系列では `ceil(接客/2)` となる。
- 原35人の初期接客値は8～19。偶数系列では各枠50回中4～9回、奇数系列では4～10回。接客値が奇数の19人では、時計の偶奇で通過位相数が1回変わる。
- 4マップ・初期11店舗の配属枠33個には、実際の店員参照が29件、空きが4件ある。29件はいずれも保存初期状態0。各人・各枠の位相表をJSONへ保存した。初期位置等の別条件を満たす前から仕事が始まるという意味ではない。

## 仕事選択の文脈

原呼出し順は、レジ人数等の前置判定37F78→レジ候補38AD8→補充候補38D6C→清掃候補39618。清掃の時間条件が通っても、先のレジ・補充が選ばれれば清掃へ進まない。候補、汚れ、経路等の条件も別に必要である。

休憩中の再選択ですべて失敗すると状態0を維持する（370D0→370E4）。一方、活動中・目標なし・体力ありの分岐では、最後に休憩先39428を探し、状態3へ移る（37364–3737C）。この2分岐を同一の常時タスク選択ループへまとめると原処理との差が生じる。既存目標を保持している間の進行にも、この休憩復帰用の3枠制限を無条件に掛けてはならない。

このパッケージは清掃の時間条件を原命令で扱う。レジ候補ヘルパー内部の同様の時間条件については、今回の新規確定事項に含めない。既知の仕事優先順位・休憩条件の再利用と、新しい原能力値との時計位相の接続を区別している。

時計を保存し、更新で2加算して原位相を維持する。休憩満回復分岐と活動中の目標再選択分岐を分け、時計剰余を独立乱数へ置き換えない。接客値の参照先も保持する。実秒、FPS、清掃実行率、作業効率や休憩時間の実測値には換算しない。時計の初期偶奇や途中ロードを仮定せず両系列を出力した。uint32の折返しをまたぐ箇所では、この300周期の単純な延長を使わず元の32bit計算を実行する。
