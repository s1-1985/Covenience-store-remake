# 原ロード呼出しから画像・パレット・有効画素範囲への接続

2026-11-17 JST。画像ロード関数140E8の直接呼出し55箇所を原命令から取り出し、そのうちTIM要求39箇所・31画像を、32枠の転送表・34件の画像名へ対応付けた。さらに転送先の重なりと、53什器のアイコンの実画素範囲を接続した。

**今回の追加は参照箇所と既存抽出物の接続である。14画像でファイル寸法と転送要求寸法が異なること自体は、既存r2アーカイブの台帳に記録済みだった。** 原32画像の転送指定・画素・パレットを独立に照合し直したが、それを新しい画像解読とは数えない。[過去成果との全32対応](prior-evidence-crosscheck.json)を保存した。

[load-callsites.json](load-callsites.json)に原位置・直前2命令の引数・遅延スロットを保存した。走査範囲は80011C00～80097FFF。TIM要求39箇所は、直前の引数設定から画像番号と種別が全て定数に確定した。例えば80011DCCは画像3「SYOP_S00」、80012090は画像6「SHOPTYP1」を種別8で要求する。

| 番号 | 画像 | 専用転送枠 | この走査の直接TIM要求 |
|---:|---|---|---|
| 29 | TOWN_YU1.TIM | あり | 見つからない |

この3枚を「ゲーム全体で未使用」とは断定しない。走査は直接JALと定数引数の接続で、関数全体の到達可能性、計算で作る間接呼出し、実行中のファイル名表変更の不存在まで証明したものではない。EXE内に140E8そのものを格納するリテラル関数ポインターは見つからなかったが、それも間接経路全般の不存在の証明には使わない。

転送表32枠が存在することを、32枚全ての通常ロードを観測した意味に読み替えない。番号29は下記の転送指定検証に含めたが、ロード要求を自然操作で通した結果ではない。

## 元画像の座標を転送先と混同しない

原13F7CはEXEの矩形表を読み、原13EACはその指定矩形と、原855DCで読み取ったTIM内の画素・パレットへのポインターをLoadImageへ渡す。ファイル内に書かれたXYをそのままVRAM上の位置として採用する処理ではない。

32枠全てで画素の転送先XYはTIMヘッダーと異なり、パレットの転送先XYも29枠で異なった。例えば人物画像MAN0のパレットは元ファイル内(0,480)に対し転送先(0,493)。この例自体も以前の人物テクスチャー解析で判明済みであり、今回の31画像への参照接続に再利用した。

[texture-bindings.json](texture-bindings.json)には、画像ID・原ファイルのハッシュ・ビット深度・元寸法・転送先・原呼出し位置・有効画素バイト・パレットを一つの行として保存した。転送表のXと幅は16bit語単位、復号画像の横幅は4bit画像で4倍・8bit画像で2倍となるため、両者を別フィールドにした。

LoadImage境界はGPUへ送信せず、矩形と入力ポインターを記録した。矩形の幅×高さ×2バイトに当たる入力領域について、元ファイルにある範囲の全バイトは一致した。超過部分の診断メモリにはA5を置き、ラッパーが元高さで縮めたり、不足行を新しく0で作ったりしないことを区別した。

**A5は診断用の人工入力であり、原ゲームでその値が表示されるという意味ではない。** 実機のCD読込みのセクターパディング、以前のロード内容、実画面でのUV参照は、この再照合では追っていない。元アーカイブにはセクター境界まで扱った従来の検証もある。今回の64回のGPU境界捕捉を、新たな実機描画確認や不足行の特定として数えない。

## 53什器のアイコンは有効画素の中に収まる

CASE_T00の転送要求は256行だが、元画素は224行。53什器の定義から、アイコン番号と32×32の原矩形を実画素範囲へ接続すると、全て224行以内に収まった。アイコン番号は1～54のうち53件で、最大の54番も行192～223を使う。

[fixture-icon-source-coverage.json](fixture-icon-source-coverage.json)に、全53件の矩形・画素インデックスのハッシュ・原パレットのハッシュ・転送先CLUTを保存した。少なくともこの53アイコンの切出しに、CASE_T00の存在しない行224～255を補う必要はない。

既知だったのはアイコン番号と、追加画像CASE_T01の差分が54番（什器45）に限られること。今回の接続からも追加画像を通常表示へ自動採用する根拠は得られていない。店内什器・商品・全UIの全描画経路まで有効範囲内と証明した結果ではない。

## 同じ転送先を別の画像が使う

32枠を比較すると、画素領域で48組、パレット領域で49組が重なる。[全組合せ](vram-overlaps.json)を保存した。例えばMAN0とTITL0は画素領域(320,0,128,256)とCLUT(0,493)が同じ。KAO01とTITL1も画素領域(320,256,128,256)とCLUT(0,494)を共有する。

これは転送表上の重なりであり、全組が同じ画面で同時に使われるという意味ではない。スマホ版では転送先座標だけを素材の識別子にすると別画像を区別できないため、原ファイルID・ハッシュ・その画像のパレットを組として保持する。[移植用の規則](android-texture-binding-bridge.json)を添付した。

## 再現と保管物

```sh
python analyze-texture-binding.py /path/to/restored-source.zip
```

元ZIPは`archives/20261103-r2/restore.py`で復元する。入力アーカイブとEXEのハッシュを確認し、32個の元TIMをアーカイブから読む。追加2画像は隣の`20261113-disc-data-extraction/source`の原バイトを参照する。Pythonとunicorn 2.1.4を使用。Capstoneは保存用命令列の生成にのみ用いた。

[原命令列](binding-readers.asm)、[最小原バイト範囲](source-ranges.json)、[転送境界の結果](native-upload-results.json)を保存した。GPU境界64回を代用した一方、矩形選択・TIMパース・転送ラッパーの処理は原命令を使用。GPU画素化・15bit色とSTPの最終合成・自然な画面遷移は今回の範囲外。原EXE SHA256は`d6a167a1c9e0fe98d7e44e12968caa489ac3eb7ed3b9e46012a188af8432b1fd`。

本作業は7残件のいずれかを解明したものではなく、別途残っていた画像と使用経路の接続を進めた成果である。管理数は解明1・未解決6を維持する。Android本体とAPKは変更していない。
