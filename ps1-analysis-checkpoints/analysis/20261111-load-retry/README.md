2026-11-11。main-20（時計18960、累積9488更新）から、営業メニュー→設定→読込確認画面へ原コントローラー入力を渡した。原の確認関数 `80051174` を一度開いたまま、その中で読込試行 `80051524` を2回実行する。

各試行で128バイト×892回の原読込みを実行した。1条件1784回、2条件合計3568回。原カードファイルの書込みは0件、終了時の未閉鎖ハンドルは0件。

破損のままでは2回目も確認画面を継続し、×入力→設定へ戻る→STARTで営業に戻る。正常カードへの交換では、同じ確認画面からの2回目が成功し、原 `8006BC40` による37領域の復元を確認した。保存時計17640から3更新し17646となる。いずれも `80051524` の呼出し直前・直後で37領域が変わらず、成功した場合だけその後の呼出し側でデコードされる。

原表示は1回目がID498「セーブデータがこわれています。」、交換後の成功はID489「ロードが終了しました。」となる。[前段の原文字プレビュー](../20261111-corrupt-load/original-load-messages.png) と原呼出し列を照合した。

## 外部入力と検証器の扱い

交換条件では2回目の試行入口で、BIOSファイル側モデルが参照するカードを既存の正常 `.mcr` に交換した。これはカード差替えを表す制御された外部入力であり、ゲームRAM・チェックサム結果・デコーダー完了値を注入したものではない。実カードの抜差し・BIOS/SIO通信や交換タイミングの実機再現までは検証していない。

初期カードは前段の本文1ビット変更カード、交換用は前回 `20261105-card-image/fragmented-0.mcr`。各条件の `operating-menu-save.mcr` に初期の生カードを保持する。`.card-file.bin` は最終的に照合したファイルであり、交換条件では正常カードの内容となる。ハッシュは各 `play-load.json` の `input_image_sha256`、`replacement_image_sha256` にある。

再試行の初版は、保存用監視器がカード状態確認のたびに「最初にエンコードした作業バッファが残る」ことを検査して停止した。1回目の読込み後は作業バッファが読込結果へ変わるため、読込用 `7B1F8(1)` ではこの保存前提を検査しないよう変更した。原ゲームコードの変更はない。失敗ログは `development-save-observer-*.log`、監視器差分は各条件の `save-monitor.patch` に保存する。

独立した読込UI監視器は1回目と2回目のチェックサム期待値を別々に持たせた。原チェックサム関数の戻り値と、原の実呼出し列を照合する。差分は `load-monitor.patch`。生カードの物理転送対応は、交換条件では交換後の試行のみを保持する。両試行の完全な論理I/O列とネイティブ到達記録は `play-load.json` に残る。

## 証拠と再現

[results.json](results.json) と各条件の `play-load.json` に、同じ確認セッション内の2回の到達・戻り値、表示ID、全I/O、37領域保全、デコード、営業復帰を保持する。原命令と比較した親処理・客/従業員・フレームの検証、再開RAM・メタデータ、入力カード、監視器差分も各条件フォルダーに保存した。

`restore-latest.py` でmain-20を復元した `algorithm-analysis` を `ALGO` とし、このフォルダーで実行する。

```sh

python play-retry.py ALGO replace-with-valid
python audit.py
```
