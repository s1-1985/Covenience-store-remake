既存の全人物バッファ・原描画パケット比較を保持し、追加で各描画入口の人物レコード全件を記録した。57回すべて、直前の原構築結果と件数・全レコードが一致した。28個の構築区間では、次の構築まで人物レコードを変えずに描画していた。

店員は実際のID・状態・外見・向き・座標へ対応付けている。同じ姿勢が続く65箇所では、座標とUVが同じだった。12回のマス移動でも、前回確認済みのグリッド座標式と方向画像式に一致した。この営業枝では、中間の座標や足踏み用画像切替を観測していない。

これはAndroid側の再現仕様を検討する根拠であり、「初代全体に一切アニメーションがない」という結論ではない。客や別場面、別関数による演出、実機の表示速度は分けて確認する。

## 時計だけで描画段階を推定しない

時計20,580で異なる人物レコードが描かれた例がある。新しい構築の前に古い構築結果を描く呼出しが含まれるため、同じ時計値でも同じ描画状態とは限らない。`audit.json` は描画の呼出元、構築番号、古いレコードを描いた時計差を記録する。ゲーム時計を見て独自に補間したり、テクスチャーのアニメーションと判断したりしない。

`8014A090` のフレームカウンターはこのSDK境界では0だった。65回はCPU描画関数の呼出し数であり、実画面の65フレーム・60fps・実時間の歩行速度を示さない。

## 再現

`restore-latest.py` の復元環境にmain-24を用意し、以下を実行する。main-24は前回の保存済み圧縮RAMとメタデータを同名で展開すればよい。

```sh
python verify-timeline.py ALGO second-store
python audit-timeline.py
python pack-evidence.py
```

結果と原営業比較のJSONは可逆zlib圧縮で保存する。`evidence-manifest.json` に圧縮前後のサイズ・SHA-256を保持し、`audit-timeline.py` は圧縮結果からも再実行できる。同じ32更新を確認用に再実行したが、先頭を共有する試験を64更新とは数えない。

出典はディスク由来 `SLPS_007.82`（SHA-256 `d6a167a1c9e0fe98d7e44e12968caa489ac3eb7ed3b9e46012a188af8432b1fd`）、main-24（RAM SHA-256 `8574c3d0fa7f98cb385e74e317ae570886f73960c4fc366da4cafeac410c7072`）。原80056A3C・80018940・80018A5Cを実行し、比較は既存Unicorn/原子関数を共有する。SDK/GPU/SPU/IRQ境界は従来モデル。GPU画素・実音声・壁時計による速度測定ではない。main・Claudeブランチ・Android本体の変更なし。

呼出元の追跡を追加した際、独立親モデルが子関数を呼ぶ診断用戻り番地まで同一比較して初回の追加照合が失敗した。原側と独立親側の戻り番地を分けて保存し、残る全観測項目は一致比較するよう修正した。`development-caller-comparison.json` とログに残した。戻り番地の差を人物データの差として扱っていない。

## 音声開始前に挟まる描画

上の古い人物レコードを描いた1回は、戻り先が原 `80064FD0` だった。原EXEの `80064FC0..80064FE4` を確認すると、`80064550`（既存音声状態の停止）→`80018A5C`（描画）→`80064740`（要求音声の開始）の順になっている。今回の診断枝には音声番号22の開始が1件あり、この音声ラッパー内で挟まる描画と整合する。

つまり、通常の営業ループの前後2回だけを描画回数として数えると、この呼出しを落とす。時計20,580の途中で直前の構築結果を描き、その後の人物構築で店員ID6の座標が `[6,3]` から `[7,3]` に反映される。`sound-frame-audit.json` に原命令10語・呼出順・観測フレーム・音声番号を保存した。実際のセリフや音声の再生遅延を測った結果ではない。

