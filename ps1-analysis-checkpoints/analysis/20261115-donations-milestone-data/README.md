## 月初の余剰資金寄付

午前0時・日/区分1で、宣伝処理の後に各社の資金を判定する。**15億を超える**場合に発動し、寄付額は **その時点の資金−10億**。15億と同額なら発動しない。

| 判定前資金 | 発動 | 寄付額 | 同じ会社へ支払を計上した後の資金 |
|---:|---|---:|---:|
| 1,500,000,000 | しない | 0 | 1,500,000,000 |
| 1,500,000,001 | する | 500,000,001 | 1,000,000,000 |
| 1,600,000,000 | する | 600,000,000 | 1,000,000,000 |

対象会社の稼働中店舗は人気+0xC6Cを5増やし、100を上限とする。年次評価用+0xC68はこの加算の対象ではない。支払は原0x8001CBC4で資本支出台帳へ計上する。原文は「資金に余裕があるので」「町の発展のために寄付します」であり、税金として解釈していない。

自社側は通知を1件予約する。ライバル側も対応店舗の人気を上げて寄付を支払うが、この枝に通知予約はない。自社側の支払関数には先頭店舗ポインターを渡し、実際の会社選択はその所有ビットを使う。通常の先頭自社店という前提と、ライバルだけが入った生の初期ファイルを混同しない。

[donation-data.json](donation-data.json) と [費用境界・人気変換表](source-derived-boundaries.json)を参照。

## 来客記念は「アイドルを一日オーナー」

原MSG471の表示は「〔数値〕万人目の来客をきねんして、アイドルを一日オーナーによびました。」。文字制御0x4003に続く5は数値の表示幅であり、「5万人固定」ではない。

到達判定と画面表示には別の集計元がある。

| 処理 | 参照値 | 動作 |
|---|---|---|
| 到達の予約 | 自社の累積入店数量0x800CD930 | 入店前後の整数商÷10,000が増えたら、保留欄0x800CD8B8へ新しい商を保存 |
| 午前0時の消費 | 保留欄が符号付きで正、祭りフラグ0 | 保留欄を0にし、RNG%2で表示人物の配置を選ぶ |
| 記念画面の数値 | 現在の稼働中自社店+0x1188の合計 | 合計10,000以上なら、÷10,000の整数商を「万人」の数値として表示 |
| 人気の更新 | 10店舗枠の稼働/所有ビット | 記念画面から戻った後、下記の原条件で人気100を代入 |

複数の万人境界を越えても、保留欄は通知件数を蓄積せず最新の商へ置き換わる。画面の数値はその時点の店舗別累計を集計し直すため、全期間のグローバル累計と常に一致するとは限らない。

人気100を代入する原条件は **「稼働中 OR 自社所有ビット」**。そのため稼働中のライバル店と、非稼働の自社側枠も含む。非稼働のライバル枠だけが対象外となる。このORを「稼働中かつ自社」に変更しない。

また、店舗側集計が10,000未満で記念画面が早期終了しても、親の人気更新は実行される。画面のしきい値の内側へ人気更新を移すと原処理と異なる。記念画面内の現金・台帳への入金処理はなく、架空の現金ボーナスは追加しない。

画像リソース18、効果音59。120回の待機呼出しの後に入力待ちがあり、表示全体を固定120フレームと断定していない。

## 8月・区分4の祭りが優先

原MSG470は「今日は夜にお祭りがあります。」。月8・日/区分4・午前0時にリソース16、効果音58で通知する。毎回の午前0時更新で祭りフラグをリセットし、この条件のときだけ1にする。

同じ更新では来客記念を消費せず、保留値と記念用の乱数抽選を持ち越す。次の祭り以外の午前0時更新で、正の保留値があれば処理する。祭り通知だけに現金や人気のボーナスを付ける根拠は今回の範囲にはない。

[月/区分48行](calendar-events.json)、[処理順・原条件](milestone-festival-rules.json)を保存した。区分1～4は原データ値であり、暦の日付を独自に30日制へ変えていない。
