# 祭りの範囲外需要：先頭客の状態書込みと分岐への接続

2026-11-17 JST。［確実］原需要処理を最後まで実行すると、制御した入力下で購買型144の需要が先頭客の状態へ加算され、その後の原状態分岐が変わる。**自然な祭り開催まで進めたプレイではない。R02は未解決を維持する。**

## 新しい結果と既知事項

前回分かったのは、購買型144が隣接文字列を人物データとして誤読し、選択に成功すれば先頭客の位置へ需要を書き込むという条件付きのアドレス対応である。今回は次を原処理で接続した。

- 元TOWN0001を原初期化・原ロード・原店舗指標計算で展開し、需要計算0x8002619Cを最後まで実行した。需要・店舗選択のゲーム処理は差し替えていない。
- 全稼働店の営業時間番号を0、月8・stage4・時0・端数0、祭りスイッチ1、乱数種2とした診断入力で、mix136のセル(39,10)は店なし、(15,14)は店舗スロット2を選択した。
- 原0x80026868が店2の+0xF04、物理アドレス0x12E9ACへ16ビット加算を書き込んだ。ここは先頭客の状態バイトと次バイトである。
- 先頭状態0～5を与えた6条件では各状態が1増え、次バイトFFと残り30バイトは変わらなかった。通常144型の需要合計は需要合計欄と一致し、この範囲外需要はその合計に入らない。
- 直後の原客分岐0x80032814へ、親のフレームを用意して入ると以下の分岐先になった。各処理本体の直前で停止している。

| 書込み前の状態 | 書込み後 | 原分岐先 | 停止した位置 |
|---:|---:|---|---|
| 0 | 1 | 入店 | 0x800329BC |
| 1 | 2 | 買物状態2 | 0x80032ABC |
| 2 | 3 | 会計 | 0x80032B18 |
| 3 | 4 | 買物状態4 | 0x80032B8C |
| 4 | 5 | 退店 | 0x80032C0C |
| 5 | 6 | 5種類の状態処理を選ばず末尾へ | 0x80032C68 |

［確実］「正規客生成が144を使わないため影響がない」という説明では不十分である。既存客への状態書込みと分岐変更は実行できた。一方、客が消える、会計が狂う、クラッシュする、永久停止する、といった結果はこの試験からは断定できない。状態6も分岐を通らないことを確認した範囲であり、その後の全ライフサイクルは未確認である。

## 対照入力と制約

| 入力 | 範囲外の店舗選択 | 先頭客の状態書込み |
|---|---|---|
| 元TOWN0001、営業時間2・祭りなし | 呼出しなし | なし |
| 元TOWN0001、営業時間2・祭りあり | 2セルとも選択なし | なし |
| 元TOWN0001、営業時間0・祭りなし | 呼出しなし | なし |
| 元TOWN0001、営業時間0・祭りあり | (15,14)が店2 | 加算1 |
| 保存済み4店舗RAM、営業時間0・祭りあり | 2セルとも選択なし | なし |

元TOWN0001の展開状態はライバル店2店だけを含み、自社開業済み状態ではない。全稼働店の営業時間を一律に上書きしているため、ライバル設定も診断入力である。客状態0～5と次バイトFFも直接投入した。月と祭りスイッチは原開催UIや経過時間によって設定したものではない。

保存済み4店舗RAMは既存の時計24560の原営業証跡を再利用した。CPUレジスターから営業を再開したのではなく、全RAMを限定関数の入力として使用した。対象の需要・店舗選択・客分岐のコードバイトが原EXEと一致することを検証した。店舗指標を原0x80023C20で再計算し、同じ診断カレンダー・営業時間・乱数種を与えた結果である。新しいRAM複製は保存していない。

前回の在庫参照対応どおり、店2の誤読在庫は店舗順序配列の先頭を読む。元TOWN0001では先頭1で判定を通るが、保存済み営業状態では先頭0となる。店3は店0の商品15在庫を誤読し、その値も0だった。これらは今回の入力で選択を妨げる条件であり、あらゆる後続プレイで安全だという証明にはならない。

## 再現と一次資料

ユーザー提供ディスクの保存済みr2アーカイブから原EXEとTOWN0001を読み込む。アーカイブ・EXE・TOWN・保存済みRAMのSHA256は[source-provenance.json](source-provenance.json)に記録した。

```sh
python analyze-festival-state.py /path/to/source.zip
```

Python 3.12、Unicorn 2.1.4で検証した。スクリプトは保存済みアーカイブのハッシュを検証し、原テーブル初期化0x8005C858、原町ロード0x8001A0B8、原店舗指標計算0x80023C20を実行する。外部資源ロード0x800140E8のみ、提供した町バイトの読込み済み境界として戻る。ゲーム計算の呼出しを代替していない。限定関数の診断であり、PSエミュレータでの自然プレイ検証ではない。

## Androidへの扱いと残件

[移植上の扱い](android-festival-state-bridge.json)に分離した。祭り中も購買型0～143の範囲を確認してから需要を集計する。人口構成mix136の7人と有効な需要型の範囲は別に扱い、客状態を需要の保存先にしない。この安全な範囲確認自体は前回からの方針であり、今回新しく実装したAndroid機能ではない。

残るのは、通常操作による営業時間・所有・在庫の変化から自然開催時に書込み条件へ到達するかと、実際の描画・会計・次の客生成までの影響である。台帳は7項目中1件解明・6件未解決、網羅性と全体進捗率は未測定のままである。APKは更新していない。
